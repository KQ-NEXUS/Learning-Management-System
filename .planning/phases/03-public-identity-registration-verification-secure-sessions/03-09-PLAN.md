<design_decision>
## G-03-6c decided: distinguish the step-up failure. The generic copy was the wrong call.

`T-03-39` in `03-05-PLAN.md` chose the generic message so the email-change form would not be a
password oracle for an attacker holding a stolen session. That reasoning is reversed here, on purpose
and on the record:

- **The oracle does not exist to close.** An attacker holding the session already knows the account's
  email address — it is rendered on the page they are looking at. They can test candidate passwords
  against it at `/signin` with no session at all. The email-change form grants no capability the
  sign-in form does not already grant, and unlike `/signin` it is not even the natural place to try.
- **The cost falls entirely on the legitimate owner.** UAT recorded a real person unable to work out
  why their change was refused. A dead end on a self-service flow is a support ticket.
- **Nothing locked is being contradicted.** D-10 locks *that* the step-up runs before anything is
  written. It says nothing about the failure copy. `03-CONTEXT.md` contains no decision on this
  message; the generic mapping was a plan-level judgement, and this reverses that judgement rather
  than a user decision.

**Not doing, and why.** The rigorous version of the residual concern would count a failed step-up
against the sign-in lockout counter. That is deliberately not added: the same counter gates sign-in, so
a learner who fumbles their password twice on their own account page would lock themselves out of the
product entirely. The exposure being traded away is a password-guessing channel that is strictly worse
for the attacker than the one already available at `/signin`, which *is* lockout-protected. Recorded
as an accepted risk in the register below rather than left unstated.

## G-03-6b decided: revalidate AND echo the saved value. Revalidation alone does not fix it.

`revalidatePath` re-renders the server component, but the name and phone inputs are uncontrolled and
read `defaultValue`. React 19 resets an uncontrolled form after a form action completes — which is
exactly the reported symptom, the field snapping back to the pre-save server value. A DOM value already
mounted does not follow a changed `defaultValue` prop.

So the fix is two halves that only work together: `revalidatePath("/account")` so any later render is
fresh, plus the action echoing the saved profile back in its state and the fields keying off a
save counter so the post-action reset lands on the value that was actually saved.
`updateOwnProfile` already returns that profile and the action currently throws it away, so this costs
no extra read.
</design_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated non-staff browser -> `/staff/*` | A valid learner session crosses into the staff route group and must be sent somewhere sensible without disclosing staff surface. |
| learner browser -> `requestEmailChangeAction` | The failure message is the only channel through which this form can leak anything about a credential. |
| server render cache -> the account page | A stale render can show a learner a value that is no longer true of their own record. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan | Status |
|-----------|----------|-----------|----------|-------------|-----------------|--------|
| T-03-57 | Information Disclosure | the step-up failure message | low | accept | Reverses `T-03-39`. The message names the caller's own password and nothing else — never the target address, never whether it is registered. The residual password-guessing channel is strictly worse for an attacker than `/signin`, which is already reachable without a session and is lockout-protected, and the session-holder can already read the account's address off this very page. Accepted with the reversal reasoned in this plan's design-decision section rather than left unstated. | planned |
| T-03-58 | Denial of Service | a failed step-up counted against the sign-in lockout | medium | accept | Deliberately NOT wired to the lockout counter. Counting profile-page typos against the sign-in lock would let a learner lock themselves out of the entire product from their own account page — a self-inflicted denial of service worse than the guessing channel it would close. Revisit only if a per-form step-up counter separate from the sign-in lock is ever introduced. | planned |
| T-03-59 | Information Disclosure | the staff shell rendered to a non-staff caller | medium | mitigate | Unchanged from `T-03-42`: the guard still redirects before the shell renders, so the workspace nav is not disclosed. Only the destination changes, and the destination is a module constant, not a request-supplied value. | planned |
| T-03-60 | Tampering | the redirect target as an open redirect | low | mitigate | Unchanged from `T-03-44`: the destination is a module-level constant in `landing.ts`; no request-supplied value reaches the redirect call and there is no next-url parameter to abuse. | planned |
| T-03-61 | Information Disclosure | a stale account render showing another state | low | mitigate | Revalidation is scoped to the account route and the page reads only the current actor's own record through `getOwnProfile`, whose lookup derives the target from the session actor and accepts no target id. A refreshed render cannot show a different learner's data. | planned |
| T-03-62 | Spoofing | the echoed saved profile trusted over the record | low | mitigate | The echoed value originates from the service's own post-write return, not from the submitted form, so a tampered submission cannot cause the page to display a value that was not written. A reload reads the record, which is what Task 1's human check explicitly re-tests. | planned |
