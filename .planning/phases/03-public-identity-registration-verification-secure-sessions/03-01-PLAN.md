<objective>
Prove the whole public-identity pipeline end to end on one path: a visitor registers with a brand-new
email address, receives a verification email through Brevo, clicks the link, and lands on an ACTIVE
account. Every layer this phase will later expand into — the schema migration, the shared identity
constants, the pure cooldown policy, the outbound email transport, the EmailDispatch sink, the token
service, the pre-auth registration service, and the two `(auth)` screens — is wired for real on this
one path before any breadth is added.

Purpose: this is the longest new pipeline in the phase and it introduces every unfamiliar pattern at
once (an additive Prisma migration, a pre-authentication service that must not touch `withPermission`,
the first outbound third-party HTTP call in the repository, and a non-enumerating response shape). If
the architecture is wrong, one commit reveals it instead of ten.
Output: an applied migration, six new source modules, two new screens, and five new test files.
</objective>

    - `consumeToken` happy path: a fresh unexpired token claims once, runs the caller's state flip, and stamps `consumedAt`.

    a `user` slice with `findUnique` and `update`; and `$transaction`), a `dispatch` collaborator, an
    `audit` collaborator, an optional `generateToken` defaulting to `randomBytes(32).toString("base64url")`,
    and an optional `now`. Do not import or apply `withPermission` anywhere in this file — every entry
    point here runs before a session exists, and the authorization wrapper throws when there is no
    actor. Export:
    - `issueToken({ identifier, purpose, ttlMs })` — normalise the identifier with the lowercase-and-trim
      convention `signIn` already uses, read the newest row for that identifier and purpose ordered by
      `createdAt` descending, refuse with a cooldown result when `isInCooldown` says so (D-05), then
      inside one `$transaction` stamp `consumedAt` on every prior row for that identifier and purpose
      where `consumedAt` is null and `expires` is in the future (D-03) and create the new row with
      `expires` set to now plus `ttlMs`. Resolve to the raw token string for the caller to embed in a
      link; return a discriminated result so the caller cannot mistake a cooldown refusal for a send.
    - `consumeToken({ token, purpose }, apply)` — the whole claim happens inside a single
      `store.$transaction`. Inside it, run a conditional `updateMany` whose where clause matches the
      token and purpose with `consumedAt` null and `expires` strictly greater than now, setting
      `consumedAt` to now; when the reported count is not exactly 1, return the not-ok result without
      calling `apply`; otherwise read the claimed row and await `apply(tx, row)` in that same
      transaction before returning the ok result. This compare-and-set is what makes replay and the
      check-then-act race structurally impossible rather than merely unlikely, and the strict
      greater-than is what makes a token expired exactly at its `expires` instant.
    - `verifyEmail(token)` — calls `consumeToken` with the email-verification purpose and an `apply`
      that finds the User by the claimed row's `identifier` and updates `status` to `"ACTIVE"` with
      `emailVerified` set to now. Records a `user.verified` audit event with the verified user as
      actor after the transaction commits, then returns a two-state result: verified, or not-valid.
      The not-valid result carries no detail about which condition failed and no account data.
    - `resendVerification(email)` — looks up the User; when one exists with status
      `PENDING_VERIFICATION`, issues a fresh email-verification token and dispatches it; in every other
      case does nothing. Returns one single result value in all cases so the caller cannot distinguish
      the branches. Plans 02 and 03 both consume this entry point, so its shape is settled here.
    Export the default instance wired to `prisma`, `emailDispatchService.dispatch` and `recordAudit`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `/register` server action | Untrusted, unauthenticated form input crosses here. There is no session and no `withPermission` gate by design. |
| anonymous browser -> `/verify?token=` | An attacker-controlled token value crosses here and, if honoured, changes account state. |
| application server -> Brevo API | An API credential and a recipient address leave the trust boundary over the network. |
| application server -> PostgreSQL | User rows, password hashes, and single-use tokens are persisted here. |
