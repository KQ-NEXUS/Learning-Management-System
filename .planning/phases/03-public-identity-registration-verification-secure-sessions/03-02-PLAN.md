equality rather than merely asserting each branch works.

  <behavior>
    - Brand-new email: one User at PENDING_VERIFICATION, two PolicyAcceptance rows, one token issued, one dispatch call, success value returned.
    - Already PENDING_VERIFICATION: no second User row, no new PolicyAcceptance rows, a fresh token issued with the prior one invalidated, one dispatch call, the same success value returned.
    - Already ACTIVE: no User row created, no token issued, no dispatch call, the same success value returned.
    - Branch equality: the value returned by all three branches compares deeply equal.
    - Password below `MIN_PASSWORD_LENGTH`: rejected with the invalid-input value, before any store call, for all three account states alike.
    - Missing name, missing email, or either consent flag false: rejected with the invalid-input value, before any store call.
    - Lost insert race: when `user.create` rejects with a `P2002` code, the call falls through to the resend branch and returns the same success value rather than propagating the error.
    - Audit: the brand-new branch writes one `user.created` event; the already-pending branch writes one resend event; the already-active branch writes no account-mutating event.
  </behavior>

    the address by the work it triggers. Reject when the trimmed name is empty, when the trimmed email

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `/register` server action | Untrusted, unauthenticated form input including two consent flags crosses here. |
| `/register` server action -> `registration-service` | The branch decision that determines whether an account exists happens past this line and must not become observable. |
