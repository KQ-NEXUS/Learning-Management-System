<objective>
Turn the tracer's success-only verify page into IAM-02's full contract: one link that works exactly
once, and one identical, recoverable panel for every way a link can fail — expired, already used,
malformed, unknown, wrong purpose, or absent entirely — with a working resend path embedded in it.

Purpose: IAM-02 does not merely require that a bad link is rejected; it requires that a bad link leads
somewhere useful without revealing anything. A visitor whose 24-hour link expired must be able to get
a new one from the page they landed on, and an attacker probing tokens must learn nothing from the
difference between "expired" and "never existed".
Output: a two-state verify screen with an embedded recovery form, and the verification-service test
coverage that pins the token lifecycle.
</objective>

    Expiry boundary: with a frozen now, assert a token whose `expires` equals now is not claimable and a
    token whose `expires` is now plus one millisecond is claimable. The strict comparison is deliberate
    and matches `isLockedOut`'s `lockedUntil` convention in `src/server/auth/lockout.ts`; a
    greater-than-or-equal here would keep a token alive for one extra tick past its stated lifetime.

    Replay: claim a token successfully, then claim the same token again with the same frozen now, and
    assert the second call returns the not-valid result and that the caller's apply callback ran exactly
    once across both calls. Assert the fake store recorded exactly one conditional update matching the
    token, proving the claim is a compare-and-set rather than a read followed by a write.

    Purpose isolation: issue a token under the email-verification purpose and assert claiming it under
    the password-reset purpose returns the not-valid result and does not stamp `consumedAt`.

    Invalidate on reissue (D-03): issue a token, advance the frozen clock past `REQUEST_COOLDOWN_MS`, issue a
    second token for the same identifier and purpose, then assert the first token is no longer claimable
    and the second one is. Assert the first row's `consumedAt` is non-null even though nobody clicked it.
    Add a comment at that assertion recording that a stamped `consumedAt` does not mean the link was
    opened — a superseded token carries the same marker, and any later analytics that reads this column
    as a completion signal will over-count. The schema cannot express the distinction.

    Cooldown: issue a token, then issue again one millisecond before the window closes and assert the
    cooldown result with no second row; then issue again at exactly the window boundary and assert it
    succeeds.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `/verify?token=` | An attacker-controlled token value crosses here and, if honoured, changes account state. |
| anonymous browser -> `resendVerificationAction` | An arbitrary email address crosses here and causes an outbound email to be sent to it. |
| verify page -> `verification-service.verifyEmail` | The distinction between expired, used, unknown and wrong-purpose exists on this side of the line and must not cross it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan | Status |
|-----------|----------|-----------|----------|-------------|-----------------|--------|
| T-03-16 | Information Disclosure | `/verify` invalid panel | high | mitigate | One panel with fixed copy for every failure cause; the page has exactly two branches and never reads a user record on the invalid path, pinned by a test asserting the not-valid result exposes no user field. | planned |
| T-03-17 | Tampering | token replay via `/verify` | high | mitigate | The compare-and-set claim inside one transaction (plan 01) is pinned here by a replay test asserting the apply callback ran exactly once across two claims. | planned |
| T-03-18 | Elevation of Privilege | cross-purpose token use | high | mitigate | The claim predicate matches on purpose as well as token, so a password-reset token cannot activate an account and a verification token cannot set a password; pinned by a purpose-isolation test. | planned |
| T-03-19 | Denial of Service | resend form as an email-bombing vector | medium | mitigate | `resendVerification` routes through `issueToken`, which refuses inside the 60-second per-address cooldown before creating any row or sending anything (D-05); pinned by a cooldown test. | planned |
| T-03-20 | Information Disclosure | resend confirmation copy | high | mitigate | One state value returned for all four resend cases, with the confirmation phrased conditionally so it cannot be read as an existence signal; pinned by a four-way deep-equality and object-identity test. | planned |
| T-03-21 | Denial of Service | missing or malformed `token` parameter | low | mitigate | Absent, empty and array-valued parameters short-circuit to the invalid panel without calling the service; there is no error boundary in this app yet, so an unhandled throw here would surface a framework error page. | planned |
</threat_model>
