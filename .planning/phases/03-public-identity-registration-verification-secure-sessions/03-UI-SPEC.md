# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Governing decision:** CONTEXT.md D-14 locks registration, verification, reset, and profile pages to match `src/app/(auth)/signin/page.tsx` + `SignInForm.tsx`'s existing visual style **exactly** — same minimal centered Tailwind card, same typography/spacing, no marketing header/footer/hero chrome. This UI-SPEC codifies that existing, already-shipped pattern verbatim (read from source, not recalled) rather than proposing a new design language. Where this phase must add a screen `/signin` doesn't have a precedent for (the verify-link landing state, the `/account` shell), the contract extrapolates from the *same* token set, never a new one.

Declared values (must be multiples of 4):

| Token | Value | Usage |

| sm | 8px | Input vertical padding (`py-2`), button vertical padding (`py-2`) |
| — | 12px | Input/button horizontal padding (`px-3`) — a valid multiple of 4, just not one of the named round tokens |

| xl | 32px | Not used by this phase's screens (reserved, unused) |

**Exceptions:** None as violations — but one explicit non-usage rule: never use the primitives library's `gap-1.5` / `py-1.5` (6px) density (`ConfirmModal.tsx`, `ResourceForm.tsx`) on any Phase 3 screen. That 6px rhythm belongs to the staff-console primitives D-14 explicitly opts out of. Phase 3 screens use only `/signin`'s verbatim set: `gap-1`, `gap-4`, `gap-6`, `px-3`, `px-6`, `py-2`.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / subtitle / error text | 14px (`text-sm`) | 400 regular (no weight class — Tailwind base) | 1.5 (Tailwind default `leading-normal` for `text-sm`) |
| Label / button text | 14px (`text-sm`) | 500 medium (`font-medium`) | 1.5 |
| Heading (h1 page title) | 20px (`text-xl`) | 600 semibold (`font-semibold tracking-tight`) | 1.2 (tight, matches `tracking-tight` intent — no explicit `leading-*` class needed at this size) |
| Hint / helper microcopy (new this phase — e.g. "At least 10 characters", resend-cooldown text) | 12px (`text-xs`) | 400 regular | 1.5 |

**Weight note — confirmed exception to the 2-weight guideline (user-approved 2026-09-02):** `/signin` genuinely uses three weight utilities today — `font-semibold` (heading), `font-medium` (labels + button), and unstyled/default 400 (body paragraphs, error text), verified directly in `page.tsx`/`SignInForm.tsx`. The `gsd-ui-checker` flagged this against the standard 2-font-weight ceiling (BLOCK, Dimension 4). The alternative — collapsing the h1 to `font-medium` — would make these new screens' headings render lighter than `/signin`'s actual current heading, reintroducing exactly the kind of cross-screen visual mismatch D-14 exists to prevent (per the user's own stated concern: "my fear is having 2 different codes and UI that dont match"). The user explicitly chose to keep all three weights and accept this as a documented exception rather than alter `/signin`'s locked visual outcome. Treat 500/600 as the two "emphasis" weights and 400 as the unstyled body default; do not introduce a fourth weight beyond these three.

No new font sizes beyond the four above. `text-xs` (12px) is the one genuinely new addition this phase needs (for hint text `/signin` has no precedent for) — it is Tailwind's next step down from `text-sm` and is already used elsewhere in the codebase (`staff/layout.tsx`'s clock, `DetailLayout`'s meta text), so it is not an invented value.

## Copywriting Contract

Non-enumeration (IAM-06, D-08) governs every row below marked **identical-response**: the exact same string ships regardless of the internal branch (new/pending/active account; email exists/doesn't exist). This is a testable assertion, not a style preference — 03-RESEARCH.md Pitfall 5 flags this as the single easiest thing to accidentally get wrong.

| Element | Copy |
|---------|------|
| Register — primary CTA | "Create account" (button; pending label: "Creating account…") |
| Register — success (identical-response for new/pending/active, echoes the submitted email back — that's the user's own input, not a leak) | Heading: "Check your email" · Body: "We've sent a verification link to {email}. Click it to activate your account." |
| Register — cross-link | "Already have an account? Sign in" |
| Register — password hint | "At least 10 characters." (matches D-19; no complexity-class copy, since none is enforced) |
| Verify link — success | Heading: "Email verified" · Body: "You can now sign in." · CTA: "Continue to sign in" (links to `/signin`) |
| Verify link — safe generic failure (identical-response across expired/used/malformed/unknown token, per IAM-02) | Heading: "This link is no longer valid" · Body: "Links expire after 24 hours or can only be used once. Enter your email below to get a new one." · Form: email input + button "Resend verification email" |
| Forgot password — primary CTA | "Send reset link" (pending label: "Sending…") |
| Forgot password — success (identical-response whether the email exists or not) | Heading: "Check your email" · Body: "If an account exists for that email, we've sent a link to reset your password." |
| Reset password — primary CTA | "Update password" (pending label: "Resetting…") |
| Reset password — password hint | "At least 10 characters." |
| Reset password — success | Redirect to `/signin` with an inline confirmation: "Password updated. Sign in with your new password." (Not an enumeration risk — this only renders on the already-authenticated-token path, D-16 forces `signOutAllForUser` first.) |
| Reset password — safe generic failure (identical-response across expired/used/malformed token) | Same copy as Verify link's failure state, swapping the form's button for "Send new reset link" |
| Profile — primary CTA | "Save changes" (pending label: "Saving…") |
| Profile — success (per-field, inline, non-blocking) | "Saved." (small, next to the field or below the form — not a full-page redirect) |
| Profile — email change requested | "Confirm your new email address — we've sent a verification link to {newEmail}. Your current email stays active until you confirm it." |
| Profile — step-up prompt (email field) | Label: "Current password" · Hint: "Enter your current password to change your email address." |
| Error state (generic form failure, all screens) | "Something went wrong. Nothing was saved — try again." (matches `/signin`'s existing "action not applied" honesty convention; entered values are never cleared) |
| Destructive confirmation | None in this phase. No delete/revoke control ships with `/account`; the one security-sensitive action (email change) uses an inline step-up password field within the same form, not a `ConfirmModal` dialog. |

**Interaction note (not a copy row, but load-bearing):** the "identical-response" rows above must be implemented as one literal string/response shape per screen, not three near-identical strings — write the equality test 03-RESEARCH.md's Wave-0 gap list already calls for (`tests/registration-service.test.ts`, `tests/password-reset-service.test.ts`) against these exact copy blocks.
