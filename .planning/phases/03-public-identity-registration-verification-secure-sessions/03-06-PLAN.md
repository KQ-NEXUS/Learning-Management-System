<objective>
Fix the routing defect the research pass found and close the cheap secondary hardening beside it. The
sign-in action currently redirects every successful caller to a staff-only route, which was correct
while staff were the only callers and becomes wrong the moment this phase creates the first Learner.
Alongside it, the staff layout's guard checks only that someone is authenticated, so a Learner who
reaches a staff route today passes the guard and then hits an authorization error with no error
boundary in the app to catch it.

Purpose: this is the last thing standing between a verified Learner and a working first session. It
runs in its own wave because it depends on `/account` existing, and because it touches three Phase 1
and Phase 2 files that every other plan in this phase deliberately leaves alone.
Output: a pure landing-path resolver, a branched redirect, a hardened staff guard, and the sign-in
cross-links that connect the phase's three public entry points.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated non-staff browser -> `/staff/*` | A valid session belonging to a Learner crosses into a route group built for staff. |
| `signInAction` -> the redirect target | The destination is chosen from a database-sourced flag; choosing wrongly strands a caller on a route they cannot use. |
| `getActorBySessionToken` -> `Actor` | The staffness hint enters the actor shape here and must not be mistaken downstream for an authorization input. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan | Status |
|-----------|----------|-----------|----------|-------------|-----------------|--------|
| T-03-40 | Elevation of Privilege | the staffness hint read as authority | high | mitigate | The flag decides routing and chrome only. Every protected operation still resolves authority from `Assignment` rows through the permission wrapper, unchanged by this plan; a comment at each modified select clause and at the guard records this, and the layout gains no permission string. | planned |
| T-03-41 | Denial of Service | a Learner rendering a staff route | medium | mitigate | The staffness condition on the layout guard redirects before any permission-wrapped child call runs, so an authorization throw cannot surface as a framework error page in an app that has no error boundary (D-18). | planned |
| T-03-42 | Information Disclosure | the staff shell rendered to a non-staff caller | medium | mitigate | The guard redirects before the shell renders, so the workspace nav and its list of built areas are not disclosed to a Learner. | planned |
| T-03-43 | Information Disclosure | the sign-in failure shape | high | accept | The failure arm of the sign-in result is deliberately left untouched by this plan; it already collapses the missing, unverified and wrong-password cases into two reasons, and re-opening it here would risk regressing a working non-enumeration property for no gain. | planned |
| T-03-44 | Tampering | the redirect target as an open redirect | low | mitigate | The target is chosen from two module-level constants in `landing.ts`; no request-supplied value reaches the redirect call, so there is no next-url parameter to abuse. | planned |
</threat_model>
