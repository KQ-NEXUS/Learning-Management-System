<objective>
Close G-03-3, the second blocker and the one with a security consequence. None of the four
`dispatch` call sites catch a provider send failure, so the 401 seen live during UAT threw straight to
the Next.js error overlay on two separate pages. The password-reset path is the dangerous one:
`requestReset` sends only inside its `issued.ok && user && user.status === "ACTIVE"` branch, so during
a Brevo outage a real active account crashes while an unknown address returns the normal frozen
confirmation. That is a working account-enumeration oracle, and it defeats D-08 and Phase 3 success
criterion 5 (IAM-06) — the exact property four separate plans built tests for.

Purpose: an outage must degrade delivery, never disclosure and never availability. Registration
additionally commits the User row before dispatching and writes its `user.created` audit after, so a
send failure today leaves an account with no audit row — a repudiation gap that fixing the crash alone
would leave in place.
Output: a named opt-in best-effort wrapper, four guarded call sites, corrected registration audit
ordering, three defence-in-depth action guards, and a suite that can finally make a transport fail.
</objective>

<design_decision>
## The fork, decided: keep `dispatch` throwing, add a named opt-in wrapper beside it

The gap offers two shapes: swallow centrally inside `emailDispatchService.dispatch`, or catch at each
of the four call sites. Neither as stated is right; the decision is a third shape that takes the
correctness of the first and the explicitness of the second.

**Rejected — a central swallow.** `dispatch` already records the `FAILED` row before rethrowing, and
`brevo-client.ts` carries a comment saying in as many words that a send failure must never let the
caller report success. Making `dispatch` always resolve silently inverts that contract for every
future caller. Phase 13 (COM-01, exactly-once delivery) is specified against this primitive and will
need to know a send failed in order to retry it; a primitive that cannot fail cannot be retried on. A
swallow that is invisible at the call site is also the kind of thing that is correct on the day it is
written and wrong the first time someone adds a fifth caller.

**Rejected — four bare try/catch blocks.** Correct, but four copies of the same three lines, and
nothing stops the fifth caller from forgetting.

**Chosen — `dispatchBestEffort`, exported from the same module as `dispatch`.** A tiny higher-order
function taking the injected dispatch dependency and its params, returning `{ sent: boolean }` and
never rejecting. `dispatch` keeps throwing, so the primitive's contract and the brevo-client comment
stay true. Every swallow is one named call a reader sees at the call site, and the name says what it
does. It lives next to `dispatch` so anyone reading the primitive finds the sanctioned way to opt out
of its throw in the same file, rather than reinventing one.

Two consequences deliberately accepted:

- **The audit ordering is a separate fix, not a side effect.** Registration's `user.created` write is
  moved to immediately after the transaction commits, before token issuance and before the send. Not
  wrapping it — reordering it. A committed User must have an audit row whatever happens next, and the
  send is the thing most likely to fail.
- **`requestReset` keeps writing `user.password_reset_requested` even when the send fails.** The audit
  records that the reset was requested, which is true; the `EmailDispatch` row with status `FAILED` is
  the record of what happened to the email. Splitting the audit outcome on send success would put a
  send-delivery fact into the wrong table and give an operator two places to look for one answer.
</design_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Brevo -> `sendTransactionalEmail` | A third party the application does not control decides whether this call returns or throws. |
| service -> server action -> rendered page | An escaping throw becomes a framework error page, and a page that appears for one address and not another is an oracle. |
| provider availability -> observable response | Delivery is allowed to degrade; response shape is not. |
