<objective>
Close G-03-6a, the first of the two blockers. `confirmEmailChange` issues
`findUnique({ where: { pendingEmail } })` against a column that carries no `@unique`, so Prisma
throws `PrismaClientValidationError` on every confirmation click — the email-change flow shipped
completely non-functional. The suite did not catch it because the hand-written fake store in
`tests/profile-service.test.ts` answers that query happily: the mock encodes the bug instead of the
Prisma contract.

Purpose: this is the highest-severity defect in the phase and the cheapest to get wrong twice. Fixing
the one line without fixing the fake leaves the same class of bug free to reappear anywhere a fake
answers a query the database would refuse — so this plan fixes the call, fixes the ambiguity that
choosing `findFirst` exposes, and replaces the hand-written selector assumption with one derived from
`prisma/schema.prisma` itself.
Output: a working confirmation path, a schema-derived contract guard for test fakes, and a regression
test that would have been red before this plan.
</objective>

<design_decision>
## The schema question, decided: keep `findFirst`, do not add `@unique`

The gap leaves the choice open. It is decided here as **`findFirst`, with no schema change and no
migration**, for three reasons, the first of which is disqualifying on its own:

1. **`@unique` on `pendingEmail` would break non-enumeration.** `requestEmailChange` writes
   `pendingEmail` with a plain `update` and has no unique-constraint handling. Under a unique
   constraint, a second learner requesting a change to an address someone else already has pending
   would get a `P2002` thrown out of the service and rendered as a framework error page — while a
   learner requesting an unclaimed address would get the frozen `EMAIL_CHANGE_ACCEPTED`. That is
   exactly the observable difference T-03-34 and D-08 exist to prevent. Adding the constraint would
   trade a crash on the confirmation path for an enumeration oracle on the request path.
2. **The file already answers this question.** `profile-service.ts` uses `findFirst` for non-unique
   lookups at the collision check in `requestEmailChange` and again at the in-transaction re-check in
   `confirmEmailChange`. The broken line is the outlier, not the precedent.
3. **`findFirst` costs no migration.** A `@unique` addition needs a migration plus a
   duplicate-detection pass over any existing rows before it can be applied safely.

**But `findFirst` alone is not sufficient**, and this is the part the gap report does not spell out.
If two accounts can simultaneously hold `pendingEmail = "x@example.com"`, `findFirst` picks an
arbitrary one, and the confirmation can move the address onto the wrong account — a correctness bug
strictly worse than the crash it replaces. `VerificationToken` already enforces "only the newest link
works" per identifier+purpose (D-03), so the token side is unambiguous; the `User` row side is not.

The fix is the row-level analogue of D-03: before writing its own `pendingEmail`, `requestEmailChange`
clears that address from any other row. At most one account then ever holds a given pending address,
`findFirst` becomes unambiguous, and the `User` rows agree with the token rows about which request is
live. This is application-layer, needs no migration, and contradicts no locked decision — D-10 fixes
*that* the change is re-verified, not *how* the pending address is stored.
</design_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| emailed confirmation link -> `confirmEmailChange` | An untrusted token from a mailbox selects which account row is mutated. |
| `requestEmailChange` -> the `pendingEmail` column | One authenticated learner's write touches a column another learner's row may also hold. |
| test fake -> the Prisma contract | A fake that is more permissive than the database lets a broken query ship green. |
