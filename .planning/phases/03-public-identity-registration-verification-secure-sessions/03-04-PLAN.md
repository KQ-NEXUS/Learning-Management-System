<objective>
Close IAM-03's one remaining gap. Sign-in, sign-out, lockout and session revocation already shipped in
Phase 1; password reset never did. This plan adds the request half (a non-enumerating forgot-password
screen that issues a 1-hour single-use token) and the completion half (a reset screen that consumes the
token atomically, rehashes the password, and revokes every existing session).

Purpose: a forgotten password is currently an unrecoverable state for a learner, and `.planning/codebase/CONCERNS.md`
records it as the blocker on IAM-03. It is also the single highest-value token in the system — a reset
link grants account access outright, which is why D-02 gives it a quarter of the verification link's
lifetime and D-16 forces a global session revocation on completion.
Output: one new service, two new screens, and the test coverage that pins the reset lifecycle.
</objective>

  <behavior>
    - `requestReset` for an active account: issues one token with the password-reset purpose whose `expires` is exactly now plus `PASSWORD_RESET_TOKEN_TTL_MS`, and dispatches one email.
    - `requestReset` for an unknown address: issues no token, dispatches nothing, returns the same value.
    - `requestReset` for a pending-verification account: issues no reset token, dispatches nothing, returns the same value.
    - `requestReset` for a deactivated account: issues no token, dispatches nothing, returns the same value.
    - `requestReset` inside the cooldown window: returns the same value with no second token.
    - Request branch equality: all five outcomes deep-equal one another and share one object identity.
    - `resetPassword` happy path: the token is consumed, `passwordHash` is replaced with a value the injected hash collaborator produced, and `signOutAll` was called once with that user's id.
    - `resetPassword` replay: a second call with the same token returns the not-valid value, does not call the hash collaborator's result into the store, and does not call `signOutAll` a second time.
    - `resetPassword` expired token: at a frozen now equal to the token's `expires`, the call returns the not-valid value and the stored hash is unchanged.
    - `resetPassword` short password: a password below `MIN_PASSWORD_LENGTH` returns the invalid-input value without consuming the token, so the visitor's link still works on a corrected retry.
    - `resetPassword` wrong purpose: an email-verification token passed to `resetPassword` returns the not-valid value and does not change the password.
    - Lockout regression: a successful sign-in still zeroes `failedLoginAttempts` and clears `lockedUntil`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `forgotPasswordAction` | An arbitrary email address crosses here and causes an account-access-granting link to be emailed. |
| anonymous browser -> `/reset-password?token=` | An attacker-controlled token value crosses here and, if honoured, replaces a password. |
| `password-reset-service` -> `Session` rows | A successful reset must invalidate credentials issued before it. |

| T-03-24 | Elevation of Privilege | reset token replay | critical | mitigate | The compare-and-set claim inside one transaction (plan 01) plus the purpose match; pinned by a replay test asserting the stored hash is unchanged and `signOutAll` is not called a second time. | planned |
| T-03-25 | Elevation of Privilege | stale session surviving a reset | high | mitigate | `signOutAllForUser` is called immediately after the reset transaction commits (D-16), following the precedent `staff-account-service.ts` sets for deactivation; pinned by a call-count and argument assertion. | planned |
| T-03-26 | Spoofing | reset token guessing | high | mitigate | `randomBytes(32).toString("base64url")` from plan 01 gives 256 bits of entropy, and D-02 caps the reset window at 1 hour — a quarter-day narrower than the verification window because this token grants account access. | planned |
