# Phase 04.1 Plan 17: Assignment drawer focus, failure feedback and scope search resilience

The assignment drawer traps keyboard focus like ConfirmModal, keeps denied saves visible in a role=alert banner without discarding the chosen user/role/scope, and rejects stale or failed search completions instead of rendering them as selectable results. Staff account creation gains the same scope-search recovery.

## Accomplishments

- **Keyboard/modal lifecycle** (`AssignmentDrawer.tsx`): opener is saved and re-focused on close; first usable control receives focus on open with an `h2` fallback when no enabled control exists; Tab and Shift+Tab wrap both directions; Escape, the Close button and backdrop clicks are suppressed while the save is pending; cleanup restores each captured background `inert` value and never inerts an ancestor that contains the drawer.
- **Failure feedback**: form and authorization errors render in a visible `role="alert"` banner; `aria-invalid` / `aria-describedby` are wired to the matching field where a target exists; the form dispatches through an explicit `startTransition(() => action(formData))` so entered user, role and scope survive a rejected save instead of being reset.
- **Search resilience**: scope and staff-user typeaheads use a composite `type:query:retry` key; only completions matching the current key become selectable, a rejected query sets a retryable error rather than an empty success, failed scope queries clear the stale `scopeId`, and `canSave` is gated on `!scopeError && !scopePending`.
- **Staff account form** (`StaffAccountForm.tsx`): scope lookup carries pending/error state, a `catch` that surfaces "Search failed — try again" with a Retry control, and a `cancelled` guard so a superseded scope/query response cannot land; the existing `useActionState` contract and server-authoritative role/scope checks are untouched.
- No route, data model, permission, dependency or server guard file changed.
