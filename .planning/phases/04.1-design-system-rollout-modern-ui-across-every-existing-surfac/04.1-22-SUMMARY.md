# Phase 04.1 Plan 22: Retained Module Edits and Recoverable Staff Mutations Summary

**Module add/rename now keep the staff member's typed text on failure with the error next to its own control, and role-detail and assignment-panel mutations recover from a rejected Server Action with busy cleared and the dialog/reason intact.**

## Accomplishments

- **WR-04 (ModuleComposer / ArrangeClient):** composer callbacks resolve to an explicit `{ok:true}|{ok:false,message}` result. A failed add keeps the typed title and shows the error under the add input; a failed rename stays in edit mode with the typed name and a row-local `role="alert"`, never under the add input. Concurrent duplicate submits are blocked per control; busy always clears in `finally`. ArrangeClient translates the resolved action result and catches unexpected rejection.
- **WR-06 (RoleDetailPanels):** `updateRoleAction` (both the direct addition-only submit and the ConfirmModal permission-removal path) and `setRoleActiveAction` are wrapped `try/catch/finally`. A rejection clears busy, keeps the ConfirmModal open with the typed reason, and shows generic operation-specific feedback. Permission-catalogue IDs, optimistic version and last-administrator/continuity protections are unchanged (they live in the action/service).
- **WR-06 (AssignmentsPanel):** `revokeAssignmentAction`, `deactivateStaffAccountAction` and `reactivateStaffAccountAction` calls are wrapped `try/catch/finally`. A rejection keeps the ConfirmModal open with the reason, emits generic feedback, clears busy, never reports the mutation as applied, and does not auto-retry. Bound assignment/account IDs and service authorization are unchanged.
- Three new focused component test files cover, for each surface, the rejected-promise path, the resolved `{ok:false}` path, and a later user-triggered success.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Component tests flaked under the full parallel suite**
- **Found during:** Post-task verification (running `vitest run --project components` with all 12 workers)
- **Issue:** The default 5 s per-test timeout is too tight for the heavy `RolePermissionsPanel` / `AssignmentsPanel` mounts (full `PermissionPicker`, `AssignmentDrawer`) when the machine is saturated — the same class of flake `tests/components/setup.ts` already documents for editor mounts. Runs in isolation always passed.
- **Fix:** Raised the affected `it()` timeouts to 20–30 s and the inner `findBy`/`waitFor` ceilings to 10–15 s; double-flushed microtasks in the composer tests. Ceilings only — a query still resolves the moment its node exists.
- **Files modified:** the three new test files
- **Verification:** isolated full `--project components` run — 154/154 pass
- **Committed in:** `08f7ae6`, `13e424c`

**2. [Rule 3 - Blocking] `createRoleAction` missing from the role test's action mock**
- **Found during:** Task 2
- **Issue:** `RoleForm` (rendered by `RolePermissionsPanel`) consumes `createRoleAction` via `useActionState`; a partial `vi.mock` of `@/app/staff/roles/actions` threw "No 'createRoleAction' export is defined".
- **Fix:** Added `createRoleAction: vi.fn(async () => ({ errors: [] }))` to the mock (edit panel never invokes it).
- **Files modified:** `tests/components/role-detail-panels.test.tsx`
- **Committed in:** `045a434`
