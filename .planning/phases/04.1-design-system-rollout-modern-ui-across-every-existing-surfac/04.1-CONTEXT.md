<domain>
## Phase Boundary

Retrofit every surface that already exists — 30 routes: 18 `/staff/*`, 6 `(auth)`, 4 public catalogue,
`/account`, and the root redirect — onto one approved design system, so Phase 5 onward is built to it
rather than retrofitted after the fact.

**This is a full visual redesign, not a repalette.** That is the single most important correction this
discussion produced. The approved mockup specifies a new brand ramp, a new neutral ramp, a new type
stack, a new depth model (radius + shadow + paper ground), a dark navy staff sidebar, a split-panel
auth shell, and a wide learner shell for `/account` and the public catalogue. Every one of those is a
structural change to files `04.1-UI-SPEC.md` concluded needed no change at all.

**In scope:** the token chain in `globals.css`; the four primitives (`ResourceTable`, `ResourceForm`,
`DetailLayout`, `ConfirmModal`); `staff/layout.tsx`; a new `(auth)/layout.tsx`; a shared learner shell
for `(public)` + `/account`; Phase 4's six bespoke components; the typeface and icon system; and the
WCAG 2.2 AA (NFR-09) reconciliation the new palette forces.

**Out of scope:** new features, new routes, new data, new permissions. No screen gains or loses a
capability. The root `/` route is a pure `redirect()` with no visual surface — no plan task for it.

</domain>

## Implementation Decisions

### Mockup authority and ambition

- **D-01:** The 28-screen mockup named in ROADMAP.md — `https://claude.ai/code/artifact/a4e2573f-256a-4b84-994f-32f9350aca26`,
  titled "KQ Nexus Modern" — **is** the design contract and **is** reachable. `04.1-UI-SPEC.md` states it
  was unreachable and that "nothing below was invented from it"; that was an environment limitation, not a
  fact about the artifact. It was read this session via the Artifact tool (`action: "read"`), and its source
  is now vendored into the phase directory so no downstream agent depends on network access to it
  (see `<canonical_refs>`).
- **D-02:** **Full adoption.** Phase 04.1 implements the mockup's design system in its entirety — palette,
  neutrals, typography, radius, shadow/depth model, paper ground, staff sidebar, auth split panel, learner
  shell, gradient brand treatments. Not a subset, not "colour and type only."
  — **Reversibility:** costly — the neutral swap (D-14) and the shell rebuilds touch most files that declare
  a colour or a layout wrapper; reverting means re-editing the same breadth of files, though no data,
  schema, or public contract is involved.
- **D-03:** `04.1-UI-SPEC.md` is **regenerated**, not patched. Re-run `/gsd-ui-phase 04.1` after this
  discussion. Sections contradicted by the mockup: §0.2/§0.3 (aesthetic preserved, "no component file needs
  editing"), §3 (spacing frozen), §4 (typography frozen), §5.2/§5.3 (accent→teal, blue removed), §5.5 (the
  full list of colour-touching files), §8 rows 1/2/5/6/7/8 (per-surface "no code change expected"), §9
  (token repalette only), and the Appendix's three open questions — all now resolved here. Sections that
  remain accurate and should be carried forward by the regenerated spec: §0.1 (verified route inventory),
  §0.4/§0.5 (which files import the primitives and the exact `(auth)` duplication), §2 (the primitives'
  current TypeScript contracts), §6 (copywriting — preserve verbatim), §7 (state coverage: 92 considerations,
  71 explicit / 14 backstop / 7 unresolved).
- **D-04:** **System-faithful, not pixel-faithful.** The tokens, shell structures, depth model and component
  treatments are binding; exact pixel positions are not. The mockup draws 28 screens; the app has 30 routes,
  and roughly forty screens are configured from `ResourceTable` rather than written by hand. Screens not
  drawn inherit the system through the primitives. This preserves ROADMAP criterion 3 ("without any
  per-screen styling") — the change lives in `staff/layout.tsx` and the four primitives, exactly as the
  criterion requires.

### Typography

- **D-05:** Body/UI face ships as **Segoe UI Variable first, Plus Jakarta Sans as the loaded fallback**,
  per the mockup's own type annotation: *"If you are shipping to real browsers, Segoe UI Variable is free on
  Windows and worth keeping in the stack ahead of it."* Plus Jakarta Sans was itself a forced substitute —
  the original reference used Aptos and Segoe UI Variable, neither of which an Artifact can load.
  **Known consequence, accepted:** Segoe UI Variable is a Windows system face, so Windows users see a
  different typeface from macOS/Linux/Android users, who fall through to Plus Jakarta Sans. The app will
  not render identically across platforms. Plus Jakarta Sans loads via `next/font/google`.
  Geist Sans is retired.
- **D-06:** Mono face becomes **IBM Plex Mono**, replacing Geist Mono. The mockup uses it for the auth
  panel's locale footer; adopting it as the single mono face also changes every tabular figure in the staff
  tables (`Column.mono`). Loads from Google Fonts via `next/font/google`.
- **D-07:** Display tracking from the mockup is binding: `-0.035em` on headings, `-0.045em` on `h1`.

### Colour — brand, accent and state

- **D-08:** **Blue stays the brand.** `--primary`, `--ring`, links and active nav are brand blue
  `#2457d6` (slightly brighter than today's `#1c4ed8`, chosen because it reads better beside teal), with
  `--color-brand-deep #15398f` for the 140° gradient on primary buttons and the logo mark.
  This **overturns `04.1-UI-SPEC.md` §5.2**, which inferred that teal replaced blue entirely. The mockup's
  own annotation is explicit: *"Blue stays the brand; teal now means progress, pass and grade; amber means
  course state."*
- **D-09:** **Teal is state-only and never interactive.** `#12a594` marks progress, pass/grade and
  completion. It must not be spent on buttons, links, focus rings or active navigation. A hard rule, so the
  executor cannot misapply it per screen.
- **D-10:** **Green stays distinct for success** — `#15803d` (5.02:1 on white, already passing). The mockup
  sets `--color-green` and `--color-teal` to the same hex, which would make a success pill and the accent
  indistinguishable; its own annotation quotes three roles ("Education teal + course amber + grade green"),
  and no teal pill is drawn anywhere in the 28 screens. Green wins.
- **D-11:** **Danger keeps the codebase value** `#b42318` with its paired surface `#fdf3f2`, not the
  mockup's `#d92d20`. Rationale: 6.57:1 vs 4.84:1 gives real headroom, error text sits on the surface tint
  in `ConfirmModal` and `PublishDialog` where the brighter red drops uncomfortably low, and the mockup does
  not specify a paired surface at all.
- **D-12:** **The two-tone fill/text-safe rule stands** on top of the mockup palette, per ROADMAP criterion 2.
  Fills go on dots, bars, indicators and non-text surfaces; text-safe siblings go wherever the colour
  carries words. Non-negotiable regardless of aesthetics — teal is 3.07:1 and amber 2.36:1 on white, both
  below the 4.5:1 that NFR-09 requires for text.
  - Amber text-safe: **`#b45309`** — the ROADMAP's locked value, already `--warning` today. The mockup draws
    `#b54708`; the difference is imperceptible and the roadmap value avoids a contradiction between documents.
  - Amber fill: **`#f79009`** — the mockup's dot value, used uniformly for every amber indicator.
    ⚠ **This amends ROADMAP criterion 2**, which names `#e09b34` explicitly. `#e09b34` is retired from the
    palette. The roadmap line must be corrected rather than left contradicting this file.
  - Teal fill `#12a594` / teal text-safe `#0f766e` — both as the roadmap locks them.

### Status pills

- **D-13:** **Adopt the mockup's tinted pill**, retiring the current "neutral pill, tone-coloured dot,
  `text-zinc-700` label" contract that `04.1-UI-SPEC.md` §2.1 listed as "do not regress". Each semantic
  colour carries three tones — tint background, deep ink text, mid-tone dot:
  | Tone | Tint bg | Ink | Dot |
  |---|---|---|---|
  | Green (success) | `#ecfdf3` | `#067647` | `#17b26a` |
  | Blue (info/brand) | `#eff4ff` | `#1e40af` | `#3b6ef5` |
  | Amber (course state) | `#fffaeb` | `#b45309` | `#f79009` |
  | Grey (neutral) | `#f7f7f7` | `#525252` | `#a3a3a3` |
  This dissolves the amber contrast problem `04.1-UI-SPEC.md` §5.4/§7.14 flagged as needing a WCAG 1.4.11
  bordered-pill exemption: `#b45309` on `#fffaeb` computes to roughly 5.3:1, passing outright, with the dot
  as pure reinforcement. **No exemption is needed and none should be claimed.**
  — **Reversibility:** reversible — `StatusPill`'s tone map is a single lookup object in `ResourceTable.tsx`.

### Neutrals and contrast

- **D-14:** **Full swap from Tailwind's zinc ramp to the mockup's cool neutrals** — ink `#101828`,
  muted `#667085`, line `#dfe5ee`, paper `#f5f7fb`, surface `#ffffff`, surface-2 `#eef3fb`. Every `zinc-*`
  usage migrates to a semantic token. Rationale: the mockup's ground is cool blue-grey; leaving warm zinc
  greys beside `#f5f7fb` paper reads muddy, and half-migrating guarantees two neutral families coexist —
  precisely the "two different UIs that don't match" problem flagged in Phase 3.
  — **Reversibility:** costly — touches most files that declare a colour; no schema or contract involved.
- **D-15:** **Input borders are darkened; decorative borders are not.** In the mockup an input is a white
  box with a `#dfe5ee` border on `#f5f7fb` paper — white-on-paper is ~1.07:1 and the border ~1.3:1, so
  nothing identifies the control at the 3:1 NFR-09 requires (WCAG 1.4.11). Inputs, selects, textareas and
  checkboxes get an edge that clears 3:1 (around `#667085`); card outlines, table row dividers, tab strips
  and panel frames keep `#dfe5ee` — a row or card is identified by its content and layout, not solely its
  edge. This is a deliberate, documented divergence from the drawn design, taken because NFR-09 is a locked
  requirement of this phase.
- **D-16:** **All `text-zinc-400` micro-text moves to the muted token** `#667085` (~4.97:1 on white,
  ~4.6:1 on paper). One rule, no per-site judgement. Covers the 19 call sites `04.1-UI-SPEC.md` §5.4
  enumerated: required/optional markers, sort arrows, filter-chip dismiss, tab-badge counts, drag handles,
  and the "not yet checked" hints.
- **D-17:** **Contrast is verified against both grounds** — white card *and* `#f5f7fb` paper — and the
  computed ratios are recorded in the regenerated UI-SPEC. Muted at ~4.6:1 on paper passes with almost no
  margin, so it must be checked rather than assumed.

### Depth model

- **D-18:** **Full shadow on sparse surfaces, subtle shadow on dense ones.** Public, auth, account and
  detail cards take the mockup's `0 18px 48px rgba(16,24,40,.10)`; staff list and table containers take
  `--shadow-xs` (`0 1px 2px rgba(16,24,40,.06)`). This follows the mockup's own warning verbatim:
  *"shadows stack visually when cards sit close together, and the staff screens have the densest layouts in
  the app."* Radius is adopted as drawn everywhere — 16px cards, 11px controls, 38px control height.

### Shells

- **D-19:** **Staff shell** — `staff/layout.tsx` is rebuilt around a 228px dark navy sidebar
  (`#0d1b3d`, fg `#eef3fb`, active row `#15398f` + white text, muted `#8fa3cf`, border `rgba(255,255,255,.10)`).
  Nav is the mockup's flat five items with a dot indicator per item: Courses, Programmes, Users, Roles, Audit.
  ⚠ `04.1-UI-SPEC.md` §8 row 5 says "No code change expected" for this file. That is wrong — this is the
  largest single structural change in the phase.
- **D-20:** **The disabled "Cohorts" and "Enrolments" nav items are removed.** The nav shows only routes
  that exist; Phase 5 adds them when it builds them. This eliminates the one WCAG 1.4.3 inactive-component
  exemption `04.1-UI-SPEC.md` §5.4 carved out — after this phase there is no legitimate sub-3:1 element
  anywhere in the app.
- **D-21:** **Auth shell** — one `(auth)/layout.tsx` owning a split panel: 44% navy panel on the left
  (logo lockup top, headline + subcopy at the bottom, mono locale footer) and a flex-1 centred column on the
  right holding a `max-width: 378px` form stack with `gap: 20px`, an optional icon chip, a 25px `h1` and 14px
  subcopy, on the `#eef3fb` muted ground. All six routes strip their duplicated
  `mx-auto flex min-h-screen max-w-sm flex-col justify-center gap-6 px-6` wrapper — satisfying ROADMAP
  criterion 4 far more strongly than a bare shared column would.
  ⚠ **ROADMAP criterion 4's "rendered output is pixel-identical to today" done-condition no longer applies**
  and must be dropped; the auth screens change completely by design.
- **D-22:** **Phase 3's D-14 is superseded.** That decision chose "no marketing header/footer/hero chrome"
  on auth-adjacent screens. The mockup's navy panel carries a headline ("Professional training that an
  employer can verify.") and subcopy. D-14's real intent was that auth screens must not drift apart from
  each other — one shared `(auth)/layout.tsx` satisfies that intent more strongly than the old bare column,
  since all six routes now get provably identical chrome. Copy comes from the mockup verbatim.
- **D-23:** **One shared learner shell** serves both `(public)/layout.tsx` and `account/layout.tsx`:
  white top bar on the muted ground, gradient logo mark, "Catalogue | Account" nav with a 2px underline on
  the active item, avatar chip top-right, `max-width: 1080px` container, `14px 28px` padding.
  `account/layout.tsx`'s `max-w-sm` centred wrapper is deleted. This settles `04.1-UI-SPEC.md` §7.7 and
  Appendix item 2, which left `/account` narrow because the mockup was unreachable — the mockup in fact
  draws it wide.

### Icons

- **D-24:** **Add `lucide-react`.** The app has zero icons today; the mockup uses inline stroke SVGs at
  1.7 stroke width, which is lucide's geometry. Per-icon imports tree-shake, so unused icons cost nothing,
  and later phases (cohorts, payments, certificates) get a full set rather than hand-drawing each one.
  One new dependency. This settles `04.1-UI-SPEC.md` Appendix item 3, which declined to decide.

### Scope of opportunistic fixes

- **D-25:** **Fix the cheap pre-existing gaps, defer the rest.** Of the 7 unresolved items in
  `04.1-UI-SPEC.md` §7, take those that are a few lines and live in files this phase already opens:
  `RichTextEditor`'s missing empty-state placeholder, a fallback for broken image/video URLs that pass the
  scan, and the unverified public-catalogue empty states. Defer `ArrangeBoard`'s initial-load contract,
  `RichTextEditor`'s loading affordance, and `LessonContent`'s long-body handling to the phases that own
  those flows (see `<deferred>`).

### Verification

- **D-26:** **State-render tests plus a manual 28-screen walkthrough.** Extend the Vitest suite so each
  primitive asserts all five states still render (loading, empty, denied, error, validation-error), then walk
  the 28 drawn screens by hand against the mockup. No visual-regression tooling this phase: baselines would
  have to be captured *after* the redesign lands, so they would prove nothing about this phase's own change,
  and the Playwright MCP server failed to connect this session. Visual judgement on a redesign stays human.
  The 14 "backstop" rows in `04.1-UI-SPEC.md` §7 — concentrated on long-text and overflow — are the specific
  checks the walkthrough must cover, and they carry more weight now that every surface changes, not fewer.

### Claude's Discretion

Left to the regenerated UI-SPEC to resolve against the drawn screens, all consequences of D-04
(system-faithful) rather than open questions:

- The segmented filter control the mockup draws on staff lists ("All / Published / Draft", active segment =
  white fill + `shadow-xs`) versus `ResourceTable`'s current select-and-dismissible-chip filters. Note the
  behaviours §2.1 requires must survive whichever affordance wins: filters and sort read from the URL, and a
  filter validation error keeps the previous rows visible beneath it.
- Responsive and narrow-viewport behaviour — the mockup is drawn at 1280px only and nothing narrow exists.
  `ResourceTable`'s existing below-640px card treatment (never horizontal scroll) must survive.
- Dark mode — not drawn anywhere in the mockup; not introduced by this phase.
- The exact darkened input-border value satisfying D-15 (`#667085` is the working assumption).

<code_context>
## Existing Code Insights

### Reusable Assets

- **The four primitives** (`src/components/primitives/`) — `ResourceTable` (+`StatusPill`), `ResourceForm`
  (+`FormField`, `TextInput`), `DetailLayout` (+`DetailFacts`), `ConfirmModal`. Roughly forty screens are
  configured from these rather than written by hand, so they are the leverage point: restyling them
  propagates to most of the app for free. Their *contracts* are correct and stay; only their visual
  implementation changes.
- **`FormField`'s render-prop shape** — deliberately misuse-resistant: a control cannot be rendered without
  its aria wiring (`id`, `name`, `aria-invalid`, `aria-describedby`). Keep this API exactly as it is.
- **`next/font/google`** — already wired in `src/app/layout.tsx` for Geist; swapping in Plus Jakarta Sans
  and IBM Plex Mono is the same mechanism, not new infrastructure.
- **Tailwind v4 `@theme inline`** — already the project's config mechanism. The new token chain is a
  `globals.css` edit, not a build-config change.

### Established Patterns

- **Zero raw hex outside `globals.css`** — verified true today. Every component consumes colour through
  Tailwind utilities bound to custom properties or the zinc scale. Preserve this: ROADMAP criterion 1 requires
  it, and it is what lets the palette change centrally.
- **Utility class names are the migration seam** — keeping semantic names stable (`bg-accent`, `text-danger`,
  `bg-danger-surface`) means a token change needs no find-and-replace. New tokens (paper, surface-2, ink,
  muted, line, the pill tones, `-fill` siblings) add names rather than renaming existing ones wherever possible.
- **Archive, never delete** (CAT-08) and **no delete affordance in `ResourceTable`** — a product rule the
  restyle must not accidentally reintroduce.
- **RBAC-06 denial parity** — `denied` renders identical copy whether or not the record exists, leaking no
  count, title or id. A visual change must not introduce a distinguishing cue.

### Integration Points

- `src/app/globals.css` — the token chain; everything else depends on it landing first.
- `src/app/layout.tsx` — font wiring (D-05, D-06).
- `src/app/staff/layout.tsx` — navy sidebar rebuild (D-19, D-20).
- `src/app/(auth)/layout.tsx` — **new file**; the six page files strip their wrapper (D-21, D-22).
- `src/app/(public)/layout.tsx` + `src/app/account/layout.tsx` — the shared learner shell (D-23).
- `src/components/primitives/*.tsx` — pills, borders, radius, shadow, muted text (D-13, D-15, D-16, D-18).
- `src/app/staff/audit/AuditTable.tsx`, `staff/users/AssignmentDrawer.tsx`, `staff/roles/PermissionPicker.tsx`
  — duplicate primitive-style markup locally and need the same treatments applied by hand
  (`04.1-UI-SPEC.md` §0.4 remains the accurate inventory here).
- `package.json` — `lucide-react` (D-24). Note it is already modified in the working tree.

**Sequencing:** the token chain must land before anything else can be visually verified. After that the
shells (staff / auth / learner) and the primitives are independent of each other and parallel-eligible; the
six bespoke Phase 4 components depend only on the primitives and tokens.

<specifics>
## Specific Ideas

- The mockup's `converge` annotation is the decisive statement on colour and should be quoted to any agent
  that questions D-08: *"Blue stays the brand; teal now means progress, pass and grade; amber means course
  state."* Two independent sources (the user's own reference and a 192-profile product database) both put
  teal in an LMS — but as accent beside the blue, not as a replacement for it.
- The mockup's `reference` annotation names the depth model as the largest departure: *"shadcn casts 1-3px,
  your reference casts 48px. Depth is doing the work that borders did before."* That sentence is the design
  intent behind D-18 and behind keeping decorative borders light in D-15.
- The mockup's `honest` annotation is a self-critique worth preserving: the 48px shadow *"is the thing most
  likely to date. It reads as current now; hairlines and flat surfaces read as current too, and have for
  longer."* D-18 is the hedge against that, not a rejection of the look.
- Auth panel copy, verbatim from the mockup: headline *"Professional training that an employer can verify."*,
  subcopy *"Every certificate carries a public verification link. No phone call, no letterhead."*,
  mono footer *"AFRICA/LAGOS"*.

</specifics>
