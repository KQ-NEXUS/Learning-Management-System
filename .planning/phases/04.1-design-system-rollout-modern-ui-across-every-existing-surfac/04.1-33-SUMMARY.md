# Phase 04.1 Plan 33: ConfirmModal / PublishDialog pending-window focus containment Summary

**Both integrity dialogs now hold keyboard focus on the dialog container while every control is disabled during the in-flight pending window, closing WR-01 (the ConfirmModal/PublishDialog half of G-RV-03).**

## Performance

- **Duration:** ~8 min
- **Started:** 2026-09-07T12:27:00Z
- **Completed:** 2026-09-07T12:31:00Z
- **Tasks:** 2
- **Files modified:** 4

## Accomplishments

- `ConfirmModal` Tab handler no longer bails out with a bare `return` when the focusable list is empty; it calls `event.preventDefault()` and focuses `dialogRef.current`. Added `tabIndex={-1}` to the `role="dialog"` container so it can take that focus.
- `PublishDialog` Tab handler got the same empty-list repair (its container already carried `tabIndex={-1}`).
- Added a pending-window focus-escape regression to each suite: with every control disabled, a `Tab` keydown is `defaultPrevented` and `document.activeElement` is the `role="dialog"` element. Each was proven to fail against the pre-repair source.
- Added a companion idle-wrap assertion to `confirm-modal.test.tsx` pinning the unchanged behaviour (Tab from the last focusable still wraps to the first and is still `defaultPrevented`).

## Decisions Made

- Container-trap fix over `inert`/`aria-hidden` background: deterministic under jsdom, no layout change, respects the plan's "no new primitive/prop/route" scope discipline. `AssignmentDrawer` / `StaffShell` `inert` treatment was deliberately not retrofitted.
- Regressions assert `event.defaultPrevented` + `document.activeElement` (the two things the handler actually controls) because jsdom does not implement sequential focus navigation — same technique the existing focus-wrap tests use.
