The core fixes are sound and the new tests pass (32 component/route tests + 84
design-contract assertions, all green):

- `ArrangeClient` / `ProgrammeArrangeClient`: the save/add/remove handlers now wrap

## Warnings

### WR-01: `handleRestore` swallows every failure silently — same class of bug this wave closes

**File:** `src/app/staff/courses/[id]/arrange/ArrangeClient.tsx:201-204`

```ts
async function handleRestore(kind: "module" | "lesson", id: string) {
  const res = await restoreItemAction({ courseId, kind, id });
  if (res.ok) router.refresh();
}
```

This wave adds `try/catch/finally` recovery to every other imperative Server Action
handler in the file, but `handleRestore` is left untouched:

- On a graceful `{ ok: false }` result the `if` simply falls through — nothing is
  shown, the item stays in the "Withdrawn" list, and the user gets no signal that
  the restore did not take.
- On a promise rejection (network drop, action runtime error) this produces an
  unhandled promise rejection and, again, no user feedback.
- `ArrangeBoard`'s "Restore" button (`src/components/catalogue/ArrangeBoard.tsx:377-384`)
  has no `disabled`/busy state, so there is no pending indicator to strand — but also
  nothing that tells the user the click did anything.

This is the exact "ambiguous mutation, no recovery" failure class G-RV-01/CR-01 exist
to close; `restoreItemAction` was just missed.

**Fix:** give it the same shape as the other handlers, driving a visible error. e.g.:
```ts
async function handleRestore(kind: "module" | "lesson", id: string) {
  try {
    const res = await restoreItemAction({ courseId, kind, id });
    if (res.ok) {
      router.refresh();
    } else {
      setModuleError(res.message); // or a dedicated restoreError slot
    }
  } catch {
    setModuleError("Something went wrong restoring that item. Nothing was changed — try again.");
  }
}
```

### WR-02: Blanket `catch` around Server Actions will swallow `NEXT_REDIRECT` / `NEXT_NOT_FOUND`

**File:** `src/app/staff/courses/[id]/arrange/ArrangeClient.tsx:119`, `151`, `174`, `193`;
`src/app/staff/programmes/[id]/arrange/ProgrammeArrangeClient.tsx:98`, `117`, `135`;
`src/app/staff/courses/[id]/lessons/[lessonId]/LessonEditorClient.tsx:59`

Every new `catch` block is a bare `catch { setXError("Something went wrong …") }`. If
any awaited action ever calls `redirect()` or `notFound()`, Next throws a control-flow
error (`error.digest` starting `NEXT_REDIRECT` / `NEXT_NOT_FOUND`) that these blocks
would swallow and mis-report as a spurious "Nothing was changed — try again." even
though the mutation succeeded.

This is not hypothetical: `saveLessonAction` in the sibling
`.../lessons/[lessonId]/actions.ts:166` already calls `redirect()`, and
`withdrawLessonAction` in that same file only dodges the trap by *convention* — its
comment (lines 202-205) explicitly says it must return a result rather than
`redirect()` "which that handler's try/catch would swallow". The safety of the whole
pattern currently rests on every present and future action author remembering that
rule.

**Fix:** re-throw framework control-flow errors before treating a rejection as a
generic failure:
```ts
} catch (error) {
  if (
    typeof error === "object" && error !== null && "digest" in error &&
    typeof (error as { digest?: unknown }).digest === "string" &&
    /^NEXT_(REDIRECT|NOT_FOUND)/.test((error as { digest: string }).digest)
  ) {
    throw error;
  }
  setModuleError("Something went wrong saving the module order. Nothing was changed — try again.");
}
```
(or a shared `isFrameworkError(e)` helper, or Next's `unstable_rethrow` where available.)

### WR-03: `confirmWithdraw` success path leaves the modal stuck on "Working…" if client navigation stalls

**File:** `src/app/staff/courses/[id]/lessons/[lessonId]/LessonEditorClient.tsx:52-58`

```ts
if (result.ok) {
  router.push(`/staff/courses/${courseId}/arrange`);
  router.refresh();
  return;               // withdrawing stays true, withdrawOpen stays true
}
```

On success neither `setWithdrawing(false)` nor `setWithdrawOpen(false)` runs — the
code relies on the component unmounting via navigation. If `router.push` resolves
slowly, or the target route throws during render, the user is left on a modal showing
"Working…" with ESC suppressed (`ConfirmModal` suppresses ESC while `pending`) and no
way out short of a reload. The withdraw already committed server-side, so this is an
ambiguous-state surface of the same kind CR-01 targets.

**Fix:** close the modal / clear the pending flag before navigating, or wrap the nav
so a failure re-enables the dialog:
```ts
if (result.ok) {
  setWithdrawOpen(false);
  setWithdrawing(false);
  router.push(`/staff/courses/${courseId}/arrange`);
  router.refresh();
  return;
}
```

## Info

### IN-01: Avatar renders an empty circle when the email local-part has no alnum segments

**File:** `src/app/account/layout.tsx:45-48`

When `profile.name` is blank and the email local-part yields no `._-`-delimited
segments with a leading character (e.g. `"@example.com"`, or a local part that is all
punctuation), `initials` becomes `""`. The `role="img"` span then renders a coloured
circle with no glyph, carried only by `aria-label`. Acceptable degradation, but
consider a single fallback glyph (first alnum char of the email, or a generic
person icon) so the chip never looks broken.

### IN-02: Focus trap only recaptures at the first/last boundary

**File:** `src/components/primitives/ConfirmModal.tsx:92-118`;
`src/components/catalogue/PublishDialog.tsx:102-127`

The Tab handler wraps only when `document.activeElement === first` / `=== last`. Focus
that lands outside the dialog by other means (a background click moving focus to
`document.body`, or focus sitting on a non-boundary element) is not pulled back on the
next Tab — except during the all-disabled pending window, which this wave now handles.
The pending-window fix is correct; this is the pre-existing limitation of the
hand-rolled trap and is noted only so it is not mistaken for fully solved. A real
focus-trap util (or `inert` on the background) would close it.

### IN-03: `flush()` helpers depend on a fixed microtask-tick count

**File:** `tests/components/arrange-client.test.tsx:46-52`;
`tests/components/programme-arrange-client.test.tsx:45-50`

`flush()` hard-codes three `await Promise.resolve()` ticks to settle "the action
promise, the handler body, and the component's `finally`". Any refactor that adds an
`await` to a handler (e.g. the `isFrameworkError` guard in WR-02, or an extra service
round-trip) silently under-flushes and the assertions race. Prefer `await vi.waitFor(...)`
or `await screen.findBy...` on the post-condition rather than counting ticks.

### IN-04: Rejection-recovery tests cover only the two save handlers

**File:** `tests/components/arrange-client.test.tsx`

The suite proves `handleSaveModuleOrder` and `handleSaveLessonArrangement` recover
from a rejected action, but `handleRestore` (see WR-01), `handleAddModule` and
`handleRenameModule` are in the same "translate a rejection into a definite result"
class and are untested here. Add a rejected-`restoreItemAction` case in particular —
it would currently fail, surfacing WR-01.
