## 2. Existing Primitives — Component Contracts (unchanged; carried forward per D-03)

> Not a shadcn-style installed-package inventory — `Tool: none`, so the template's `## Component
> Inventory` provenance-line requirement does not apply. This is the hand-rolled equivalent: the
> four components the roadmap calls "the primitives," documented from their current TypeScript
> contracts at `src/components/primitives/*.tsx`. **These contracts do not change under this
> regeneration** — only their visual implementation (radius/shadow/border/color, per §3–§5) does.

### 2.1 `ResourceTable<T>` — the list primitive

`src/components/primitives/ResourceTable.tsx`. Used by ~20 of the ~40 list/detail screens per its
own doc comment.

- **States** (`ResourceTableState<T>`, discriminated union): `loading` · `ready` (rows) ·
  `empty` (`activeFilterCount?`, `totalWithoutFilters?`) · `denied` (`permission?`) ·
  `error` (`message?`, `trace?`, `attempt?`, `maxAttempts?`)
- **Props**: `noun`, `title?`, `columns: Column<T>[]`, `state`, `getRowKey`, `getRowHref?`,
  `getRowLabel?`, `shownCount?`, `totalCount?`, `filters?: TableFilter[]`, `onFilterChange?`,
  `activeQuery?`, `onClearFilters?`, `sort?: SortState`, `onSortChange?`, `selection?: BulkSelection`,
  `headerActions?`, `validationError?`, `onRetry?`, `onCreate?`, `createLabel?`, `primaryColumnKey?`
- **`Column<T>`**: `key`, `header`, `render`, `subtitle?`, `width?` (held during loading — no reflow
  on data arrival), `align?`, `mono?` (now IBM Plex Mono, D-06), `hideOnMobile?`, `sortable?`
- **Behaviors already correct, do not regress:** filters/sort read from the URL and shown as a
  dismissible query chip; a filter validation error keeps previous rows visible beneath it; denied
  renders identical copy whether or not the record exists (RBAC-06); below 640px rows become cards,
  never horizontal scroll; no delete affordance anywhere — archive replaces it (CAT-08).
- **`StatusPill`**: `label`, `tone?: "neutral" | "success" | "warning" | "danger" | "accent"`. **This
  prop signature does not change.** What changes is the visual per tone — the old "neutral pill,
  tone-colored dot only, `text-zinc-700` label" contract is superseded by the mockup's tinted pill
  (D-13). See §5.6 for the new tone table; the state/prop contract above is otherwise unaffected.

### 2.2 `ResourceForm` (+ `FormField`, `TextInput`) — the create/edit primitive

`src/components/primitives/ResourceForm.tsx`.

- **States** (`ResourceFormState`): `ready` · `loading` · `denied` (`permission?`) ·
  `error` (`message?`)
- **Props**: `title`, `subtitle?`, `draftStatus?`, `errors?: FieldError[]`, `state?`,
  `submitLabel?`, `pending?`, `onSubmit`, `onCancel?`, `onRetry?`, `children`
- **`FormField`**: render-prop shape (`children: (props) => ReactNode`) so a control cannot be
  rendered without the aria wiring (`id`, `name`, `aria-invalid`, `aria-describedby`) — deliberate
  misuse-resistant API, keep it exactly as-is.
- **Behaviors already correct, do not regress:** error summary at top links to each offending field
  and receives focus after a failed submit (WCAG 2.2 AA / NFR-09); fields validate on blur, not per
  keystroke; cross-field errors surface in the summary; a failed save never shows success and never
  clears entered values.

### 2.3 `DetailLayout` (+ `DetailFacts`) — the record primitive

`src/components/primitives/DetailLayout.tsx`.

- **States** (`DetailLayoutState`): `ready` · `loading` · `denied` (`permission?`) ·
  `error` (`message?`, `onRetry?`)
- **Props**: `breadcrumbs?`, `title`, `identifier?`, `subtitle?`, `badges?`, `actions?`,
  `sections: DetailSection[]`, `mode?: "tabbed" | "stacked"`, `state?`
- **`DetailSection`**: `id`, `label`, `badge?`, `content`, `error?` — a section that fails loads
  fails **alone**; the rest of the record stays readable. Do not regress this.
- **Behaviors already correct:** tabbed mode implements full roving-tabindex keyboard nav
  (arrows/Home/End); tabbed and stacked are the same section config rendered two ways.

### 2.4 `ConfirmModal` — the integrity-action primitive

`src/components/primitives/ConfirmModal.tsx`. Used for every action PRD §7.3 requires a reason for:
manual payment confirmation, refunds, grade overrides, attendance corrections, certificate
revocation, role changes, sensitive exports.

- **Props**: `open`, `eyebrow?` (default "Integrity action"), `title`, `description`,
  `confirmLabel`, `tone?: "danger" | "default"`, `minReasonLength?`, `reasonLabel?` (default
  "Reason"), `pending?`, `error?`, `onConfirm(reason)`, `onCancel`
- **Behaviors already correct, do not regress:** confirm stays disabled until the reason clears
  `minReasonLength`, with a live counter, not a post-hoc error; focus trap while open, returned to
  the trigger on close; ESC cancels but is suppressed while the action is in flight; a failed
  action renders "Action not applied" explicitly — never ambiguous about whether it took effect.

## 3. Spacing, Radius & Depth (supersedes the first pass's "frozen" §3)

**No longer frozen.** The first version treated spacing/radius/shadow as an existing system to leave
alone; D-02/D-18 make the depth model one of the largest structural changes this phase makes, per
the mockup's own `reference` annotation: *"ONE BIG SHADOW... this is the largest departure from
every earlier mockup — shadcn casts 1-3px, your reference casts 48px. Depth is doing the work that
borders did before."*

### 3.1 Spacing

The grid is Tailwind's native 4px scale, constrained here to the standard set — **4, 8, 16, 24, 32,
48, 64px** — with no half-steps and no ranges: every spacing role below resolves to exactly one of
these values, and every per-shell instance in §7 is snapped to one of them too. The mockup's own
inline styles frequently land a few px off this grid (`gap: 9px`, `padding: 11px 14px`, header bar
`52px`, staff content padding `26px 24px 34px`, and similar) — this is a design tool's own export
rounding, not a second grid to honor, so it is not treated as an exception anywhere in this document.
Each specific mapping is called out inline at the point it's used (§7.1–§7.3) rather than asserted as
a blanket exemption here.

| Token | Value | Usage |
|---|---|---|
| xs | 4px | Icon-to-label gaps inside pills/badges/chips, tightest inline gaps, label-to-hint gaps |
| sm | 8px | Standard control internal padding (compact controls), row gaps, list-item gaps |
| md | 16px | Cell/control horizontal padding, card body padding, checkbox/input inline gaps |
| lg | 24px | Card padding, section-level gaps, shell page-edge padding (staff, public, account — unified at this one value after snapping, §7.1/§7.3) |
| xl | 32px | Page container padding, staff content-pane bottom padding, auth right-column padding, learner-shell body top padding |
| 2xl | 48px | Shell outer padding (auth left panel, staff header bar height), learner-shell body bottom padding, empty/denied/error panel padding |

### 3.2 Radius

The mockup declares four radius tokens and uses them consistently by role — **override Tailwind v4's
default `--radius-*` theme keys in `globals.css`** so `rounded-sm`/`rounded-md`/`rounded-lg`/`rounded-xl`
resolve to these values project-wide, rather than hand-writing arbitrary values at every call site:

| Token | Value | Usage |
|---|---|---|
| `--radius-sm` | 8px | Small icon tiles/avatars, tiny chips, jump-bar pills |
| `--radius-md` | 11px | **Controls** — buttons, inputs, selects, textareas, dropzones |
| `--radius-lg` | 12px | Small fact/summary cards (public catalogue detail fact grid) |
| `--radius-xl` | 16px | **Cards** — every `.card`-equivalent container: table shells, detail panels, form shells, sidebar-adjacent side cards |
| pill | 9999px | `StatusPill`, badges, avatar circles, toggle track |

Control height: **38px** standard button/input height (D-19's own summary line), **32px** for
compact/secondary buttons (`btn-sm` equivalent — the segmented filter control's row height, table
pagination buttons).

### 3.3 Shadow / depth

Two shadow tokens, applied by **surface density**, not uniformly — this is the mockup's own `honest`
annotation acted on directly: *"shadows stack visually when cards sit close together, and the staff
screens have the densest layouts in the app."* (D-18)

| Token | Value | Where it applies |
|---|---|---|
| `--shadow-xs` (native Tailwind key, redefined to match exactly) | `0 1px 2px rgba(16,24,40,.06)` | **Dense surfaces**: staff list/table containers, staff form field wrappers, filter search boxes, fact-grid cards |
| `--shadow-card` (new custom theme key — do **not** overload Tailwind's native `shadow-sm`, which means something visually different; a 48px shadow under that name would surprise every future call site that just wants "a small shadow") | `0 18px 48px rgba(16,24,40,.10)` | **Sparse surfaces**: public catalogue cards, catalogue detail panels, auth is a split panel (no card), account cards, staff *detail* side-cards (one at a time, not a dense grid), `ConfirmModal`/`PublishDialog` dialog surfaces |
| `--glow` | `rgba(36,87,214,.18)`, used as `0 6px 18px var(--glow)` | Primary buttons only — the blue glow under `.btn-primary` |

**Rule for the executor:** a staff *list* screen (table of many rows) uses `shadow-xs` on its one
table container — never stack a 48px shadow under a dense grid of rows. A staff *detail* screen's
one or two side cards may use `shadow-card` since they're sparse, single cards, not a repeating grid.
When in doubt, prefer `shadow-xs` on any surface that repeats more than ~3 times in a view.

## 4. Typography (supersedes the first pass's "frozen" §4)

**No longer frozen.** D-05/D-06/D-07 change the type stack outright.

### 4.1 Faces

- **Sans/UI**: Plus Jakarta Sans (400/500/600/700/800 weights available via `next/font/google`),
  stacked as `'Plus Jakarta Sans', 'Segoe UI Variable', system-ui, sans-serif` so Windows users get
  the free system face ahead of the loaded fallback (D-05, accepted platform variance).
- **Mono**: IBM Plex Mono (400/500), replacing Geist Mono everywhere, including every tabular figure
  in staff tables and the `Africa/Lagos` / `AFRICA/LAGOS` timezone footers (D-06).

### 4.2 Tracking (global rule, not per-utility)

Apply as a base style in `globals.css`, exactly as the mockup does, rather than a Tailwind utility
on every heading element — this is simpler to keep consistent across ~50 files that already render
`<h1>`/`<h2>`/`<h3>` or heading-styled `<span>`s without one shared component:

```css
h1, h2, h3 { letter-spacing: -0.035em; }
h1 { letter-spacing: -0.045em; }
```

(D-07 — locked from the mockup.)

### 4.3 Type scale

The mockup draws public/marketing screens (hero, catalogue) at genuinely larger display sizes than
the primitive-driven staff/form screens, and those two contexts never share a single screen — so
this phase declares **two independently-bounded scales, each capped at 4 sizes**, rather than one
scale spanning both (which would either crush the hero down to UI-chrome size or bloat every table
cell up to marketing scale). Every role below is a single fixed px value — no ranges anywhere in
this section, including in §7's per-shell prose, which snaps to these same numbers wherever the
mockup's raw markup lands a fraction of a pixel off.

**Primitive / app-UI scale — exactly 4 sizes** (staff list/detail/form, auth, account chrome,
`ConfirmModal`, and — folded in below — public/account paragraph copy):

| Role | Size | Weight | Line height | Usage |
|---|---|---|---|---|
| Section title (`h1`) | 25px | 600 | 1.2 | `ResourceTable`/`ResourceForm`/`DetailLayout` page title, auth `h1`, account `h1` |
| Card/section heading (`h2`) | 16px | 600 | 1.3 | Card header bars ("Your details", "Sessions"), tab labels' active state, sidebar/nav wordmark ("KQ Nexus") |
| Body / control text | 14px | 400 for plain text (table cell text, paragraph/reading copy, hints, timestamps, breadcrumbs, inactive nav) · 600 for anything carrying emphasis (form field labels, button labels, active nav/tab/breadcrumb state) | 1.5 | Form field labels, table cell text, button labels, hints, timestamps, breadcrumbs; also public/account paragraph copy (previously a separate 14.5–16.5px marketing role — folded into this one fixed value, §4.3 note below) |
| Micro / eyebrow | 11px | 600 | 1.2 | Column headers, badges, mono eyebrows (`IBM Plex Mono`), sidebar meta labels ("Admin workspace", role label), secondary inline links |

Two distinctions that used to be carried by font-size now live on other axes, so the 4-size cap
holds: primary vs. secondary text at the same 14px/400 (e.g. a table row's primary label vs. its
muted subtitle) is distinguished by color alone (`--foreground` vs `--muted-foreground`); plain text
vs. label/button/active-state emphasis at that same 14px is distinguished by weight alone (400 vs
600). Neither distinction introduces a fifth font size — this is a deliberate consolidation to stay
inside the cap, not an oversight.

**Marketing/display scale — exactly 4 sizes** (drawn once each, on the handful of front-of-house
screens: landing hero, catalogue index/detail, learner-preview banner):

| Screen element | Size | Weight | Notes |
|---|---|---|---|
| Landing hero `h1` | 42px | 600 | `-0.045em` tracking, 1.08 line-height — the single largest text in the app |
| Catalogue detail `h1` | 33px | 600 | 1.12 line-height |
| Catalogue index `h1` | 28px | 600 | Also reused for the auth split panel's left-column headline (mockup's raw 27px snapped up to this shared value, §7.2 — closer neighbor than the primitive scale's 25px) |
| Preview learner-mode `h2` | 22px | 600 | Lesson title in the learner-preview reading pane |

Public/account body copy is **not** a fifth marketing size — it folds into the primitive scale's
14px body role (above), since it is reading content in the same sense as an account card's body
text, just on a public-facing route.

**Weights: exactly two active this phase** — 400 (`font-normal`) and 600 (`font-semibold`). The
first pass's draft additionally used 500 (`font-medium`) for interactive labels, active states, and
buttons; that weight is retired from active use — every such instance folds into 600 (see the table
above and §7's per-instance notes). 500/700/800 remain loaded via `next/font/google` for the sans
face (available for future phases) but nothing this phase edits may reference them.

### 5.5 The two-tone fill/text-safe rule — unchanged in principle, re-verified against the new hexes

Non-negotiable per ROADMAP criterion 2 regardless of aesthetic: fills go on dots/bars/indicators and
non-text surfaces; text-safe siblings go wherever the color carries words. `--teal-fill` (3.07:1)
and `--warning-fill` (2.35:1) both fail 4.5:1 for text, so **neither is ever painted behind or as a
text label** — text always uses `--teal-text`/`--warning` (the text-safe siblings).

**`--warning-fill`'s standalone 3:1 failure** is mitigated exactly as the first pass proposed, still
valid: WCAG 1.4.11 exempts a graphical object with a visible border or with an adjacent, independent
text label carrying the same information. Under D-13, `StatusPill` no longer needs this exemption at
all — the tinted-pill treatment means the dot sits beside its own text label inside a colored
background, and the *ink* text (not the dot) is what a screen reader/low-vision user relies on, at a
verified 4.5:1+ (§5.4). The exemption is still needed for the two remaining freestanding uses of
`--warning-fill`: the `ArrangeBoard` "3 unsaved changes" indicator (already a tinted pill per the
mockup, so it's covered the same way) and any future bare progress-bar fill — **do not** introduce a
borderless, unlabelled amber swatch anywhere (e.g. a colored legend square with no adjacent text).

### 5.6 `StatusPill` — the new tone table (supersedes "neutral pill, tone-colored dot only")

D-13 retires the previous contract ("do not regress" language in the first pass's §2.1) in favor of
the mockup's tinted pill: each tone now carries **three** colors — a tinted background, a deep-ink
label, and a mid-tone dot as pure visual reinforcement (the label text, not the dot, carries the
meaning — confirmed accessible per §5.4's per-tone contrast rows).

| `tone` prop value | Visual tone | bg | ink (label text) | dot |
|---|---|---|---|---|
| `success` | Green | `#ecfdf3` | `#067647` | `#17b26a` |
| `accent` | Blue | `#eff4ff` | `#1e40af` | `#3b6ef5` |
| `warning` | Amber | `#fffaeb` | `#b45309` | `#f79009` |
| `neutral` | Grey | `#f7f7f7` | `#525252` | `#a3a3a3` |
| `danger` | Red **(discretionary — see below)** | `#fdf3f2` | `#b42318` | `#d92d20` |

**Discretionary note on the `danger` row:** the mockup's own JS defines exactly four tone objects
(`GREEN`/`BLUE`/`AMBER`/`GREY`) and draws no red pill anywhere in the 28 screens — every red usage in

should be claimed** for `StatusPill` itself (D-13's own conclusion, re-verified independently here).
