<objective>
Close the **WR-01** half of **G-RV-03** from `04.1-VERIFICATION.md` (listed as a Warning under
truth 6, "Phase 4 bespoke components are reconciled or explicitly deferred", and as WR-01 in
`04.1-REVIEW.md`): in both `ConfirmModal` and `PublishDialog` the Tab handler queries only
`:not([disabled])` controls and bails out with a bare `return` when that list is empty. During the
pending window every control in both dialogs is `disabled`, so the handler returns without
`preventDefault`, the browser advances focus in document order, and — because neither dialog marks
the background inert — a keyboard user lands on the live page behind the modal. This is precisely
the window in which the design suppresses ESC to stop stray interaction.

Purpose: restore the WCAG 2.2 AA focus containment (NFR-09) these dialogs already claim in their
own comments.
Output: two repaired focus traps and two extended regression suites.

Scope discipline: no new primitive, prop, route, data model or dependency. `AssignmentDrawer`'s and
`StaffShell`'s existing `inert` background treatment is NOT retrofitted here — this plan uses the
container-trap fix, which is deterministic under jsdom and touches no layout.

## Planner Assumptions

- No dependency install, schema change, new permission or new route is required. ASVS level 1;
  `high` is the blocking threshold.
- `PublishDialog`'s dialog container already carries `tabIndex={-1}`; `ConfirmModal`'s does not.
- jsdom does not implement sequential focus navigation, so the regression asserts the two things the
  handler actually controls: `event.defaultPrevented` and `document.activeElement`. This is the same
  technique the existing focus-wrap tests in both files already use.
- `[tabindex]:not([tabindex="-1"])` in the existing selector means a `tabIndex={-1}` container is
  never itself returned by the focusable query, so the empty-list branch stays reachable.
- Estimate factor 1, sample_count 0, confidence low.
- Preserve working-tree changes and do not commit (parent execution policy).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Modal dialog → live page behind it | Keyboard focus must not cross out of an `aria-modal` dialog while an integrity action is in flight |
| Pending window → user intent | The confirmed payload must stay exactly what the user confirmed; a focus repair must not reopen a mutation path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-04.1-G33-01 | Tampering | `ConfirmModal` / `PublishDialog` pending window | high | mitigate | Focus is held on the dialog container while controls are disabled, so a keyboard user cannot reach and operate the live page behind an in-flight integrity action. Asserted by `defaultPrevented` + `activeElement` regressions in both files. |
| T-04.1-G33-02 | Repudiation | Publish payload | high | mitigate | `toggle`'s pending freeze, `canPublish`, `migrateCohortIds` and the `submit` payload are untouched; the existing "immutable pending payload" cases must remain green. |
| T-04.1-G33-03 | Denial of Service | Focus handling | low | accept | The container trap can hold focus on the dialog while pending — that is the intended containment, and ESC remains available the moment `pending` clears. No lock-out beyond the in-flight window. |
| T-04.1-G33-04 | Information Disclosure | Dialog error surfaces | low | mitigate | No error-rendering code is touched; the "Action not applied" / "Not published" blocks and their copy are unchanged. |
</threat_model>
