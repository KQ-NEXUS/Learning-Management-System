## Summary

This phase is a large, mechanical-but-risky visual migration, not new feature work: swap the token
chain in `globals.css`, rebuild three shells (staff sidebar, new auth split panel, shared learner
shell), restyle four primitives and six already-token-compliant bespoke components, add one new
dependency (`lucide-react`), and swap two Google fonts — while a 707-test Vitest suite (all green,
confirmed by running it this session) and `npm run build` must both stay clean throughout, and no
screen may lose any of its five states (loading/empty/denied/error/validation-error). The hard part
is not deciding *what* the new system looks like — `04.1-UI-SPEC.md` has already fully specified
that, was checked by `gsd-ui-checker`, and is APPROVED — the hard part is sequencing roughly 180
`zinc-*` class-name call sites across ~15+ files behind a token chain that must land first, verifying
NFR-09 contrast mechanically rather than by one-time hand computation, and not letting the three
D-25 "opportunistic fixes" (which add small genuine behavior, not just paint) get planned as if they
were pure restyle work.

This session independently re-verified, by reading the actual source files (not just trusting
UI-SPEC.md's claims): the current `globals.css` is an 8-variable flat block (not the "six flat
values" ROADMAP's prose says — see Common Pitfalls); `staff/layout.tsx` exists today as a light,
224/56-width sidebar with zinc borders and two disabled nav placeholders (confirms D-19/D-20's
"largest single structural change" framing); `(auth)/layout.tsx` does **not** exist yet (confirmed:
only `(public)/layout.tsx`, `account/layout.tsx`, `staff/layout.tsx`, and the root `layout.tsx` are
present) and all six `(auth)/*/page.tsx` files independently repeat the exact wrapper string; the
four primitives live at `src/components/primitives/{ResourceTable,ResourceForm,DetailLayout,
ConfirmModal}.tsx` and are re-exported from `index.ts`; the six bespoke components live at
`src/components/catalogue/{RichTextEditor,ArrangeBoard,UploadPanel,PublishDialog,ReadinessPanel,
LessonContent}.tsx`; `StatusPill`'s current implementation is exactly the "neutral pill, zinc-300
border, zinc-700 label, colored dot" contract UI-SPEC §5.6 describes as being retired; and the full
707-test suite (55 files, Vitest 4 + Testcontainers Postgres) passes cleanly on the current
(pre-migration) code, giving the planner a verified green baseline to diff against.

**Primary recommendation:** Sequence strictly behind UI-SPEC.md §9's row 1 (token chain + fonts),
then parallelize the four independent branches (primitives, staff shell, auth shell, learner shell)
it already identifies; add a Vitest-based mechanical contrast check and the four missing primitive
state-render test files as Wave 0 work before touching any visual code, since neither exists in the
repo today; treat the three D-25 items as their own small tracked tasks, not folded silently into
"restyle" tasks; and gate the `lucide-react` install behind a `checkpoint:human-verify` per the
Package Legitimacy Audit's SUS verdict below (a false positive from a "too-new published version"
heuristic, but the protocol's mechanical gate applies regardless).

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Design tokens (color/radius/shadow/type) | Browser / Client (CSS) | — | `globals.css` + Tailwind v4 `@theme inline` compile to CSS custom properties; no server involvement |
| Font loading | Frontend Server (SSR) | Browser / Client | `next/font/google` self-hosts and injects `<link>`/CSS at build+render time in `layout.tsx`; the browser paints with the resulting `font-family` |
| Staff/auth/learner shell layout | Frontend Server (SSR) | Browser / Client | `staff/layout.tsx`, new `(auth)/layout.tsx`, `(public)/layout.tsx` + `account/layout.tsx` are React Server Components performing auth-guard redirects server-side, then rendering static shell markup the client hydrates for interactivity (nav, sidebar collapse) |
| Four primitives' visual treatment | Browser / Client | — | Pure presentational restyle of existing client/server components; no data-layer change |
| Icon rendering (`lucide-react`) | Browser / Client | — | Tree-shaken SVG React components, rendered wherever imported; no server logic |
| Contrast/accessibility verification | Browser / Client (rendered DOM) | CI / Test tooling | Computed against rendered CSS custom-property values; best verified in a Vitest/jsdom unit test, not a server-side check |
| State machines (loading/empty/denied/error/validation-error) | API / Backend (data) + Browser / Client (render) | — | **Unchanged by this phase** — `ResourceTable`/`ResourceForm`/`DetailLayout`/`ConfirmModal`'s discriminated-union state props are untouched; only which CSS classes render each state changes |

**Why this matters for planning:** every capability in this phase's true scope lives in the Browser/
Client or Frontend-Server (SSR) tiers — there is no API/Backend or Database tier work at all (no new
routes, no new server actions, no schema change). A task that proposes touching `src/server/**` for
this phase is out of scope by construction and should be flagged.

### Pattern 1: Three-tier token chain with a component tier for pill tones and the staff sidebar

**What:** `globals.css` declares `--primitive-*` (raw hex, never referenced by components),
`--{background,foreground,accent,teal-fill,...}` (semantic names Tailwind utilities bind to), plus
two isolated sub-tiers (`--pill-*` for `StatusPill`'s five tones, `--sidebar-*` for the staff shell
only) that are never referenced outside their one consumer.
**When to use:** Any time a component needs a value that is a *composition* of the semantic tier
(e.g., a pill's three-color triple) rather than a single role — keeps the semantic tier's role names
from ballooning while still letting `StatusPill`/`staff/layout.tsx` read named variables, never hex.
**Example (already paste-ready in `04.1-UI-SPEC.md` §5.3):**
```css
/* Component tier — isolated to StatusPill, never read elsewhere */
--pill-amber-bg: #fffaeb; --pill-amber-ink: #b45309; --pill-amber-dot: #f79009;
```

### Pattern 2: Restyle without touching component contracts

**What:** Every one of the four primitives and six bespoke components keeps its exact TypeScript
props/state union; only class-name strings and a small number of new class names (`bg-surface-2`,
`text-muted-foreground`, `bg-pill-*`) are edited.
**When to use:** The whole of this phase, except the three D-25 additions (new Tiptap placeholder
extension, broken-media `onError` fallback, catalogue empty-state copy) which are small, named,
genuinely-new-behavior exceptions — call these out as distinct tasks, don't fold them into "restyle
ResourceTable.tsx"-shaped tasks.
**Example — verified current `StatusPill` implementation, read from source this session:**
```tsx
// Source: src/components/primitives/ResourceTable.tsx, lines 630-649 (current, pre-migration)
export function StatusPill({
  label,
  tone = "neutral",
}: {
  label: string;
  tone?: "neutral" | "success" | "warning" | "danger" | "accent";
}) {
  const dot = {
    neutral: "bg-zinc-400",
    success: "bg-success",
    warning: "bg-warning",
    danger: "bg-danger",
    accent: "bg-accent",
  }[tone];

  return (
    <span className="inline-flex items-center gap-1.5 border border-zinc-300 px-1.5 py-0.5 text-[11px] whitespace-nowrap text-zinc-700">
      <span aria-hidden className={`size-1.5 rounded-full ${dot}`} />
      {label}
    </span>
  );
}
```
This confirms UI-SPEC.md §5.6/§2.1's claim in code: the prop signature (`label`, `tone` union of
exactly the same five values) does not change under D-13 — only the returned JSX's classes do (tint
background + ink text + dot, replacing the flat white/zinc-300/zinc-700 treatment).

### Anti-Patterns to Avoid

- **Reintroducing a raw hex anywhere outside `globals.css`:** the `grep -rniE "#[0-9a-f]{6}"` sweep
  (verified clean this session — matches only in `globals.css`) is the mechanical proof of ROADMAP
  criterion 1; re-run it as a gate at the end of each wave, not just once at the end of the phase.
- **Treating the D-25 items as free because they live in files already being restyled:** UI-SPEC's
  own Appendix flags this explicitly — size them as their own small tasks.
- **A dark-mode variant "for completeness":** explicitly out of scope (Claude's Discretion, resolved
  "no" in UI-SPEC §8.16 item 3). Do not add speculative dark-mode tokens.
- **Reaching for a `weight`-less `IBM_Plex_Mono({ variable: ... })` call:** IBM Plex Mono has no
  `"variable"` entry in Next.js's font-data table — see Common Pitfalls. This will throw a build
  error, not silently degrade.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Icon rendering | Hand-drawn inline SVGs for every glyph (search, plus, grip, upload, check, alert, etc.) | `lucide-react` (D-24, already locked) | Per-icon tree-shaking, consistent stroke geometry matching the mockup, React 19-compatible, 97.8M weekly downloads of production use |
| Font self-hosting | Manually downloading and serving `.woff2` files for Plus Jakarta Sans / IBM Plex Mono | `next/font/google` (already wired for Geist; same mechanism) | Automatic self-hosting, no external request at runtime, already the project's established pattern |
| WCAG contrast ratio math | A bespoke color library or manual spreadsheet re-verification each time a token changes | A ~15-line relative-luminance helper function, unit-tested against the exact pairs in UI-SPEC §5.4 (see Code Examples) | The WCAG formula is fixed and small; a dependency is unwarranted for one formula, but *some* mechanical check is needed since none exists in the repo today |
| Focus-visible styling | A custom focus-ring component/hook | The existing `:focus-visible { outline: 2px solid var(--accent); outline-offset: 3px; }` global rule (already in UI-SPEC §5.3, unchanged mechanism from today's `globals.css`) | Already correct, already global, already NFR-09-compliant; only the offset value (2px→3px) and outline color's resolved hex change |
| Segmented filter control | A new bespoke listbox/tab widget from scratch | Restyle of the existing `TableFilter` rendering inside `ResourceTable` (UI-SPEC §8.16 item 1) — the URL-driven filter/sort contract is unchanged, only the visual affordance | Avoids introducing a second filtering mechanism; the state machine that already reads/writes the URL and preserves stale rows on a validation error must survive unchanged |

**Key insight:** almost nothing in this phase should be "built" in the conventional sense — it is a
restyle of existing, working, well-tested components. The one place genuine new code is warranted
(D-25's three fixes, the mechanical contrast check, and the four new primitive state-render test
files) should be visibly smaller and separately reviewable from the restyle tasks around it.

## Common Pitfalls

### Pitfall 1: IBM Plex Mono is not a variable Google Font — a weight-less `next/font/google` call will fail

**What goes wrong:** Calling `IBM_Plex_Mono({ variable: "--font-ibm-plex-mono", subsets: ["latin"] })`
with no `weight` — the same shape the codebase's current `Geist_Mono` call uses — will error at build
time, because IBM Plex Mono has no variable-font axis registered in Next.js's font-data table.
**Why it happens:** [VERIFIED: `node_modules/next/dist/compiled/@next/font/dist/google/font-data.json`,
read this session] Plus Jakarta Sans's weight list is
`["200","300","400","500","600","700","800","variable"]` — it **does** support the weight-less,
variable-font call form. IBM Plex Mono's weight list is `["100","200","300","400","500","600","700"]`
— **no `"variable"` entry** — so it is a static-weight-only Google Font and `next/font/google`
requires an explicit `weight` array for any such font.
**How to avoid:** Call it as `IBM_Plex_Mono({ variable: "--font-ibm-plex-mono", subsets: ["latin"],
weight: ["400", "500"] })` per D-06's two active weights (400 for body/mono text, 500 for any
emphasized tabular figure — confirm against §4.3's "two active weights" ruling before picking which).
Plus Jakarta Sans can keep the weight-less variable-font call form exactly like today's `Geist` call.
**Warning signs:** A build error naming "weight" as a required property for `IBM_Plex_Mono`, or (if
the array is supplied but too narrow) a silently-missing weight rendering as browser-default 400
everywhere `font-medium`/`font-semibold` was expected.

### Pitfall 2: No mechanical contrast check exists — NFR-09 currently rests entirely on one hand-computed table

**What goes wrong:** UI-SPEC §5.4's 20-row contrast table is correct today (independently recomputed
by `gsd-ui-checker` per §12), but nothing re-runs that computation in CI. If a future edit nudges a
token value (e.g., someone "fixes" a color slightly during implementation), nothing fails until a
human notices — exactly the kind of drift NFR-09 is supposed to prevent.
**Why it happens:** [VERIFIED: `npm ls axe-core jest-axe @axe-core/react vitest-axe`, this session]
`axe-core` is present only as a transitive dependency of `eslint-plugin-jsx-a11y` (lint-time DOM
pattern checks), not wired into any test file; there is no runtime/render-time accessibility
assertion library installed anywhere in the repo.
**How to avoid:** Add one small Vitest unit test (no new dependency needed) that hard-codes the
token hex pairs from `globals.css`'s new `:root` block and asserts each meets its WCAG threshold via
a small relative-luminance helper (see Code Examples). This is not a substitute for the manual
28-screen walkthrough (D-26) — it only guards the *token values themselves*, not their application
to every screen.
**Warning signs:** A visually-plausible color change that passes code review but silently drops a
pair below 4.5:1/3:1 — the exact failure mode NFR-09 exists to prevent.

### Pitfall 3: ~180 `zinc-*` call sites is a large enough surface that a partial migration is easy to miss

**What goes wrong:** [VERIFIED: `grep -c "zinc-" src/components/primitives/*.tsx` → 99 matches;
`grep -c "zinc-" src/components/catalogue/*.tsx` → 77 matches; this session] plus at least 10 staff
route/component files identified by name-grep also reference `zinc-*` (`AuditTable.tsx`,
`CoursesTable.tsx`, `ProgrammeForm.tsx`, `EffectiveAccessPreview.tsx`, `PermissionPicker.tsx`,
`RoleDetailPanels.tsx`, `RoleForm.tsx`, `AssignmentDrawer.tsx`, `AssignmentsPanel.tsx`,
`StaffAccountForm.tsx`). A manual find-and-replace across this many call sites, done piecemeal
across several plan tasks, risks leaving stray `zinc-*` classes that read as "close enough" visually
(zinc and the new cool-neutral ramp are both grey) but violate D-14's "full swap" requirement and
reintroduce exactly the "two neutral families coexisting" problem Phase 3 already flagged.
**Why it happens:** No automated lint rule enforces "no `zinc-*` utility classes" today — confirmed
by inspecting `eslint.config.mjs`, which has no such `no-restricted-syntax`/pattern rule.
**How to avoid:** Treat `grep -rn "zinc-" src/` returning zero matches as an explicit, scripted
end-of-phase gate (alongside the existing raw-hex grep), not just a visual spot-check. Consider a
single project-wide search-and-replace pass per neutral role (e.g., all `text-zinc-400` → 
`text-muted-foreground` in one commit) rather than fixing it file-by-file inside each shell/primitive
task, so the invariant is easy to verify in one diff.
**Warning signs:** `grep -rn "zinc-" src/` returning any match after the phase is claimed complete.

### Pitfall 4: The full test suite takes ~6 minutes and needs Docker — budget for it, don't skip it

**What goes wrong:** Assuming the 707-test suite is fast enough to run after every small edit, or
conversely, skipping it locally because "it's just a restyle" and only relying on `npm run build`.
**Why it happens:** [VERIFIED this session by running `npm test` to completion] The full suite
(`node` project + `components` project) takes **350.81s (~5.8 min)** end-to-end, including Prisma
migrations against a Testcontainers-managed Postgres instance (confirmed Docker is available and

changes. Both runs were **707/707 and 59/59 passing respectively on the pre-migration codebase** —
this is the verified green baseline this phase must not regress.
**How to avoid:** Use `npx vitest run --project components --no-file-parallelism` as the fast
per-task loop (visual/state changes live entirely in this project); reserve the full `npm test` for
wave-boundary and final-gate checks, per the Validation Architecture sampling rate below.
**Warning signs:** A plan that budgets sub-minute iteration loops against the full suite, or one that
never runs the full suite at all before claiming the phase done.

### Pitfall 5: `staff/layout.tsx` and `(auth)`/`(public)`/`account` layouts currently branch on auth state server-side — the rebuild must preserve the redirect logic, not just the markup

**What goes wrong:** [VERIFIED: `src/app/staff/layout.tsx`, read this session] The current staff
shell is an `async` Server Component that calls `getCurrentActor()` and does two `redirect()` calls
(`/signin` if no actor, `LEARNER_LANDING_PATH` if not staff) *before* rendering the sidebar — this is
documented in the file's own comment as "defence in depth," not the security boundary itself (the
server action's own check is), but it is still load-bearing for correct UX. A rebuild focused purely
on the visual sidebar structure could accidentally drop or reorder this guard.
**Why it happens:** The visual rebuild (228px navy sidebar, D-19) is large enough that it's tempting
to rewrite the whole file rather than edit around the existing guard clause.
**How to avoid:** Preserve the exact two-`redirect()` sequence and the comment's stated rationale;
only the JSX returned after the guard clause should change. The same applies to
`account/layout.tsx`'s single `getCurrentActor()` guard (no `isStaff` check needed there, confirmed
in the current file) and `(public)/layout.tsx`, which today has **no** auth guard at all (it is
intentionally public) — the new shared learner shell must keep that asymmetry: `(public)/layout.tsx`
stays guard-free, `account/layout.tsx` keeps its one guard, even though both now render the same
visual chrome via a shared shell definition (UI-SPEC §7.3 already notes this: "not a single new
layout file, since the two route groups have different guards").
**Warning signs:** A signed-out user reaching `/account` without a redirect, or a Learner momentarily
seeing the staff sidebar shell before the redirect fires.

### Mechanical contrast check (no new dependency — recommended addition for NFR-09)

```ts
// Suggested location: tests/unit/contrast.test.ts (new file, "node" project — no DOM needed)
import { describe, expect, it } from "vitest";

/** WCAG 2.x relative luminance + contrast ratio — the same formula UI-SPEC §5.4 computed by hand. */
function relativeLuminance(hex: string): number {
  const [r, g, b] = [1, 3, 5].map((i) => parseInt(hex.slice(i, i + 2), 16) / 255);
  const linear = (c: number) => (c <= 0.03928 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4);
  const [rl, gl, bl] = [r, g, b].map(linear);
  return 0.2126 * rl + 0.7152 * gl + 0.0722 * bl;
}

function contrastRatio(hexA: string, hexB: string): number {
  const [l1, l2] = [relativeLuminance(hexA), relativeLuminance(hexB)].sort((a, b) => b - a);
  return (l1 + 0.05) / (l2 + 0.05);
}

describe("token contrast — NFR-09", () => {
  // Pairs sourced verbatim from 04.1-UI-SPEC.md §5.4 — keep this list in sync with globals.css.
  const textPairs: [string, string, string][] = [
    ["ink on white", "#101828", "#ffffff"],
    ["ink on paper", "#101828", "#f5f7fb"],
    ["muted on white", "#667085", "#ffffff"],
    ["muted on paper", "#667085", "#f5f7fb"],
    ["teal-text on white", "#0f766e", "#ffffff"],
    ["warning (amber text-safe) on white", "#b45309", "#ffffff"],
    ["success on white", "#15803d", "#ffffff"],
    ["danger on white", "#b42318", "#ffffff"],
  ];

  it.each(textPairs)("%s meets 4.5:1", (_label, fg, bg) => {
    expect(contrastRatio(fg, bg)).toBeGreaterThanOrEqual(4.5);
  });

  const uiEdgePairs: [string, string, string][] = [
    ["input-border on white", "#667085", "#ffffff"],
    ["input-border on paper", "#667085", "#f5f7fb"],
  ];

  it.each(uiEdgePairs)("%s meets 3:1", (_label, fg, bg) => {
    expect(contrastRatio(fg, bg)).toBeGreaterThanOrEqual(3);
  });
});
```
