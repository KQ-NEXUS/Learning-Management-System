Write the six `<behavior>` cases into `tests/resource-service.test.ts` first. Run and watch them fail.

Then extend `ResourceServiceConfig<T>` with three optional fields:
`archiveData?: (id: string) => Record<string, unknown> | Promise<Record<string, unknown>>`,
`restoreData?: (id: string) => Record<string, unknown> | Promise<Record<string, unknown>>`, and
`runInTransaction?: <R>(fn: () => Promise<R>) => Promise<R>`.

The payload builders take the record id and may be async because Module and Lesson cannot produce their
payloads without a query: withdrawing must park the row below every sibling, and restoring must append it
to the end of the live list. A synchronous `() => ({...})` cannot express either.

`runInTransaction` groups the read-before-write, the payload build and the update into one unit of work so
a failed write cannot leave a half-applied audit trail. Be precise about what it does NOT do, because the
distinction matters and the obvious reading is wrong:

**The unique index is the concurrency guarantee, not the transaction.** The injected runner is
`(fn) => prisma.$transaction(fn)` and the payload builder's sibling query is an ordinary read; two
concurrent restores can both observe the same `max(position)` and both compute the same landing slot, and
no isolation level short of SERIALIZABLE would serialise two identical read-compute-write sequences
anyway. What saves this is `@@unique([parent, position])`: the second writer fails on the index. The
outcome is fail-safe — one caller wins, the other is rejected — never two rows sharing a slot.

So the remaining job is to make the loser's experience sane rather than opaque. Catch Prisma's `P2002`
unique-constraint error inside `archive` and `restore`, retry the payload build and update ONCE, and if
the retry also collides, throw a typed `PositionContentionError` carrying a message the UI can show
("someone else changed this list — reload and try again"). Without that, a staff member who happens to
press Restore at the same moment as a colleague sees a raw Prisma error string. Document this in a
comment: the index is the correctness boundary, the retry is the ergonomics.

The factory stays free of any Prisma import — the caller injects the runner and the retry predicate. When
`runInTransaction` is absent the operations behave exactly as they do today, so `course-service.ts` needs
no change.

In `archive`, replace the hard-coded `data: { status: "ARCHIVED" }` with
`data: (await config.archiveData?.(input.id)) ?? { status: "ARCHIVED" }`, and wrap the read-before,
payload build and update in `runInTransaction` when it is supplied. Keep the audit entry shape and the
mandatory `reason` argument exactly as they are.

Add a `restore` operation built the same way as `archive` — `withPermission(permissions.edit, (input) => toScope(input.id))`,
read before, update with `await restoreData(input.id)`, audit with action `${slug}.restored`, mandatory
`reason`, all inside `runInTransaction` when supplied.
Return it from the factory only when `restoreData` is supplied, and type the returned object so the
`restore` key is present only in that case (a conditional/overloaded return type, or two exported
factory entry points — pick one and comment which and why).

Head the new fields with comments citing their reasons: `archiveData` exists because `Module` and
`Lesson` have no `status` column and use `withdrawnAt` (D-17), and Phase 12's `TicketAttachment` will
hit the same wall; `restoreData` exists because D-34 requires a withdrawn item to be recoverable
through the product, and because restoring must NOT return the row to its original position — that slot
is very likely occupied by now and the position indexes are total, so the naive
`{ withdrawnAt: null }` payload is a unique-violation waiting to happen. D-16's requirement that
un-archiving returns a Course to DRAFT rather than PUBLISHED is the same field doing the same job for a
different model.

Note in the comment that the *guards* on archive and restore (a running Cohort blocks it, D-12/D-14) are
NOT the factory's job — they live in the calling service, plan 04-08.

`MAX_ARRANGEMENT_SIZE`, `parkedWithdrawnPosition(minSiblingPosition: number | null): number`,

`assertArrangementSize(count: number): void`.

The header comment must state the convention in full, because three plans depend on it and none of them
is an obvious place to look it up:

> `position` occupies two bands under one TOTAL unique index per parent.
> - **Live band, 0 .. n-1.** Contiguous, no gaps, rewritten wholesale by the reorder.
> - **Reorder parking band, -1 .. -n.** Occupied for the duration of ONE statement inside the reorder
>   transaction (plan 04-05 pass one maps `p` to `-p - 1`). Never observed by another session.
> - **Withdrawn band, at or below -1,000,001.** A withdrawn row keeps a real, unique slot because the
>   index is total and `withdrawnAt` exempts nothing. Parking it far below the reorder band is what stops
>   a withdrawal from colliding with an in-flight reorder of its live siblings.
>
> `MAX_ARRANGEMENT_SIZE` is the wall between the reorder band and the withdrawn band. An arrangement
> larger than it is refused outright rather than allowed to wrap into the withdrawn band silently.

`nextAppendPosition` must clamp at 0 — this is the D-34 "restore appends to the end" rule, and the clamp
is what stops a restore into an otherwise-empty parent from landing at `-1000001`.
