<position_rule>
## Positions are assigned by the server, inside the transaction that inserts the row

VERIFIED against `prisma/schema.prisma`: every `position Int` on `ProgrammeCourse`, `Module`, `Lesson` and
`CohortCourse` has **no `@default`** and carries a **total** `@@unique([parent, position])`. Three
consequences bind every write path in this plan:

1. **An insert that omits `position` throws a Prisma missing-argument error.** So `create` cannot be left
   to pass data straight through — the position must be computed and supplied.
2. **Taking the position from the client is wrong twice over** — it is attacker-controlled, and two clients
   reading the same list produce the same number and one of them hits a unique violation.
3. **Counting rows is also wrong.** `count` is not `max + 1` the moment anything has been withdrawn, and a
   count read outside the insert's transaction is a check-then-act race.

The rule, applied identically in all four places (`addCourseToProgramme`, `createModule`, `createLesson`,
and the factory's `restore` payload builders): inside ONE `prisma.$transaction`, read
`max(position)` among the parent's **live** siblings, pass it to `nextAppendPosition` from
`src/lib/positions.ts`, and insert with the result.

Withdrawal uses `parkedWithdrawnPosition(min(position))` from the same module — and that minimum is taken
across **ALL** siblings, including already-withdrawn ones, so each withdrawal parks one slot deeper than
the last. The two aggregates deliberately scope differently:

| Operation | Aggregate | Over which rows | If you get the scope wrong |
|---|---|---|---|
| create / restore | `max(position)` | LIVE siblings only | Including a parked row makes the append land back inside the withdrawn band |
| withdraw | `min(position)` | ALL siblings, live and withdrawn | Live-only means every withdrawal returns the same slot and the second one collides |

Never expose `position` on any input schema.
</position_rule>

The two qualifiers are different on purpose and the asymmetry is the whole mechanism — read them twice.
`parkedWithdrawnPosition` must see the minimum across ALL siblings including the already-withdrawn ones,
because that is what makes each withdrawal park one slot DEEPER than the last. Compute that minimum over
live rows only and every withdrawal in a Module returns `WITHDRAWN_PARK_BASE - 1`, so the second one
collides on `@@unique([parent, position])` and a staff member sees an opaque failure the first time they
withdraw two lessons. `nextAppendPosition`, by contrast, must see only LIVE siblings — including a parked
row at `-1000002` would make it append at `-1000001`, back inside the withdrawn band.

Both read their sibling aggregate inside the transaction the factory opens, and both import from
`src/lib/positions.ts` — do not re-derive the band constants here.

`{ withdrawnAt: null }` alone is NOT an acceptable restore payload. The position indexes are total, the
old slot is very likely occupied by the time anyone presses Restore, and the result is a unique violation
surfacing to a staff user as an opaque failure. D-34 says restore appends to the end; appending is also
what makes it safe.
