<verified_facts>
Facts verified against this repository's source. They are the reason this plan exists in this shape.

1. `prisma/migrations/20260901115332_init/migration.sql` lines 827, 839 and 845 emit position uniqueness
   as `CREATE UNIQUE INDEX "ProgrammeCourse_programmeId_position_key"`,
   `"Module_courseId_position_key"` and `"Lesson_moduleId_position_key"`.
2. PostgreSQL's `SET CONSTRAINTS ... DEFERRED` affects deferrable CONSTRAINTS. A unique INDEX created by
   `CREATE UNIQUE INDEX` is not a constraint, cannot be deferred, and `SET CONSTRAINTS` neither errors
   nor warns when handed such a name.
3. A single `UPDATE ... SET position = position + 1` can violate a non-deferrable unique index
   mid-statement, because PostgreSQL evaluates it per row as the statement progresses.
4. Read-then-compare optimistic concurrency is itself a race. The check must be one atomic conditional
   statement.
5. The position indexes are **total, not partial** — `withdrawnAt` does not exempt a row from
   `@@unique([parent, position])`. A withdrawn row therefore still occupies a real slot, and any statement
   that renumbers its siblings must either move it deliberately or exclude it deliberately. There is no
   third option where it quietly does not matter.
</verified_facts>

<band_contract>
Positions live in three disjoint bands, defined once in `src/lib/positions.ts` (plan 04-03). This service
owns the middle band and must respect the other two:

| Band | Range | Owner |
|---|---|---|
| Live | `0 .. n-1` | This service's pass two; the create paths in plan 04-04 |
| Reorder parking | `-1 .. -n` | This service's pass one, for the duration of one statement |
| Withdrawn | `<= -1,000,001` | Plan 04-04's withdraw payload (`parkedWithdrawnPosition`) |

Two rules follow and both are load-bearing:
- **Pass one must filter to live rows only** (`"withdrawnAt" IS NULL`). Negating a withdrawn row parked at
  `-1000001` would move it to `1000000` — into nobody's band, and permanently.
- **The arrangement must be bounded** by `MAX_ARRANGEMENT_SIZE`, or a list of more than a million lessons
  would let the parking band overlap the withdrawn band. Refuse explicitly; never wrap silently.
</band_contract>

Write `tests/reorder.test.ts` first — pure/injected-delegate cases only, no database. Run and watch it fail.

Create `src/server/services/reorder-service.ts` exporting `StaleOrderError`, `ArrangementMismatchError`,
a pure exported `planTwoPass`, and three operations:

`commitModuleOrder({ courseId, expectedUpdatedAt, moduleIds })` — gated
`withPermission("courses.edit", (i) => ({ courseIds: [i.courseId] }))`.

`commitLessonOrder({ courseId, expectedUpdatedAt, arrangement })` where `arrangement` is
`{ moduleId: string; lessonIds: string[] }[]` covering BOTH the source and the destination module of any
cross-module move (D-21) — gated the same way.

`commitProgrammeCourseOrder({ programmeId, expectedUpdatedAt, programmeCourseIds })` — gated
`withPermission("programmes.manage", (i) => ({ programmeId: i.programmeId }))`.

Every one runs inside a single `prisma.$transaction(async (tx) => { ... })` executing, in order:

1. **Claim.** `tx.course.updateMany({ where: { id: courseId, updatedAt: expectedUpdatedAt }, data: { updatedAt: new Date() } })`
   (or `tx.programme.updateMany` for the programme case). If `count === 0`, throw `StaleOrderError`.
   This is the D-23 check and it MUST be this conditional-update form, never a read followed by a
   JavaScript comparison — the latter is itself a race.
2. **Ownership + completeness.** Count the non-withdrawn children that belong to the parent and compare
   against the ids in the payload, both as a count and as a set. Any mismatch throws
   `ArrangementMismatchError`. Never trust the client's arrangement to be complete or in-scope.
3. **Pass one.** `tx.$executeRaw` an
   `UPDATE "<Table>" SET "position" = -"position" - 1 WHERE "<parentKey>" = ANY(${ids}::text[]) AND "withdrawnAt" IS NULL`
   over every affected parent — for `commitLessonOrder` that is every `moduleId` in the arrangement, so a
   cross-module move cannot collide either. The `withdrawnAt IS NULL` filter is NOT optional: a withdrawn
   row parked at `-1000001` would negate to `1000000` and be stranded in the live band forever. Live
   positions are always `>= 0`, so `-position - 1` maps them onto `-1 .. -n`, disjoint from both the live
   band and the withdrawn band. `ProgrammeCourse` has no `withdrawnAt` column, so its statement omits that
   predicate — say so in a comment rather than leaving the difference to be noticed.
4. **Pass two.** Write the final arrangement row by row, setting `moduleId` as well as `position` for the
   lesson case so re-parenting happens in the same transaction.

Before any of that, call `assertArrangementSize` from `src/lib/positions.ts` on the payload length.

Then audit once per commit via `recordAudit` with actions `module.reordered`, `lesson.reordered`,
`programme.reordered`, `before` = the previous ordered id list, `after` = the new one.

Do NOT use `SET CONSTRAINTS` anywhere. Do NOT add a `CHECK (position >= 0)` — it would break pass one.
Do NOT replace the unique indexes with deferrable constraints; that creates permanent Prisma-migrate
drift for no gain over a two-statement alternative. Put all three prohibitions in a header comment with
the migration.sql line numbers from `<verified_facts>` so the next reader does not re-derive them.

Serialising `expectedUpdatedAt` across the wire is a real trap (RESEARCH A8): a `Date` rendered as an
ISO string truncates to milliseconds and can silently never match. Export
`serialiseOrderToken(d: Date): string` and `parseOrderToken(s: string): Date` using
`String(d.getTime())` / `new Date(Number(s))`, and require every call site to use them.

Seed a Course with three Modules and each Module with three Lessons, at contiguous positions 0,1,2.

Write these cases — each one is chosen because it FAILS under a naive implementation and passes under
the two-pass one:

1. **Full reversal of a lesson list within one module.** Every position collides with a currently-held
   position. A per-row update without the parking pass raises
   `duplicate key value violates unique constraint "Lesson_moduleId_position_key"`. Assert it succeeds and
   that reading back yields exactly the requested order.
2. **Rotation by one** (`[a,b,c] -> [c,a,b]`) — the single most common real reorder and a guaranteed collision.
3. **Cross-module move (D-21).** Move the middle lesson of module 1 to position 0 of module 2. Assert
   both modules end contiguous from 0, assert the moved lesson's `moduleId` changed, and assert the total
   lesson count is unchanged.
4. **Module reversal** on `Module_courseId_position_key`.
5. **ProgrammeCourse reversal** on `ProgrammeCourse_programmeId_position_key`.
6. **Stale token.** Capture `course.updatedAt`, perform one successful reorder, then attempt a second
   reorder with the ORIGINAL token. Assert `StaleOrderError` and assert the stored order is the one the
   first commit wrote — the loser must not have partially applied.
7. **Order-token round trip (RESEARCH A8).** Read `course.updatedAt` from the database, pass it through
   `serialiseOrderToken` then `parseOrderToken`, and assert the resulting reorder SUCCEEDS. If Prisma maps
   `DateTime` at microsecond precision and the token loses precision, this test fails and every reorder in
   production would be refused. This assertion is the entire reason the test exists — do not drop it.
8. **Foreign id.** Include a lesson id from a second Course in the arrangement; assert
   `ArrangementMismatchError` and assert nothing in either Course moved.
9. **Partial arrangement.** Omit one lesson; assert `ArrangementMismatchError`.
10. **A live reorder does not touch a withdrawn row.** Withdraw one lesson through
    `lessonService.archive` so it is parked at `<= -1,000,001` (NOT by writing `withdrawnAt` directly —
    the parked position is the point). Reorder the two remaining live lessons into positions 0 and 1.
    Assert: the withdrawn row's `position`, `moduleId` and `withdrawnAt` are all byte-identical to their
    pre-reorder values; the two live rows are contiguous at 0 and 1; and the transaction did not raise.
    Note why the naive form of this test is wrong: asserting "the withdrawn row keeps position 1" while a
    live row is being written to position 1 is unsatisfiable, because the index is total.
11. **Including a withdrawn id in the arrangement is refused.** Assert `ArrangementMismatchError` and that
    nothing moved.
12. **Restore appends without collision.** With live lessons at 0 and 1 and one withdrawn row parked,
    call `lessonService.restore`. Assert the restored row lands at position 2, `withdrawnAt` is null, no
    unique violation was raised, and the other two rows did not move. This is the D-34 behaviour and it is
    the case a `{ withdrawnAt: null }`-only payload fails.
13. **Reorder after restore.** Immediately reorder all three live lessons into reverse order and assert it
    succeeds — proving the restored row rejoined the live band cleanly rather than sitting in a gap.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff client → reorder Server Action | The arrangement array is fully attacker-controllable: ids, membership, completeness. |
| concurrent staff sessions → same Course | Two people arranging the same Course is the ordinary case, not the exotic one. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-16 | Tampering | arrangement payload containing a foreign or omitted id | mitigate | Step 2 ownership+completeness check inside the transaction; typed `ArrangementMismatchError`; integration cases 8 and 9 |
| T-04-17 | Tampering | lost update between concurrent reorders | mitigate | Conditional `updateMany` on `updatedAt` as an atomic claim (never read-then-compare); integration case 6 asserts the loser wrote nothing |
| T-04-18b | Tampering | withdrawn row negated into the live band, or a reorder colliding with a parked row | mitigate | Pass one filters `"withdrawnAt" IS NULL`; `assertArrangementSize` keeps the parking band and the withdrawn band disjoint; integration cases 10-13 exercise reorder, restore and reorder-after-restore against a real index |
| T-04-18 | Denial of Service | half-applied reorder leaving negative positions visible | mitigate | Both passes run inside one `$transaction`, so no other session observes the parking space; the failure mode is a rollback, not corruption |
| T-04-19 | Elevation of Privilege | reordering another Course's content | mitigate | `withPermission("courses.edit", ...)` scoped by the parent id supplied to the operation and re-verified by the ownership check |
</threat_model>
