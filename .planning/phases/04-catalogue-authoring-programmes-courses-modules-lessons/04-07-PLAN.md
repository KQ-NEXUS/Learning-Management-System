<planner_decisions>
**Storage (D-35): Cloudflare R2 in production, MinIO in dev and CI.** "Self-hosted" was a default rather
than a client requirement, and `PROJECT.md`'s deployment constraint has been amended. Both speak the S3
API, so `@aws-sdk/client-s3` and every line below are identical across environments — only `S3_ENDPOINT`,
`forcePathStyle` and the credentials differ. Nothing in this plan may hardcode either backend.

**Download transport (D-36): presign and redirect. This REVERSES research assumption A2.**
A2 chose app-streaming solely because a URL signed for `http://minio:9000` is unresolvable from a browser.
R2 has a real public hostname with TLS, so that objection is gone. Concretely:
`GET /api/lesson-resources/[id]/download` -> `withPermission("courses.view", lessonResourceScope(id))` ->
refuse unless `scanStatus === "CLEAN"` -> `getSignedUrl(..., { expiresIn: downloadTtlFor(lessonType) })` -> `Response.redirect(url, 302)`. (Per-type TTL under D-37 — see below. Never a numeric literal.)

**Presigned lifetime is per content type (D-37): 60 seconds for FILE and IMAGE, 4 hours for VIDEO.**

The Range-request behaviour this design assumes, stated explicitly because the whole decision turns on it:
a `<video>` element follows the 302 ONCE, caches the resolved presigned URL, and issues every subsequent
HTTP Range request directly against that resolved URL — it does NOT re-resolve
`/api/lesson-resources/[id]/download` per range. So the signature's expiry has to outlast the entire
viewing session, not just the first byte. With `UPLOAD_LIMITS` allowing VIDEO up to 2 GB, a 60-second
window guarantees a stall partway through; that is arithmetic, not a risk.

FILE and IMAGE resolve in a single request and keep the tight 60-second window. Four hours outlasts any
single sitting including pauses, while a leaked video link dies the same working day. NFR-06 still holds
either way: the key is unpredictable, the URL is never stored, never public, never permanent.

If a future phase adopts a player that re-resolves the route per range — an HLS/DASH manifest whose
segment URLs are minted on demand would — the VIDEO TTL can drop back to 60 seconds. That is a different
design and must be a deliberate change, not an assumed one.

Three further things follow and none is optional:
- Use `@aws-sdk/s3-request-presigner`. Do NOT hand-roll an HMAC token — A2's five-minute-token workaround
  is dropped, and hand-built request signing is on this phase's own Don't-Hand-Roll list.
- Video bytes never pass through the Next.js process, which is what protects NFR-02 (p75 <=2.5s) and
  NFR-01 (availability). A 2 GB download occupying a Node process is an availability problem, not a
  bandwidth one.
- NFR-06 still holds: 60-second expiry, never a stored URL, unpredictable object key.

**Uploads still go through the app.** That is correct and deliberate: the upload request is where
authorization happens and where the scan job is enqueued. Keep `@aws-sdk/lib-storage` for the multipart
streaming put.
</planner_decisions>

## Why the scan operations are deliberately NOT wrapped in `withPermission`

VERIFIED: `src/server/permissions/index.ts:15` binds `getActor: getCurrentActor`, and
`src/server/auth/current-actor.ts:15` calls `cookies()` from `next/headers`. The scan worker (plan 04-10)
is a standalone `tsx` process — no request, no cookie jar, no Next.js runtime. A `withPermission`-wrapped
`markScanResult` called from there throws on the very first job. Every upload would then sit at PENDING
forever, and the reconciliation cron — which would be wrapped too — could not rescue them either. The
failure would surface at plan 04-10's blocking checkpoint in wave 4, after the Dockerfile, ClamAV and
Compose work is already spent.

**Decision: option (a) — a separate, explicitly unauthorized, worker-only module.** The alternative (a
synthetic system actor holding a GLOBAL grant) means minting an identity that can do anything, in a
process whose whole job is handling attacker-supplied bytes. A narrow, named, two-function surface is the
smaller blast radius.

The controls that make it safe are structural, not conventional:
1. The two functions live in their own file, `src/server/services/scan-system-service.ts`, and are named
   `markScanResultAsSystem` / `findStuckPendingAsSystem` — the suffix is the warning label.
2. Neither takes a caller-supplied filter. `markScanResultAsSystem` takes a resource id and a
   `ScanStatus`; `findStuckPendingAsSystem` takes a minute count. Neither can read or write anything else.
3. They still audit. `AuditEvent.actorId` is nullable and `actorType` defaults to `"USER"`, so these write
   `actorId: null, actorType: "SYSTEM"` — this task adds an optional `actorType` field to
   `BusinessAuditEvent` and threads it through `recordAudit`, which currently never sets it.
4. A test asserts nothing under `src/app/**` imports from `scan-system-service.ts`, so the unauthorized
   path can never be reached from a request. Plan 04-10 adds the mirror-image test: no `worker/` file
   reaches `next/headers`.

   That mirror test must follow the TRANSITIVE closure, not just direct import lines. `worker/handlers/*`
   imports `storage-service.ts` and `queue.ts`; if either ever imports `@/server/permissions`, the worker
   inherits `cookies()` through two hops while a direct-import grep still passes, and the failure appears
   at runtime in production rather than in CI. Neither module has any reason to import permissions today —
   state that in both files' headers, so the constraint is visible exactly where someone would violate it.
  </worker_access>

   request headers — NOT from the body. Validate them with `zod`.
2. Authorize with `withPermission("courses.edit", lessonScope(lessonId))` BEFORE touching `request.body`.

   being told no.

6. `enqueueScan(id)`.
7. Return `NextResponse.json({ id, scanStatus: "PENDING" }, { status: 201 })`.

a message that distinguishes "no such lesson" from "not yours" (the enumeration control CAT-07 requires,

return 422 with the `validateUpload` message.
