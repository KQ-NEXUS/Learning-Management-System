<planner_decisions>
Two open questions the research handed to planning. Both are DECIDED here; implement them as written.

**OQ-1 — Does `Cohort` pin a publication directly, in addition to via `CohortCourse`? YES, both.**
`Cohort` carries `courseId XOR programmeId` (enforced by the CHECK in `001_integrity.sql`), so a
standalone-Course cohort has no guaranteed `CohortCourse` row to hang a pin on. Therefore:
`Cohort.coursePublicationId` (standalone-Course cohorts), `Cohort.programmePublicationId` (Programme
cohorts), and `CohortCourse.coursePublicationId` (per-course pins inside a Programme cohort). One
resolver in Phase 5 answers "the publications for this cohort" for both shapes.

**OQ-2 — Is `scanStatus` promoted to a shared Prisma enum? YES, now.**
`enum ScanStatus { PENDING CLEAN INFECTED ERROR }` applied to `LessonResource` (line 561),
`Submission` (line 895) and `TicketAttachment` (line 1200). One migration now stops Phases 10 and 12
inventing two more vocabularies against a bare `String`.

**Snapshot storage (RESEARCH A1): JSON payload, not normalised snapshot rows.** The frozen tree is
never queried into; "which cohorts are on version N" is answered by the FK index, not by probing JSON.

**`CohortCourse.contentSnapshot` is KEPT but never written.** Removing it churns a migration for no
gain. Add a schema comment pointing at `coursePublicationId` as the live mechanism.
</planner_decisions>
