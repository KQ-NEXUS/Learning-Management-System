<objective>
Finish REG-01: make both offer types show a visitor everything they need to choose — price, dates,
mode, availability, prerequisites and completion expectation — and make the availability signal honest at
its boundaries.

Purpose: plan 06-03's tracer put cohort cards on the Course detail page because that was the one path it
needed. Programme cohorts render the same bare "Starts {date}" list they always did, so half the
catalogue still has no way to enrol. REG-01 also names two fields the tracer did not check off —
prerequisites and completion expectation — and one boundary that decides whether the availability signal
is trustworthy: what a full cohort looks like, and what the second-to-last seat looks like.

The Full case is worth stating precisely because the obvious implementation is wrong. A disabled-looking
button advertises an action that does not exist and invites clicking; UI-SPEC 7.1 renders no button at
all. And a card showing "1 seat left" is a UI snapshot, not a reservation — the authoritative refusal
happens server-side under a row lock when the click actually lands, which is why this plan asserts the
display rule and leaves the guarantee where plan 06-03 already put it.
Output: one cohort-card component used by both offer types, with its boundary states covered by tests.
</objective>

From plan 06-02, the payload both offer pages already receive:
```typescript
export type PublicCohort = {
  id: string; startsAt: Date; endsAt: Date; enrolmentOpensAt: Date; enrolmentClosesAt: Date;
  deliveryMode: "SELF_PACED" | "INSTRUCTOR_LED" | "BLENDED";
  priceMinor: number; currency: string; seatsAvailable: number;
};
export type PublicCourse = { ...; prerequisites: string | null; durationHours: number | null; certificateEnabled: boolean; upcomingCohorts: PublicCohort[] };
export type PublicProgramme = { ...; memberCourseTitles: string[]; upcomingCohorts: PublicCohort[] };
```

Note the asymmetry already in the schema and the service: `PublicCourse` carries `prerequisites` and
`durationHours`; `PublicProgramme` carries neither, and carries `memberCourseTitles` instead. Both carry
`certificateEnabled`. The programme page's completion expectation is therefore its member-course list
plus its certificate flag, not a prerequisites string — do not invent a field the model does not have.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous visitor → offer detail page | No session; the catalogue service's `where` clause is the entire access control |
| rendered availability → the real seat count | A page render is a snapshot; the authoritative count moves under concurrency |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-25 | Tampering | A visitor treating a rendered "1 seats left" as a reservation and the app honouring it, overselling the cohort | high | mitigate | The card is display-only and creates nothing. The authoritative refusal is `takeSeat`'s row-locked capacity check inside plan 06-03's order transaction, which raises `CapacityExceededError` if a concurrent hold took the last seat between render and click. This plan asserts the display rule only and adds no client-side capacity logic. |
| T-06-26 | Information Disclosure | The programme page exposing a cohort that is unpublished, archived, or not publicly listed | high | mitigate | No new query is introduced; the page renders exactly the `upcomingCohorts` payload the untouched `PUBLIC_VISIBILITY_WHERE`-gated service already returns, and plan 06-02's tests cover that gate. |
| T-06-27 | Information Disclosure | Operational occupancy (`seatsTaken`, `capacity`) reaching an anonymous page through the card | medium | mitigate | The card consumes only the derived `seatsAvailable`; plan 06-02 excludes the raw counters from the payload and asserts their absence with an `Object.keys` test, so the field is not available to render even by mistake. |
| T-06-28 | Tampering | Manufactured scarcity or a stale price misleading a visitor into a purchase decision | medium | mitigate | Grep gate rejecting urgency vocabulary in the component; the price and seat count are rendered straight from the server payload with no client-side derivation; the offer pages are `force-dynamic` so nothing is served from a stale prerender. Recorded as a judgment-tier prohibition on this plan. |
