<objective>
Close the phase: turn the invariants that nine plans asserted individually into executable assertions,
walk the whole learner journey once against real Stripe test traffic, and reconcile the record so the
next phase inherits something true.

Purpose: PAY-09 is the requirement most likely to pass every plan and still fail the phase. Each plan
asserted its own slice of "Stripe stays behind the provider boundary", but nothing in the codebase
notices when plan 07's error handler quietly imports a Stripe type or plan 08's receipt page starts
reading a Stripe field. 06-RESEARCH.md's own test map flags PAY-09 as having no automated assertion at
all — it lists it as a code-review checkpoint. That is exactly the kind of guarantee that decays, and it
is cheap to make mechanical.

The end-to-end walkthrough exists for a different reason: no automated test in this phase actually
traverses Stripe's hosted page. Every integration test stubs the session creation and signs its own
webhook body. That is the right trade for a test suite, and it means nothing has yet proven that the
real thing works when a real person clicks a real button and a real Stripe event arrives over the wire.
Phase 13, 8 and 7 all build directly on this settlement path, so the cost of that assumption being wrong
compounds.
Output: three executable invariants, one full journey walked by a human, and a reconciled record.
</objective>
