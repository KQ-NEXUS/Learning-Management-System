# Phase 6 — UI Design Contract

> Visual and interaction contract for Registration, Checkout & Stripe Payments. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This phase is the **first checkout/payment
> surface** in the app — there is no prior checkout UI to extend — but it renders entirely on
> top of the approved Phase 04.1 design system (`src/app/globals.css` token chain, the four
> hand-rolled primitives, `LearnerShell`). **No token, primitive, or shell change is proposed
> here.** Where this document states a value, it is either **inherited** (traced to
> `04.1-UI-SPEC.md`, not re-litigated), **decided** (traced to a `06-CONTEXT.md` D-number), or
> **discretionary** (this document's own resolution of a gap `06-CONTEXT.md` explicitly left to
> Claude's discretion, flagged as such).

## 0. Grounding — Scope

### 0.1 What's new this phase

| Route | Status | New states this phase adds |
|---|---|---|
| `src/app/(public)/courses/[slug]/page.tsx`, `programmes/[slug]/page.tsx` | **Extended** | Cohort card list with price/dates/mode/availability + "Enroll now" CTA (REG-01); currently renders a bare "Starts {date}" line with no CTA and no cohort `id` |
| `/checkout/[orderId]` | **New** | Order-summary/review (D-02, D-08); verification-gate block (D-13); decline/retry inline banner (D-04); hold-expired error panel (D-10) |
| `/checkout/[orderId]/confirming` | **New** | "Confirming payment…" interstitial (D-05) |
| `/orders/[reference]` | **New** | Confirmation/receipt (D-16, D-17); payment-exception ("needs review") sub-state (discretionary, derived from `06-RESEARCH.md` Pitfall 4) |

### 0.2 Explicitly out of this contract

- **Stripe's own hosted Checkout page** (D-01) — Stripe controls its visual design entirely; this
  document has no opinion on it and specifies only the app-owned screens immediately before
  (`/checkout/[orderId]`) and after (`confirming`, `/orders/[reference]`) the redirect.
- **Embedded Stripe Elements, wallet buttons (Apple/Google Pay), PDF receipts, real ticket
  linking** — all explicitly deferred per `06-CONTEXT.md`'s Deferred Ideas; nothing in this
  document should imply their presence.
- **Any change to `globals.css`, the four primitives' contracts, or `LearnerShell`'s chrome** —
  this phase is a pure consumer of the 04.1 system, not a contributor to it.

### 0.3 Discretionary layout choice — fact-card pattern, not `DetailLayout`

`06-CONTEXT.md`'s Claude's Discretion note says "use the 04.1 design system's existing
primitives (e.g. `DetailLayout`)." Read against the actual codebase: `DetailLayout`
(`src/components/primitives/DetailLayout.tsx`) is shaped for **staff** records — breadcrumbs,
tabbed/stacked sections, and a `denied`/`error` state contract keyed to `permission` (an RBAC
concept). The order-summary and confirmation pages are **learner-owned, ownership-authorized**
records (per `06-RESEARCH.md`'s "Don't Hand-Roll" table — no `withPermission`, no permission
string to show in a denied state). The public course-detail page
(`src/app/(public)/courses/[slug]/page.tsx`) already established a lighter, public-facing
pattern for exactly this shape: a `<dl>` fact grid — `rounded-lg border border-border bg-surface
px-4 py-2 shadow-xs`, 11px/600 muted uppercase `<dt>` label, 14px/400 `<dd>` value. **This
document reuses and extends that established pattern**, not `DetailLayout`, for the order-summary
and confirmation cards. Rationale: it is already the precedent for public/learner-facing record
display in this codebase, and importing `DetailLayout`'s staff-shaped denied/error contract here
would either go unused or force an RBAC-flavored error state onto a page that has none.

## 4. Typography

Inherited from `04.1-UI-SPEC.md` §4.3's primitive/app-UI scale — this phase introduces **no new
size or weight**, and stays entirely within the 4-size, 2-weight cap already locked for that
scale.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 14px | 600 | 1.5 |
| Heading | 25px | 600 | 1.2 |
| Display | 16px | 600 | 1.3 |

Notes:
- **Heading (25px/600)** is the page `<h1>` — "Review your order", "You're enrolled", "This seat
  is no longer held". Matches the existing course-detail-page `<h1>` role.
- **Display (16px/600)** here means the card/section-heading role (04.1's "Card/section heading"
  row), used for card titles ("Order summary", "Policies", "Order details") and the confirming
  interstitial's heading — not a marketing display size. This phase draws no marketing-scale
  text; the "Display" slot is filled by the closest existing role rather than left blank.
- The countdown timer's numeric value is **not** a fifth type size — it renders at the Label role
  (14px/600) in `font-mono`, matching the existing `AFRICA/LAGOS` mono-footer treatment. Color
  (not size) carries its urgency escalation (§6).

## 7. Screens & States — Interaction Detail

### 7.1 Cohort selection (extends `courses/[slug]/page.tsx`, `programmes/[slug]/page.tsx`)

Replaces the current bare `<li>Starts {date}</li>` list with a vertical stack of cohort cards,
one per open Cohort, each using the fact-card visual language (§0.3): `rounded-lg border
border-border bg-surface px-4 py-3 shadow-xs`, laid out as a row on ≥640px (date range + mode +
price + availability left, CTA right) collapsing to a stack below 640px (existing responsive
convention, no new breakpoint). Fields per card: date range (start–end), delivery-mode label
(plain text, not a `StatusPill` — mode isn't a status), price (`Intl.NumberFormat(undefined, {
style: "currency", currency: cohort.currency }).format(cohort.priceMinor / 100)`), availability
copy (§6.1), and the "Enroll now" button (accent, 38px height) or the "Full" label when
`seatsAvailable === 0` (no button rendered in that case — a disabled-looking button implies a
retry-able action that doesn't exist here). Existing course-level facts (prerequisites, duration,
completion expectation) are unchanged — they already render above this list and are not
duplicated per-cohort.

**Unauthenticated click on "Enroll now":** no new screen — the Server Action sets the
`checkout_intent` cookie and redirects straight into the existing `(auth)` split-panel shell
(D-14/D-15), which is untouched by this phase.

### 7.2 Order-summary page (`/checkout/[orderId]`)

Renders inside `LearnerShell`, single column, `max-width: 640px` centered within the shell's
1080px container (narrower than the shell default, since this is a focused read-then-act task,
not a browsing page).

- **Order summary card** — fact-card `<dl>` pattern: cohort title, date range, mode, price. The
  **countdown** sits at the top of this card, not buried in a corner — `Clock`-adjacent
  prominence per the "Eventbrite-style" urgency framing in `06-CONTEXT.md`'s Specific Ideas: mono
  14px/600 value, label text at Body weight, color escalates `--foreground` (>5:00) →
  `--warning` (5:00–1:00) → `--danger` (<1:00), still one type size throughout (color carries the
  urgency, not size).
- **Policies card** — three checkboxes in the inherited auth-shell checkbox treatment (16×16px,
  1.5px `--input-border`, 4px radius, native `<input type="checkbox">`), each label carrying an
  inline `--accent`-colored link to the relevant policy document text. Terms and
  Refund-Cancellation are required (Pay stays disabled until both are checked); marketing is
  optional and never blocks Pay.
- **Verification-gate banner** (renders only while the actor is `PENDING_VERIFICATION`, D-13) —
  `--warning-surface` background, `--warning` text, positioned directly above the Pay button; Pay
  is disabled while this banner shows.
- **Decline/retry banner** (renders only after a returned/declined attempt, D-04) — reuses
  `ResourceForm`'s error-banner color language (`--danger-surface` background, `--danger` border
  and heading text) positioned in the same slot as the verification banner (only one of the two
  ever shows at once — they are mutually exclusive preconditions on the same Pay action). The "Try
  again" button re-submits the existing Order/PaymentAttempt (no new Order, per the anti-pattern
  `06-RESEARCH.md` calls out).
- **Pay button** — full-width on mobile, right-aligned at desktop widths, `--accent` background,
  `--accent-contrast` label, 38px height, disabled (reduced opacity + `cursor-not-allowed`, not
  hidden) while unverified or while the countdown has reached zero pending a server re-check.
- **Hold-expired** (D-10) — once the server confirms the hold is gone (not just the client
  countdown reaching zero — the countdown is a UI clock, the server check is authoritative), the
  entire page content is replaced by a single error panel matching `DetailLayout`'s existing error
  visual (`rounded-xl border border-border bg-surface px-6 py-12 shadow-card`, `AlertCircle` icon,
  `--danger` heading) with the copy from §6 and a "Back to cohort" link (`ChevronLeft` + text,
  same treatment as the existing "Back to courses" link) to the cohort's public page.

### 7.3 Confirming interstitial (`/checkout/[orderId]/confirming`)

No card, no countdown (the hold either converted to a paid order or the money already moved —
there's nothing left to hold a clock against). Centered single-column stack, vertically centered
within the `LearnerShell` body: `Loader2` spinner (`animate-spin`, `--accent` color, decorative —
`aria-hidden`, paired with an `aria-live="polite"` sr-only "Confirming your payment" so the state
is announced once, not on every poll tick), heading (Display role, 16px/600), body (Body role,
14px/400, `--muted-foreground`). The reassuring tone from `06-CONTEXT.md`'s Specific Ideas is
carried entirely by copy, not by a fifth type size or a new color — this is a "wait, this is
normal" state, not a warning.

### 7.4 Confirmation / receipt page (`/orders/[reference]`)

Same column width/centering as the order-summary page. Page `<h1>` (Heading role), then a single
"Order details" fact-card carrying: order reference (mono, `<dd>` value), offer/cohort name,
formatted amount, Payment-state `StatusPill`, Enrolment-state `StatusPill`. Beneath the card: the
support-route line (Body role, `--muted-foreground`, one `--accent` mailto link). Primary CTA
below that. This is the receipt — permanent, viewable any time at this URL (D-17), no
print/download affordance drawn anywhere on it.

**Exception sub-state** (discretionary, derived from `06-RESEARCH.md` Pitfall 4 — the seat hold
can legitimately expire in the narrow window between Stripe capturing payment and the webhook
processing it) uses the identical card shape with the copy substitutions in §6.1 and a `warning`-
toned Enrolment-state pill instead of `success`. The Payment-state pill stays `"Paid"`/`success` in
both sub-states — the money did move; only the enrolment side is pending reconciliation. This is
not a failure screen (no `danger` tone, no "something went wrong" framing) — the learner did
nothing wrong and needs no action.
