<objective>
Make a cohort selection survive the identity detour, so a visitor who clicks Enroll while signed out
comes back to that cohort's order summary rather than a generic landing page.

Purpose: REG-02 is the requirement most likely to be quietly half-built, because the easy version — a
`returnTo` query parameter — works for the one case you test by hand and fails for the case that
actually happens. Registration does not create a session; it returns a "check your email" state, and the
verification link is generated at send time and opened later, sometimes from a different tab, sometimes
the next day. A parameter bounced through the register form cannot reach that link, because the link's
URL was already written and mailed. So the intent has to live somewhere the round trip can find it, and
a short-lived httpOnly cookie is the smallest thing that works with no schema cost.

The second reason to treat this as its own plan: a post-auth redirect that accepts a caller-supplied
destination is a textbook open redirect, and this one sits on an authentication boundary. Storing a bare
cohort id and having the app construct the path itself removes that class of bug entirely rather than
trying to validate its way out of it.
Output: the intent cookie, the return-path resolver, the resumption route, and an integration test that
walks register -> verify -> sign in and lands on the right order.
</objective>

`src/server/auth/landing.ts` current shape (16 lines, entirely):
```typescript
export const STAFF_LANDING_PATH = "/staff/courses";
export const LEARNER_LANDING_PATH = "/account";
export function landingPathFor(user: { isStaff?: boolean | null }): string {
  return user.isStaff === true ? STAFF_LANDING_PATH : LEARNER_LANDING_PATH;
}
```

`src/app/(auth)/signin/actions.ts` current tail:
```typescript
const jar = await cookies();
jar.set(SESSION_COOKIE, result.token, {
  httpOnly: true, sameSite: "lax", secure: process.env.NODE_ENV === "production",
  path: "/", maxAge: SESSION_TTL_DAYS * 86_400,
});
redirect(landingPathFor(result));
```

Auth-flow facts confirmed from source, which constrain the mechanism:
- `registerLearner` creates the user with `status: "PENDING_VERIFICATION"` and returns a "check your
  email" state. No session is created (`register/actions.ts`).
- `verifyEmail` sets `status: "ACTIVE"` and `emailVerified` together
  (`verification-service.ts:151`), then the verify page offers a "Continue to sign in" link. It creates
  no session either.
- `signIn` refuses any user whose `status !== "ACTIVE"` (`auth-service.ts:51`), and
  `getActorBySessionToken` returns null for a non-ACTIVE user (`session-service.ts:35`).

Consequence: the round trip is always register -> (email) -> verify -> sign in, and only the final
sign-in produces a session. The cookie is therefore the only carrier that spans it.

From plan 06-03: `startCheckout(actor, cohortId)` and the typed refusals `CapacityExceededError`,
`CohortClosedError`, `CohortNotFoundError`, `AlreadyEnrolledError`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → checkout intent cookie | A value set before authentication is read after it, spanning the identity boundary |
| authentication completion → redirect destination | The classic open-redirect surface, sitting on the one page attackers most want to phish |
| emailed verification link → returning browser | A cross-request, possibly cross-tab, possibly next-day resumption |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
