<objective>
Harden the settlement path against everything Stripe's delivery contract and this codebase's own
concurrency actually produce: the same event delivered twice, an event whose amount does not match the
order, an event arriving after the seat hold was already swept, and an event trying to move a terminal
payment backwards.

Purpose: plan 06-03 proved the happy path and built the idempotency guard into it from the first commit,
because that was a wall. This plan is where the rest of the failure surface gets closed, and every item
on it is a real behaviour of the system rather than a hypothetical. Stripe retries a non-2xx response for
three days and can double-deliver on a 200, so at-least-once is the contract, not the exception. Phase
5's hold-release worker sweeps every five minutes and knows nothing about Stripe, so it will cancel a
`PENDING_PAYMENT` enrolment out from under a learner who is mid-payment on Stripe's page — and when the
webhook then lands, the money has moved and the seat has not. That case cannot be an unhandled exception
and it cannot silently re-take a seat that may now belong to someone else; it has to become a visible,
reconcilable exception, which is exactly the shape PAY-07 asks for one phase early.

The amount cross-check deserves its own mention. It is tempting to trust the event and write
`session.amount_total` onto the order, because the event came from Stripe and passed signature
verification. But a verified event is proof of origin, not proof that it corresponds to the order this
app thinks it does. Cross-checking against the amount recorded at order-creation time turns a whole class
of correlation bug into a flagged exception instead of a silent mispayment.
Output: replay-safe, cross-checked, race-aware settlement, plus a mechanical import-closure guard.
</objective>
