<objective>
Prove the whole phase in one committed slice: a signed-in learner picks an open cohort, reviews a real
order, pays through a real Stripe Checkout Session, and a signature-verified webhook — not the redirect
— turns that into a paid Order and an ACTIVE enrolment shown on a permanent receipt page.

Purpose: this phase's architectural risk is concentrated in one place, and it is not the UI. It is the
question of whether an unauthenticated, actorless, server-to-server webhook can safely settle money and
capacity in a codebase whose every write path resolves an actor from a session cookie. Everything else —
policy consent depth, the auth detour, the countdown, the decline banner, the exception sub-state — is
expansion on a proven spine. If the spine is wrong, discovering it after ten committed layers is the
expensive outcome this slice exists to prevent. So the slice is thin deliberately: one cohort, one happy
path, no edge cases, no error states beyond what the happy path itself must not skip.

This is a tracer, not a prototype. Every line here is production code that stays. The stubs it is
allowed to carry are functional gaps that later plans fill without moving a wall — a summary page that
renders facts but not yet the countdown or the policy checkboxes, a webhook that handles
`checkout.session.completed` but not yet `checkout.session.expired`. It carries no architectural gaps:
signature verification, idempotency, ownership checks, seat accounting and the actorless audit trail
are all real from the first commit, because each of those is a wall.
Output: the checkout service, the webhook settlement service, the Stripe adapter, the webhook route, and
the four screens that carry the path.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <decision>How should the Stripe webhook be authorized to settle an Order and activate an Enrolment?</decision>
  <context>
    Every write path in this codebase resolves its actor through `withPermission`, which calls
    `getCurrentActor()`, which reads a session cookie off the incoming request. A Stripe webhook is an
    unauthenticated server-to-server POST with no cookie jar. `approveEnrolment` — the function that
    already performs exactly the PENDING_PAYMENT -> ACTIVE transition needed here — would resolve
    `actor = null` and fail closed: the learner pays, the enrolment never activates, and nothing
    obviously errors. That is the silent failure this decision exists to avoid.

    Why this is worth stopping for rather than just building: 06-RESEARCH.md rates this its
    MEDIUM-confidence finding (assumption A3) and explicitly asks the planner to confirm the shape
    rather than treat it as settled. It is also the only genuinely new architectural decision in the
    phase — the rest is pattern-following.

    Undo cost: whichever shape is chosen starts writing `AuditEvent` and `DomainEvent` rows the moment
    the first payment settles. This project has a no-hard-deletes constraint, and Phase 8's
    reconciliation views and Phase 13's email drain both read those rows. Changing the actor model
    afterwards leaves a permanent split in the audit history that later readers must special-case.
  </context>
  <options>
    <option id="as-system-module">
      <name>A separate, explicitly unauthorized `checkout-webhook-system-service.ts` (RESEARCH's recommendation)</name>
      <pros>Third instance of a pattern the codebase already uses twice — `hold-release-system-service.ts` (worker) and `scan-system-service.ts` (upload route). The `AsSystem` suffix is the warning label; the module takes no caller-supplied filter it can be steered by; it audits as `actorId: null, actorType: "SYSTEM"` under distinct action names so a webhook settlement is never mistakable for a staff override; `tests/boundary.test.ts` can assert its import closure stays free of `@/server/permissions` and `next/`. Nothing new is invented.</pros>
      <cons>A third module that is unauthorized by design is a third place a future contributor could mistake for "authorization was forgotten here" — mitigated only by the file header, not by the type system.</cons>
    </option>
    <option id="synthetic-actor">
      <name>Mint a synthetic SYSTEM user holding a GLOBAL `enrolments.manage` grant and call `approveEnrolment` normally</name>
      <pros>No new module; the existing permission-gated path is reused verbatim; the audit trail has a real actor id.</pros>
      <cons>Creates a real identity that can perform ANY permission-gated write in the system, usable by anything that can reach the database — the blast radius `hold-release-system-service.ts`'s own header rejected this option for. It also still needs a way to inject that actor past `getCurrentActor()`, which means an actor-override parameter on the choke point: a bypass seam on the one function whose job is to have none.</cons>
    </option>
    <option id="deferred-queue">
      <name>Webhook writes only a `WebhookEvent` row; a pg-boss worker job drains it and performs the settlement</name>
      <pros>Reuses the existing worker runtime, which is already actorless and already covered by the boundary test; the webhook route becomes trivially fast and always returns 200.</pros>
      <cons>Adds latency between payment and activation that D-05's "Confirming payment…" interstitial has to absorb, on top of Stripe's own delivery delay. It does not actually avoid the decision — the worker job still needs an unauthorized settlement function, so option A gets built anyway, just one layer further away and harder to test. Phase 13 is where the outbox drain is scoped to land.</cons>
    </option>
  </options>
  <resume-signal>Select: as-system-module, synthetic-actor, or deferred-queue</resume-signal>
