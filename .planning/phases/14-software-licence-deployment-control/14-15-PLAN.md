<objective>
Add the two-step licence activation flow and the diagnostic report download to the Licence & System Status screen, behind the `licence.activate` and `licence.view` permissions.

Purpose: LIC-03 allows activation only by a restricted permission and forbids any create or extend capability; D-14 adds a non-sensitive diagnostic download; LIC-06 requires the download to be audited. Tracer: an authorized actor inspects and activates a valid file through the server actions and the permission wrapper.

Output: façade additions, server actions, the activation form, the diagnostic route and button, and tests. Plan 14-10's `LicenceStatusView` already exposes `activationSlot` and `diagnosticSlot`; this plan fills them in `page.tsx`.

Interface contract (do not rename): `licenceStaffService.inspectLicenceForStaff({ raw })` and `.activateLicenceForStaff({ raw, correlationId? })` guarded by `licence.activate`; `.getDiagnosticForStaff()` guarded by `licence.view`; `inspectLicenceAction(input: unknown)` and `activateLicenceAction(input: unknown)` returning `{ ok: true, ... } | { ok: false; code: string; message: string; neutral: boolean }`.

Edge coverage: LIC-03 (unclassified, flagged assumption): the probe returned "review manually"; this plan assumes the acceptance outcome "an Administrator can upload and activate a valid issued licence; ordinary Administrators and all other roles cannot forge or alter it" is met by the permission wrapper, the server-side re-verification, the absence of any create or edit surface and the seeded-role note in OQ3.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser upload to server action | Untrusted licence text decides commercial state; the 1 MB framework cap is only a backstop |
| server action to activation service | Authorization must hold at the action boundary, not just the UI |
| diagnostic route to download | Report content leaves the application |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-14-15-01 | Elevation of privilege | activation by a non-holder via direct POST | high | mitigate | Staff service wraps both calls in withPermission("licence.activate"); denial test proves the activation fake is never called; the form is a courtesy |
| T-14-15-02 | Tampering | preview trusted at activation | high | mitigate | activateLicenceAction submits the raw text and the activation transaction re-verifies under row lock; test asserts the action never sends preview data |
| T-14-15-03 | Denial of service | oversized or malformed upload | medium | mitigate | 8192 cap client-side before reading and server-side in the action, ASCII allow-list, framework 1 MB cap as backstop |
| T-14-15-04 | Information disclosure | stack traces or file content in action results | medium | mitigate | Fixed messages from the closed sentence set; unexpected errors log only error.name; no echo of unverified text |
| T-14-15-05 | Information disclosure | diagnostic leaks secrets or is cached | high | mitigate | Allow-listed fields only; Cache-Control private, no-store; licence.view required; denial is an empty 404; audited per download |
| T-14-15-06 | Repudiation | activation or download without evidence | medium | mitigate | licence.activated and licence.activation_rejected from the service (plan 14-07); licence.diagnostic_downloaded written by the staff service with the actor |
| T-14-15-07 | Elevation of privilege | seeded Administrator holds licence.activate (OQ3) | medium | accept | Adopted default for recovery safety; documented deviation from PRD 18.4; narrower custom role can be created before launch |
</threat_model>
