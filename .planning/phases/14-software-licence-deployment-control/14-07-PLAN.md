Build the closure-safe licence service (status snapshot, deployment identity, activation assessment) and the activation transaction, proven on a real Postgres.

Purpose: LIC-01 and LIC-03 need a verified, atomic activation and a database-backed status that every instance shares (D-13). Tracer: one valid licence activates and the status snapshot reads back ACTIVE with an audit row. Expansion tasks add every rejection rule and the concurrency proof.

Interface contract for later plans (do not rename):
- `createLicenceService(deps: { db; trustSet?: () => TrustSet; audit: (e: BusinessAuditEvent) => Promise<void>; now?: () => Date })` returns `{ ensureDeploymentIdentity(): Promise<string>; getStatusSnapshot(): Promise<LicenceStatusSnapshot>; inspect(raw: string): Promise<InspectResult> }`; plan 14-09 adds `evaluateAndRecord`, `checkWriteGate`, `assertWriteAllowed`, `getRestrictionCutoff`, `buildDiagnosticReport` to the same object.

- `activateLicence({ actorId: string; raw: string; correlationId?: string }): Promise<{ ok: true; snapshot: LicenceStatusSnapshot } | { ok: false; code: LicenceRejectionCode | "CONCURRENT_CHANGE" }>`.
- `db` is a structural subset of PrismaClient (licenceState, licenceRecord, deploymentIdentity, $transaction, $queryRaw, $executeRaw); integration tests pass `testDb.prisma`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| uploaded licence text to activation | Untrusted bytes decide commercial state |
| database rows to derived state | Stored raw text and dates could be edited outside the application |
| concurrent requests to singleton state | Races could double-activate or lose updates |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-14-07-01 | Spoofing | forged or altered licence activated | high | mitigate | verifyLicence in activate mode inside the locked transaction; rejection leaves no row; tests for BAD_SIGNATURE, UNKNOWN_KEY, KEY_REVOKED |
| T-14-07-02 | Tampering | replay or downgrade of an older valid licence | high | mitigate | issuedAt must be strictly newer than the newest record; same licenceId returns ALREADY_ACTIVE; tests for older, equal and duplicate |
| T-14-07-03 | Tampering | edited raw text or dates in the database | medium | mitigate | stored raw text is re-verified on every read; derived dates come from the verified payload; tamper test; accepted residual: SQL access can reset the singleton (PRD 18.1) |
| T-14-07-04 | Tampering | partial or lost update under concurrency | high | mitigate | FOR UPDATE on the singleton, version-guarded UPDATE, single transaction for record, state and audit; parallel tests |
| T-14-07-05 | Information disclosure | raw licence, signature or key in audit or snapshot | medium | mitigate | audit rows carry ids, codes and ISO dates only; snapshot has no raw field; tests assert absence |
| T-14-07-06 | Elevation of privilege | activation callable without permission | high | mitigate | no authorization here by design; the only caller is the permission-wrapped staff service (plan 14-15) and plan 14-17 adds an importer guard test; tracked as a key link |
| T-14-07-07 | Denial of service | cross-client licence pins the wrong client | medium | mitigate | first activation pins client.id (A5); later mismatches are WRONG_CLIENT; pinned by test |
</threat_model>
