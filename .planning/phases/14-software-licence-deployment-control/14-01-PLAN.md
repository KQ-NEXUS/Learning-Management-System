  <decision>Confirm the exact licence file contract that will be published to every client: envelope, signed bytes, header members, payload members, validation rules and key-ID scheme.</decision>
  <context>
    D-02 is locked at the level of Ed25519 via Node crypto, a signing-key ID, a versioned public-key trust set and an explicit schema-version field. The concrete encoding and payload member names were left to planner discretion and are proposed below. Once a licence is issued this contract cannot change without re-issuing every licence, so the owner confirms it first.

    Proposed contract (schema version 1):
    - Envelope: one ASCII line `LMS-LIC1.{header}.{payload}.{signature}`, each of the three parts base64url without padding. Maximum 8192 characters, allowed characters `A-Za-z0-9._-` only.
    - Signed bytes: the exact ASCII string `LMS-LIC1.{header}.{payload}` (everything before the last dot). The verifier checks the signature over those bytes before parsing any JSON. No canonicalisation step exists.
    - Header JSON members: `alg` (pinned to exactly `Ed25519`), `kid` (signing-key ID, 1 to 64 characters `A-Za-z0-9._-`, example `kqn-2026-a`), `typ` (`lms-licence`), `v` (1).
    - Payload JSON members, all signed: `schemaVersion` (1), `licenceId` (unique per issued file, per RESEARCH Open Question 2), `issuedAt`, `notBefore`, `expiresAt`, `graceEndsAt` (ISO-8601 UTC instants ending in Z), `client` with `id` and `name`, `deploymentId`, `timeZone` (IANA name, display only), `support` with `renewalEmail`, `supportEmail` and optional `phone` and `hours`.
    - Date rules: `notBefore` at or before `expiresAt`, `expiresAt` at or before `graceEndsAt`, `issuedAt` at or before `expiresAt`. Grace is a generator input (default 14 days of 24 hours in UTC), never computed by the LMS (D-10, D-11).
    - Tolerant reader: unknown optional payload members are ignored by older verifiers; a new required member needs `schemaVersion` 2 and a new envelope prefix. An unrecognised `LMS-LIC{n}` prefix is reported as an unsupported schema, not as a bad format.
    - Key-ID scheme: the LMS ships a versioned trust set of public keys with status `active` (signs and verifies), `retired` (verifies only) or `revoked` (rejected). Development keys are trusted only when NODE_ENV is not production.
    - Binding: the first activation pins `client.id` (trust on first activation, assumption A5); `deploymentId` must equal the value seeded in the database at install (D-13). Activation rejects a licence whose `issuedAt` is not newer than the newest recorded one unless it is the same `licenceId` (anti-replay, assumption A7).
  </context>
