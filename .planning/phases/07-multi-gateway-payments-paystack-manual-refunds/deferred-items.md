## 07-05 (dual-price Cohort administration and per-rail readiness)

- **`tests/cohort-lifecycle-security.integration.test.ts` — "cannot overwrite
  CANCELLED/COMPLETED after a stale readiness read, even with an unchanged
  version" (2 cases) fails against real Postgres, asserting the wrong error
  type — a pre-existing bug, not caused by this plan.** The test drives
  `publishCohort` on a cohort that a concurrent raw-SQL write moves to
  CANCELLED/COMPLETED while the publish transaction is paused mid-flight,
  then asserts the caught error `toBeInstanceOf(StaleOrderError)`. Traced the
  actual code path in `cohort-service.ts`'s `publishCohort`: inside the
  transaction, the freshly re-read row's status is checked by
  `assertCohortOpen(input.cohortId, freshRow.status)` (line ~732)
  *unconditionally, before any readiness re-evaluation and before the
  conditional `updateMany` that would throw `StaleOrderError`* — so a
  CANCELLED/COMPLETED freshRow always throws `CohortClosedError` here, never
  `StaleOrderError`. This `assertCohortOpen` call and its position relative
  to the transaction's other checks are byte-for-byte unchanged by this
  plan (confirmed via `git diff HEAD -- src/server/services/cohort-service.ts`
  — only variable names/threading for the new `enabledRails` parameter
  changed around it); the same CANCELLED/COMPLETED race would have produced
  the identical `CohortClosedError` on `HEAD`, before any Phase 7 plan ran.
  This plan's own `enabledRails: () => ({ ngn: false, usd: false })` fix to
  this file's `buildCohortService` binding (see key-decisions) was necessary
  to stop the test from HANGING (a fresh fixture cohort's `priceNgnMinor: 0`
  legacy default is not a positive price, so with both rails enabled the
  pre-transaction readiness refusal fired before the transaction — and
  therefore before the test's paused-transaction gate — ever opened,
  timing out at Vitest's default 5000ms). With that hang cleared, the test
  now reaches its own pre-existing, unrelated assertion mismatch. Not fixed
  here — this is a test-assertion bug (or an open question about whether
  `assertCohortOpen`'s fresh-read check should defer to the CR-02
  readiness re-evaluation) entirely outside this plan's own dual-price
  scope (SCOPE BOUNDARY rule). A future plan touching `publishCohort`'s
  CR-02 transaction body should correct the test's expected error type (or
  the code's check order, if the intent really was "stale version" rather
  than "cohort closed").
