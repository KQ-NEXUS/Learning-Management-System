# Phase 7 — UI Design Contract

> Visual and interaction contract for Multi-Gateway Payments — Paystack, Manual & Refunds.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker. This phase **extends** three
> screen families Phase 6 already built (offer/cohort-card selection, order-summary, receipt)
> from a single Cohort price to an administrator-entered dual-currency price with a learner-paid
> fee breakdown, and **adds** one new staff surface (Finance payments list + detail). It renders
> entirely on top of the approved Phase 04.1 design system (`src/app/globals.css` token chain,
> the four hand-rolled primitives, `LearnerShell`/`StaffShell`) and Phase 6's fact-card precedent.
> **No token, primitive, or shell change is proposed here.** Where this document states a value,
> it is either **inherited** (traced to `04.1-UI-SPEC.md` or `06-UI-SPEC.md`, not re-litigated),
> **decided** (traced to a `07-CONTEXT.md` D-number), or **discretionary** (this document's own
> resolution of a gap `07-CONTEXT.md` explicitly left to Claude's discretion, flagged as such).

### 0.2 Explicitly out of this contract

- **Paystack's and Stripe's own hosted checkout pages** — unchanged from Phase 6's D-01 ruling;
  this document has no opinion on either provider's own UI.
- **CSV export UI, reconciliation/finance dashboards** — Phase 8 (RPT-01 onward), not this phase.
- **The scheduled reconciliation function's internals** — an off-request background job with no
  UI of its own (`07-RESEARCH.md`'s Task 7 drift resolution); this document only specifies how
  its *output* (actual-vs-expected settlement values) renders once written.
- **Any change to `globals.css`, the four primitives' contracts, `LearnerShell`, or `StaffShell`'s
  chrome** — this phase is a pure consumer of the 04.1/06 system, not a contributor to it.
- **Gateway credential/school-account-identifier editing UI** — explicitly deferred per
  `07-CONTEXT.md`'s Deferred Ideas; these are deployment secrets, never rendered or editable
  through the LMS (D-02, PAY-14).
- **Dynamic card-origin pricing before Stripe Checkout** — deferred per `07-CONTEXT.md`.

### 0.3 Discretionary layout choices

**Learner-facing screens keep Phase 6's fact-card precedent, not `DetailLayout`.** The offer page,
order-summary (`/checkout/[orderId]`), and receipt (`/orders/[reference]`) remain
ownership-authorized, non-RBAC records — `06-UI-SPEC.md` §0.3's reasoning is unchanged by this
phase's added fields, so this document extends the same `<dl>` fact-card pattern rather than
introducing a second one for the same screens.

**Finance-facing screens (`/staff/payments`, `/staff/payments/[orderId]`) use `ResourceTable` and
`DetailLayout` — the one deliberate divergence from `06-UI-SPEC.md`'s "no `DetailLayout`" ruling.**
`06-UI-SPEC.md` §0.3 excluded `DetailLayout` specifically because the order-summary/confirmation
pages carry no `withPermission` check and no permission string to show in a denied state. That
reasoning does not hold for `/staff/payments/*`: these are `payments.view`-gated staff records,
authorized exactly like every other staff detail screen this codebase already has (Cohort,
Course, User). Building them from `ResourceTable`/`DetailLayout` — confirmed read this session,
`src/components/primitives/ResourceTable.tsx`, `DetailLayout.tsx` — is the established pattern for
that shape, not a new one.

**Manual-payment confirmation and refund actions use two purpose-built dialogs following the
`PublishDialog.tsx` precedent (structured fields + a mandatory reason), not the bare `ConfirmModal`
directly.** `ConfirmModal`'s own header comment (confirmed read this session,
`src/components/primitives/ConfirmModal.tsx`) already names "manual payment confirmation, refunds"
as intended uses, but its props expose exactly one free-text reason field — PAY-03 needs amount,
currency, date, channel, reference, and evidence *in addition to* the mandatory reason.
`src/components/catalogue/PublishDialog.tsx` (confirmed read this session) is this codebase's
existing precedent for exactly that shape: a custom dialog that collects structured data, then
gates its own confirm action behind a `MIN_REASON = 10`-character reason, reusing `ConfirmModal`'s
focus-trap/ESC/return-focus behaviour verbatim rather than re-deriving it. This phase's
`ManualPaymentDialog` and `RefundDialog` (naming is Claude's discretion — `07-CONTEXT.md` reserves
exact component names) follow this precedent: same `MIN_REASON = 10` threshold, same focus
management, same "action not applied" failure copy. A **bare** `ConfirmModal` (no extra structured
fields) is not used anywhere in this phase, because no manual-payment or refund action here is
reason-only.

## 4. Typography

Inherited from `04.1-UI-SPEC.md` §4.3 / `06-UI-SPEC.md` §4 — this phase introduces **no new size
or weight**, staying within the locked 4-size, 2-weight cap.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 14px | 600 | 1.5 |
| Heading | 25px | 600 | 1.2 |
| Display | 16px | 600 | 1.3 |

Notes:
- **Breakdown-card rows** (School fee / KQ NEXUS platform fee / Estimated payment-processing fee)
  render label at Body role, amount at Label role (14px/600, `font-mono tabular-nums`) — the same
  label/value weight split the existing fact-card `<dt>`/`<dd>` pair already uses, just applied to
  a `<dl>` row instead of a grid cell.
- **"Total charged"** is the one row that visually reads as a subtotal: both the label and the
  amount render at Label weight (600), and the row sits after a 1px `--border` divider inside the
  same card — still 14px, still not a fifth type size. This mirrors how an invoice's total line is
  conventionally the heaviest row without changing its font size.
- **The "Estimated" qualifier** on the payment-processing-fee row and the fee-variance disclosure
  sentence (§7.3) render at Body role in `--muted-foreground` — a qualifier, not a warning; it does
  not borrow the `--warning` color, because nothing is wrong with an estimate being an estimate.
- **Finance detail's expected/actual pairs** (§7.6) use the same Label/Body split: the value
  renders at Label weight when present, and an unresolved actual value (`null`, per D-14 — "null
  never means zero") renders as `"— (pending reconciliation)"` at Body weight in
  `--muted-foreground`, never as `"0"` or a blank cell — a null actual value is not the same fact
  as a zero actual value, and the typography must not blur that distinction.

## 7. Screens & States — Interaction Detail

### 7.1 Cohort administration (`src/app/staff/cohorts/CohortForm.tsx`, `[id]/page.tsx`)

Replaces the single `priceMinor` + `currency` `FormField` pair (confirmed read this session, lines
298–330) with two independent `FormField`s, "NGN base price" and "USD base price," each a
`TextInput` with `mono`, `type="number"`, `min={0}`, `step={1}` — identical control shape to the
field being replaced, just duplicated per currency. **Neither field is `required`** — D-08 permits
a Cohort to have only one rail priced; the *readiness* check (not form validation) is what blocks
publication for a missing enabled rail, exactly mirroring how the existing `price` readiness item
is `blocking: true` at publish time but the form itself never forces a value. Both fields keep the
existing hint-text convention ("Whole integer minor units...") with the currency-specific example
amounts in §6.1.

On the Cohort detail Overview tab, the single `{ label: "Price", value: formatPrice(...) }`
`DetailFacts` row (confirmed read this session, `[id]/page.tsx` line 302) becomes two rows, "NGN
price" and "USD price," each rendering the formatted amount or "Not set" — never an empty cell
(matching this file's own existing conditional-fact-row convention). The `ReadinessPanel`'s single
`price` item becomes two items per §6.1's exact label/detail copy, using the same `ReadinessItem`
shape (`id: "price-ngn"` / `id: "price-usd"`, `category: "Price"`, `blocking: true` only for a rail
this deployment has enabled — matching D-08's "missing enabled-rail pricing blocks publication,"
not every possible rail unconditionally).

### 7.2 Offer / cohort card (`src/app/(public)/CohortCards.tsx`)

Replaces the single "Enroll now" `<button>` (confirmed read this session, lines 52–62) with **one
button per available, usable currency rail** — never a disabled-looking button for an unusable
rail, per D-19's "no selectable but doomed payment option":

- **Both rails available:** two buttons render side by side on ≥640px (stacked full-width below
  640px, matching the card's existing responsive convention), each labelled per §6.1's exact
  copy and each posting its own hidden `currency` field alongside the existing hidden `cohortId`
  field to `enrollAction` — the same Server-Action-POST pattern Phase 6 already uses, never a
  `<Link>` (so a prefetch cannot create an order, per the existing file's own stated rationale).
- **Exactly one rail available:** one button renders, in the same position "Enroll now" occupied
  before this phase — no empty second slot, no layout shift from the one-rail case.
- **Neither rail available** (both prices unset, or the deployment's required school settlement
  account is absent per D-05): no button renders at all. In its place, the §6.1 "Payment is
  temporarily unavailable" notice renders inline within the same card, `--warning-surface`
  background — this is a **configuration** gap, not a capacity gap, so it never reuses the "Full"
  copy (`seatsAvailable === 0` is a distinct, unrelated condition and both can theoretically be
  true at once without one implying the other).
- **`seatsAvailable === 0`:** unchanged from Phase 6 — "Full" label, no button, regardless of how
  many currency rails are priced.

### 7.3 Order-summary page (`/checkout/[orderId]`)

The single "Price" fact inside the existing four-fact `<dl>` grid (confirmed read this session,
lines 103–108, 122–134) is replaced by a **separate breakdown card**, positioned exactly where that
grid's Price fact was — the Cohort/Dates/Mode facts stay in the existing grid unchanged; only Price

### 7.4 Receipt page (`/orders/[reference]`)

The single "Amount" fact (confirmed read this session, lines 113–120) is replaced the same way:
the four-row breakdown + currency/provider line + disclosure sentence, inside its own card in the
same position the Amount fact occupied — the existing Order reference/Cohort/Payment-pill/
Enrolment-pill facts are unchanged. Per D-18, this breakdown is **read from the Order's own
immutable snapshot fields**, never recomputed from the Cohort's current price or the active
`GatewayFeeSchedule` — a later price or schedule edit must never change what this page shows,
exactly as the existing page's own header comment already states for `amountMinor`/`currency`
(confirmed read this session, lines 48–52). The exception sub-state (Phase 6's "Payment received —
finishing up" / `warning`-toned Enrolment pill) is unchanged; it still renders alongside the same
breakdown, unaffected by this phase.

### 7.5 Finance payments list (`/staff/payments`)

A `ResourceTable<OrderRow>` (noun: `"payments"`) with columns:

| Column | Renders | Notes |
|---|---|---|
| Order | `order.reference` (mono, primary column — the `<Link>`-wrapped first column per `ResourceTable`'s own convention) | `subtitle`: cohort title |
| Learner | learner name | `subtitle`: learner email |
| Amount | formatted `amountMinor`/`currency` (mono) | learner total, matching every other amount rendering in this phase |
| Provider | plain text label ("Paystack" / "Stripe" / "Manual") | not a `StatusPill` — provider isn't a status (§5's guard note) |
| Payment | `StatusPill`, tone per §5's `OrderStatus` mapping: `PENDING`→neutral, `PAID`→success, `FAILED`→danger, `CANCELLED`→neutral, `REFUNDED`/`PARTIALLY_REFUNDED`→warning, `EXCEPTION`→danger | |
| Settlement | `StatusPill`, discretionary three-state view-model (see note below): "Estimated only" (neutral) / "Reconciled" (success) / "Exception" (danger) | derived, not a stored enum column |

Filters: a `"search"` kind filter (learner name/email/order reference) and a `"select"` kind
`Status` filter (options from `OrderStatus`); a segmented `Provider` filter (`isSegmented` applies
automatically once `≤4` options, per `ResourceTable`'s existing threshold — All/Paystack/Stripe/
Manual is exactly 4, so no new segmented-vs-select logic is needed). Below 640px, the existing
card-list fallback applies unchanged — `primaryColumnKey="order"`.

**Discretionary note on the "Settlement" column:** `07-CONTEXT.md`'s Claude's Discretion explicitly
reserves "exact names of pure calculator helper functions and view-model types" — this three-state
label (`"Estimated only"` / `"Reconciled"` / `"Exception"`) is exactly that kind of view-model, not
a locked requirement. Its underlying rule: `"Estimated only"` while every `gatewayFeeActualMinor`/
`schoolSettlementActualMinor` field remains `null` (D-14 — null before evidence arrives is the
normal, expected state for a fresh payment, not an error); `"Reconciled"` once actual values are
present and match expected within the fee-schedule's own rounding tolerance; `"Exception"` once
actual values are present and do not match (D-18's "visible exception" requirement).

### 7.6 Finance payment detail (`/staff/payments/[orderId]`)

`DetailLayout`, `mode="stacked"`, breadcrumbs per §6.1, `badges`: the Payment and Settlement
`StatusPill`s from §7.5. Sections, in order:

1. **"Learner charge"** — `DetailFacts` with the same four breakdown values plus currency/provider,
   learner name/email, and the Order reference (mono) — the Finance-facing rendering of the exact
   same immutable snapshot the learner's own receipt shows (§7.4), never a second, independently
   computed figure.
2. **"Settlement"** — `DetailFacts` in expected/actual pairs: "Expected school settlement" /
   "Actual school settlement," "Expected KQ gross" / "Actual KQ gross," "Actual gateway fee,"
   "Actual KQ net." Every actual field renders `"— (pending reconciliation)"` (§4, §6.1) until a
   non-null value exists — never `"0"`, per D-14's "null never means zero." When the Settlement
   column (§7.5) resolves to `"Exception,"` the §6.1 reconciliation-exception banner renders
   **above** this section, `--warning-surface` (not `--danger` — this is a bookkeeping flag for
   Finance to investigate, not a claim that the learner was wronged or that money was lost; D-18
   only requires the mismatch be visible, not that it be framed as a failure).
3. **"Manual confirmation"** — renders only while the signed-in actor holds `payments.confirm` for
   this Order's scope *and* the Order's `OrderStatus` is still one a manual confirmation can act on
   (i.e., not already `PAID`). When both hold, a "Confirm manual payment" button opens
   `ManualPaymentDialog` (§0.3, §6.1). **When the Order is already `PAID`** (PAY-04's duplicate-
   confirmation guard), this section instead renders the §6.1 "This order is already paid" banner
   and shows the existing successful `PaymentAttempt`'s provider/date/reference inline — the
   corrective path PAY-04 requires is *visibility into the existing transaction*, not a second
   attempt at the same action.
4. **"Refunds"** — a list of any existing `Refund` records for this Order (reference, amount,
   status via the §5 `RefundStatus` `StatusPill` mapping, actor, date), followed by a "Record a
   refund" button, rendered only while the actor holds `refunds.manage` *and* eligible captured
   value remains (`amountMinor` minus already-refunded amounts, per D-22/D-23's cap). The button
   opens `RefundDialog` (§0.3, §6.1), which shows the §6.1 amount hint before the amount field so
   the cap is visible before the staff member types a number, not only as a rejection after
   submit.
