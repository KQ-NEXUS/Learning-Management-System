<objective>
Rebuild the dispatch service around stable correlation keys, Pass 2 sending with retry and backoff, and audited resend, and move Phase 3's verification, reset and email-change mails onto it.

Purpose: COM-02 needs a database-enforced guarantee that a retried or replayed event never produces a second message, and COM-01 needs the auth mails on the same templated, one-sender path. The drain (Plan 07) only calls `sendQueued`; the delivery log (Plan 12) only calls `resend`.
Output: extended `email-dispatch-service.ts` with a prisma-backed store, a `sendAuthEmail` helper, the four auth services rewired, and unit plus real-Postgres tests.
</objective>

<assumptions>
- A-19: `attempts` counts send attempts; the fifth failed attempt is FAILED; backoff after failed attempts 1 to 4 is 1 minute, 5 minutes, 30 minutes, 2 hours; stale SENDING (over 10 minutes) returns to QUEUED, which can rarely duplicate one mail when a crash falls between provider acceptance and the database write (accepted, T-13-16).
- A-12: only drain-path (Pass 2) terminal failures raise the administrator alert (Plan 11); in-request auth failures record FAILED without an alert because the user recovers by requesting a new link.
- A-13: a configuration error during Pass 2 is a permanent failure: the row goes FAILED at once and can be resent after the configuration is fixed.
- The auth correlation key is `auth:` followed by the SHA-256 hex of the token. The raw token is high entropy, so its hash is not reversible; the key is stable for one issuance and new for every new token.
- The pre-existing template ids email-verification, password-reset and email-change-confirmation are kept, so historical EmailDispatch rows stay coherent.
</assumptions>
