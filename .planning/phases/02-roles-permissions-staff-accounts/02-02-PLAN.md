  <name>Checkpoint: concurrency guarantee for the continuity safeguard</name>
  <decision>Concurrency guarantee for the RBAC-07 continuity safeguard</decision>
  <context>
    02-RESEARCH.md Common Pitfalls #5 describes a time-of-check/time-of-use race: two concurrent
    requests can each read "one other administrator remains" and both proceed, leaving zero.
    02-RESEARCH.md Assumptions Log A3 flags this as needing explicit confirmation before the phase
    is considered done from a security-audit perspective, because no D-XX decision in 02-CONTEXT.md
    covers it — D-27 settles that the safeguard is reactive rather than proactive, which is a
    different question from how hard the guarantee is under true concurrency.

    This gates a real implementation choice in `continuity-service.ts` and its three call sites, so
    it is asked once here rather than re-litigated in each later plan.
  </context>
  <options>
    <option id="transaction-scoped">
      <name>Transaction-scoped count only (recommended)</name>
      <pros>No new locking primitive; the count and the mutating write already share one
      `prisma.$transaction` because Pattern 3's versioning write needs a transaction anyway, so this
      costs nothing extra. Matches D-27's reactive-only framing. Keeps the query shape simple enough
      to unit test without a database.</pros>
      <cons>PostgreSQL's default READ COMMITTED isolation leaves a narrow residual window; two
      simultaneous revocations of the last two administrators could in principle both succeed. The
      residual race is recorded in the threat register as an accepted low-severity item.</cons>
    </option>
    <option id="row-locked">
      <name>Row-level lock (SELECT ... FOR UPDATE) around the check and the write</name>
      <pros>Closes the race fully — a concurrent transaction blocks until the first commits.</pros>
      <cons>Requires a raw query alongside the Prisma client (the codebase has no such precedent
      outside `prisma/sql/001_integrity.sql`); makes the continuity check untestable without a real
      database, breaking the no-database unit-test convention every other test in `tests/` follows;
      adds a lock-contention surface on the Assignment table for an action D-27 already scopes as
      reactive.</cons>
    </option>
  </options>
  <resume-signal>Reply "transaction-scoped" or "row-locked" (or describe a third approach).</resume-signal>
</task>

Create `src/server/services/continuity-service.ts`.

Export `CONTINUITY_BLOCK_MESSAGE` as a module-level constant holding exactly the wording locked in
D-26 and 02-UI-SPEC.md's Copywriting Contract: "This change would leave no user with role-management
access. Choose a different action." It is a constant with no template interpolation so no
administrator's name, email, or count can ever reach it.

Export `ContinuityError` as a plain Error subclass copying `ScopeError`'s exact three-line shape
from `src/server/permissions/scope.ts`, constructed with no arguments and setting its message to
`CONTINUITY_BLOCK_MESSAGE` and its `name` to `ContinuityError`.

Export the discriminated union `ContinuityExclusion` with three members keyed on `kind`:
`assignment` carrying `assignmentId`, `role` carrying `roleId`, and `user` carrying `userId`.

Export `buildContinuityWhere(exclude: ContinuityExclusion, now: Date)` as a pure function returning
the Prisma `Assignment` where object. It always constrains `scopeType` to GLOBAL (D-25), `active`
to true, `revokedAt` to null, the start window to either a null `startsAt` or one at or before
`now`, the end window to either a null `endsAt` or one after `now`, the joined role to
`{ active: true, permissions: { has: "roles.manage" } }`, and — this is the clause with no
precedent anywhere in the codebase and the single most important line in this plan — the joined
user to `{ status: "ACTIVE" }`. `loadGrantsForUser` omits that clause safely because
`getActorBySessionToken` has already rejected non-ACTIVE users for the *current* actor by the time
it runs; this query deliberately counts *other* users and has no such boundary, so a deactivated
administrator whose assignments D-35 leaves intact would otherwise be counted as reachable
(RESEARCH Pitfall 1). Then apply the exclusion: an `assignment` kind sets `id` to not-equal the
given assignment id, a `role` kind sets `roleId` to not-equal, a `user` kind sets `userId` to
not-equal. The exclusion is what makes this a simulation of the post-action state rather than a
protection of the initiator — an administrator may remove their own last global grant as long as at
least one other active global holder remains afterwards (edge RBAC-07/empty).

Export `type ContinuityCount = (where: Record<string, unknown>) => Promise<number>` and
`assertRoleManagementContinuity(count: ContinuityCount, exclude: ContinuityExclusion, now?: Date):
Promise<void>`, which builds the where clause, calls `count`, and throws `ContinuityError` when the
result is zero. Passing the count function as a parameter is what lets each call site hand in
`tx.assignment.count` from inside its own `prisma.$transaction`, co-locating the check with the
write it guards per the concurrency decision resolved in the checkpoint above; a call site with no
transaction of its own may pass a bound `prisma.assignment.count`.

Add a head comment naming the four D-24 trigger points and stating that this module is the only
place role-management continuity is evaluated, so a future contributor does not add a fifth
open-coded variant.

Create `tests/continuity-service.test.ts`. Cover, all without a database:
the where clause built for each of the three exclusion kinds sets the right not-equal key and only
that key; every built where clause constrains `scopeType` to GLOBAL; every built where clause
contains a `user` clause requiring status ACTIVE (name this test explicitly after the
deactivated-administrator pitfall so a future reader sees why it exists); every built where clause
requires the joined role to be active and to have `roles.manage`; the start/end window clauses use
the injected `now`; `assertRoleManagementContinuity` resolves when the injected count returns one
or more; it rejects with `ContinuityError` when the injected count returns zero; the thrown
message equals `CONTINUITY_BLOCK_MESSAGE` exactly; and the message contains no digits and no
at-sign, proving no administrator identity or count can leak through it (D-26).
