<objective>
Make the audit trail visible. RBAC-08 requires that every role, assignment, and staff-account change
be inspectable with actor, target, before and after, scope, reason and timestamp — this plan builds
the read path and the page that renders it.

Purpose: the audit trail already accumulates rows (Phase 1's Course writes, plus everything plans 01
through 04 add). Without a view it is evidence nobody can reach. The view is deliberately built
across the whole `AuditEvent` table rather than filtered to Phase 2's own actions, because it is a
shared table every later phase writes to and scoping it down now would mean rework.

Output: `audit-read-service.ts`, the `/staff/audit` page, the expand-in-place `AuditTable`, and the
nav link.
</objective>

Create `src/server/services/audit-read-service.ts`. This file is read-only by construction: it adds
no create, update, delete or upsert call against the audit model — `audit-service.ts` remains the
sole writer, and `tests/audit-append-only.test.ts` from plan 02 keeps checking that.

Export `AuditFilter` as `{ actorId?: string | null; from?: Date | null; to?: Date | null;
action?: string | null; limit?: number }` — actor, date range and action are D-31's version-1
filters, and target-record filtering is deliberately absent because it is reached through the
record's own History tab instead.

Export `AUDIT_PAGE_LIMIT` as 100 and `buildAuditWhere(filter: AuditFilter)` as a pure function
returning the Prisma where object: an `actorId` equality when supplied, a `createdAt` range built
from whichever of `from` and `to` are supplied (both, either, or neither), and an `action` equality
when supplied. Omit a key entirely when its filter is absent rather than emitting an undefined
value, so the shape stays assertable. These three filters map onto the model's existing
`actorId, createdAt`, and `action, createdAt` indexes.

Export `AuditRow` as the projection the table renders: id, createdAt, actorId, the actor's name and
email (or nulls for a system actor), actorType, action, targetType, targetId, scopeType, scopeId,
before, after, reason, outcome, correlationId.

Define an injectable `AuditReadStore` port with `auditEvent.findMany` and `auditEvent.findFirst`,
plus a `user.findMany` for the actor filter's option list. Export
`createAuditReadService(deps: { store; withPermission })` and a bound `auditReadService`.

`list(filter)` is wrapped by `withPermission("audit.view", () => ({}))` — an empty scope, so audit
reading is a global capability — orders by `createdAt` descending, takes `filter.limit` or
`AUDIT_PAGE_LIMIT`, includes the actor's name and email, and returns `AuditRow` values. It applies
no additional restriction to the `reason` field: D-16 makes reason text visible to any `audit.view`
holder, so no second gate is layered on.

`filterOptions()` is wrapped the same way and returns the distinct action strings present in the
table plus the distinct actors (id, name, email) that appear as an `actorId`, so the page can
populate its two select filters without a second round trip.

Create `tests/audit-read-service.test.ts` on the fake-store harness. Cover: `buildAuditWhere` with
an empty filter returns an object with no keys; with an actorId only, exactly an actorId key; with
a from date only, a createdAt range carrying only a lower bound; with a to date only, only an upper
bound; with both, both bounds; with an action, an action key; `list` refuses without an `audit.view`
grant; `list` refuses when the only `audit.view` grant is Cohort-scoped, since the resolver is an
empty scope; `list` with a GLOBAL grant orders by createdAt descending and passes
`AUDIT_PAGE_LIMIT` as the take when no limit is supplied; a caller-supplied limit overrides it;
`filterOptions` refuses without the grant; and the returned rows carry the `scopeType` and
`scopeId` fields, proving the view surfaces the scope plan 02 started recording.
