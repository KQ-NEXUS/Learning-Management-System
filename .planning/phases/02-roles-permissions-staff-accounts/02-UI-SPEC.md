## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled design system, not shadcn |
| Preset | not applicable |
| Component library | none (no Radix/Base UI/headless-UI dependency in `package.json`) — 4 custom primitives in `src/components/primitives/` |
| Icon library | none — no icon package installed (`package.json` deps: `@prisma/client`, `next`, `react`, `react-dom` only). Symbols are plain glyphs (`×`, `↑`/`↓`/`↕`) or `StatusPill`'s CSS dot, not an icon font/SVG set |
| Font | Geist Sans (`--font-geist-sans`, body/UI) and Geist Mono (`--font-geist-mono`, identifiers/money/counts via `font-mono tabular-nums`) — both loaded in `src/app/layout.tsx`, wired through `@theme inline` in `globals.css` |

**Why `Tool: none` and not the shadcn gate:** `components.json` does not exist (checked this session — `ls components.json` → not found), but this is not an unstyled greenfield project needing initialization. The codebase already has an established, in-production design system: Tailwind v4 `@theme` tokens (`--accent`/`--accent-contrast`, `--danger`/`--danger-surface`, `--success`, `--warning`, zinc neutrals) plus four proven primitives (`ResourceTable`, `ResourceForm`, `DetailLayout`, `ConfirmModal`) exercised end-to-end on the Courses slice. Per this phase's explicit brief, the contract is to **reuse this system exactly**, not to introduce shadcn alongside it. Initializing shadcn now would create two parallel component systems in one codebase — skipped by design, not by oversight.

**Visual character (verbatim from `globals.css` comment):** "Utilitarian console, compact density: hairline borders, near-zero radius, data first." Every new Phase 2 screen must read as an extension of the Courses reference slice, not a new visual language.

**Focal point per primary screen:**
- **Roles list:** the table's role-name/badge column is the primary focal point — the "Default" `StatusPill` badge (accent) draws the eye to the 5 pinned defaults first (D-38); the filter bar and row-count caption are secondary.
- **Role detail page:** the Permissions checkbox tree (Permissions tab, 14 collapsible domain groups) is the primary focal point — it is where the record's substance lives and where edits happen; the Overview tab's `DetailFacts` (name, description, active-assignment count) and the History tab are secondary, subordinate reference material.
- **Users (staff accounts) list:** the table's name/email column paired with the `StatusPill` status dot is the primary focal point — status (`ACTIVE`/`DEACTIVATED`/`PENDING_VERIFICATION`) is the fact an admin scans for first; the filter bar is secondary.
- **User detail page:** the Assignments tab's role/scope rows are the primary focal point — this is the record's operative content (what access this person actually has); the Overview tab's account facts are secondary.
- **Assignment drawer:** the typeahead user-search field is the primary focal point on open (it is the first required input, D-17); the scope-type picker becomes primary only after a user is selected.

Not this phase's gap to close in isolation; it is an NFR-09/NFR-10 (WCAG 2.2 AA, responsive) concern that belongs to Phase 15's launch-readiness audit.

## Typography

Each role below is pinned to exactly **one** canonical Tailwind class — not a range — to remove ambiguity about which exact size a new Phase 2 component should use. The scale is exactly **4 distinct sizes**: `text-xs`, `text-sm`, `text-base`, `text-lg`. The Eyebrow role and the UI-control role share the same `text-xs` (12px) size — they are two rows below because they play different roles, not because they are different sizes. They are distinguished from each other by weight/case/tracking modifiers only, never by size: Eyebrow adds `font-semibold uppercase tracking-wide`, UI control stays unmodified (no uppercase, no tracking utility). `tracking-wide` is the exact modifier already verified in production use for this role in both `DetailLayout.tsx` (stacked-mode section `h2`, line 217: `text-[11px] font-semibold uppercase tracking-wide`; `DetailFacts` dt, line 263: `text-[11px] uppercase tracking-wide`) and `ConfirmModal.tsx` (reason `label`, line 155: `text-[11px] font-semibold uppercase tracking-wide`) — it is the majority convention across both files, so it is the one Phase 2 standardises on (the one outlier, `ConfirmModal`'s dialog-level eyebrow at line 130, uses `tracking-[0.12em]` at the smaller legacy `text-[10px]`; that spot is untouched pre-existing code per the legacy exception below, not a pattern Phase 2 extends).

| Role | Canonical class | Size | Weight | Line Height |
|------|------|------|--------|-------------|
| Eyebrow / uppercase label (table column headers, `FormField` labels, `DetailFacts` dt, section kickers) | `text-xs` | 12px | 600 semibold, `uppercase`, `tracking-wide` — the modifiers are what distinguish this row from UI control below; the base size is identical | 1.33 |
| UI control (buttons, links, filter chips, hint/mono metadata, secondary captions) | `text-xs` | 12px | 500 medium for interactive elements (buttons, links); implicit 400 for hints/captions/mono metadata — no `uppercase`/`tracking-*` | 1.33 |
| Body (paragraphs, dialog descriptions, table primary-cell value, form field values) | `text-sm` | 14px | 400 regular implicit (500 medium only where a value is emphasised, e.g. a table primary-cell name) | 1.43 (Tailwind `text-sm` default) |
| Section / dialog heading (`ResourceTable`/`ResourceForm` section `h2`, `ConfirmModal` dialog `h2`) | `text-base` | 16px | 600 semibold (`font-semibold`), `tracking-tight` | 1.2 |
| Page / record heading (`DetailLayout` record `h1` only) | `text-lg` | 18px | 600 semibold (`font-semibold`), `tracking-tight` | 1.2 |

**Declared weights: 500 (medium) and 600 (semibold).** Body/paragraph text uses the browser's implicit 400 (no `font-normal` utility is ever applied anywhere in the existing primitives — confirmed by reading all four files this session), so it is not counted as a third declared weight, consistent with how the codebase itself treats it. Do not introduce `font-bold` (700) or any weight outside {400 implicit, 500, 600} anywhere in Phase 2.

**Scoped legacy exception — pre-existing, not extended this phase:** `text-[10px]` and unmodified `text-[11px]` appear in a small number of narrow, pre-existing spots (`ConfirmModal`'s dialog-level kicker/timestamp text at `text-[10px]` with `tracking-[0.12em]`, and a few `text-[11px]` labels inside `ConfirmModal`/`DetailLayout` that predate this contract) — reuse these primitives verbatim as-is, but every **new** Phase 2 eyebrow/label element pins to `text-xs font-semibold uppercase tracking-wide`, never `text-[10px]` or an unmodified `text-[11px]`.

Monospace (`font-mono tabular-nums`) is reserved for: identifiers/slugs, record counts, dates/times, permission strings, and the reason-length counter — never for prose.

**Destructive (`danger`) reserved for, specifically in this phase:**

**Success / warning (`StatusPill` tones, existing):**
- `success` (`#15803d`): `User.status === "ACTIVE"`, a role's `active === true` where relevant

## UI Considerations

Ran via the `ui-consideration-probe` engine against 10 named elements/surfaces (`RolesTable`, `RoleForm`/`PermissionPicker`, `EffectiveAccessPreview`, `UsersTable`, `StaffAccountForm`, `AssignmentDrawer`, `AuditTable`, `RoleDetailPage`, `UserDetailPage`, `ContinuityBlock`), post-approval per the workflow's write-after-verify rule. **59 applicable considerations, all resolved explicitly with the user, 0 backstop, 0 unresolved.** (Supersedes the pre-approval draft table that stood here before the checker's final pass — see 02-DISCUSSION-LOG.md for the full per-item Q&A record.)

### RolesTable
- **Empty:** No true zero-roles state (5 defaults always seeded). Filtered-empty reuses `ResourceTable`'s built-in "No roles match these filters" panel + Clear filters button verbatim.
- **Loading:** Inherited `ResourceTable` skeleton (5 pulsing rows, held column widths) — unchanged.
- **Error:** Inherited `ResourceTable` "Could not load roles" panel + Retry — unchanged.
- **Populated:** Defaults pinned first with "Default" badge (D-37/D-38); custom roles below.
- **Partial:** N/A — a `Role` row is always a complete record; no partial-row rendering path exists.
- **Overflow:** Long name/description wraps within its cell — no truncation utility applied.
- **Zero-one-many:** No special-casing beyond `ResourceTable`'s built-in noun pluralization; the table always has ≥5 rows.

### UsersTable
- **Empty:** No true zero-users state (seed admin account always exists). Filtered-empty reuses the same built-in panel as RolesTable.
- **Loading / Error:** Inherited `ResourceTable` skeleton / error panel — unchanged.
- **Populated:** Name, email, `StatusPill` for status (ACTIVE/DEACTIVATED/PENDING_VERIFICATION); standard rows, no grouping (no "default" concept for Users).
- **Partial:** N/A — a `User` row is always complete by schema.
- **Overflow / Long-text:** Long name/email wraps within its cell — no truncation, single resolution covers both categories.
- **Zero-one-many:** No special-casing beyond built-in noun pluralization.

### RoleForm (`PermissionPicker`)
- **Empty:** Blank create = all 14 domain groups unchecked/collapsed; clone-from-default (D-02) pre-fills the picker with the source role's permission set.
- **Loading:** Inherited `ResourceForm` skeleton (title bar + 5 pulsing field placeholders) while editing loads.
- **Error:** Both `ResourceForm` paths apply unchanged — (a) load failure (403/could-not-load) replaces the whole form; (b) submit-validation failure shows the top error summary, entered values retained.
- **Partial:** N/A — a `Role` fetch is all-or-nothing.
- **Overflow / Long-text:** Long name/description wraps within its field (`TextInput`), no truncation. `EffectiveAccessPreview` handles its own long-content case separately (below).

### StaffAccountForm
- **Empty:** Blank on open — no clone option here (create-only), all fields empty, no role/scope pre-selected.
- **Loading:** N/A — create-only form, no existing record to fetch; only `ResourceForm`'s inherited "Saving…" submit-pending state applies.
- **Error:** Inherited `ResourceForm` error-summary path covers both client validation (duplicate email, weak temp password, no role selected) and server-side rejections, rendered as additional summary entries.
- **Partial (submit-level):** **Account creation and first-role-assignment are one atomic transaction** — both succeed or both fail together. This is a real implementation requirement, not just a UI note: it prevents a `User` being created with zero assignments if the second half of the combined D-22 flow fails, which would silently defeat D-22's "no dead-end zero-access account" intent. Flag this for the planner as a transactional requirement on the staff-account-creation service.
- **Long-text:** Same as RoleForm — wraps within field, no truncation.

### EffectiveAccessPreview (D-04)
- **Empty:** Zero permissions checked → "This role currently grants no access."
- **Populated:** Grouped by domain, comma-separated verbs per domain (e.g. "Courses: view, edit, publish · Cohorts: view · Payments: no access") — scales from 1 permission to all 36 without becoming a run-on sentence.
- **Overflow/long-text:** Fixed max-height with internal vertical scroll once many domains are granted — a security-relevant access summary must remain fully readable (scrolled, not truncated) per the same principle noted in the pre-approval draft.

### AssignmentDrawer
- **Empty (typeahead):** Placeholder "Start typing a name or email" before any query; no results list shown until 1-2 characters are typed.
- **Empty (scope picker):** Programme/Cohort show the D-18 "none yet" state until Phases 4/5 seed real records.
- **Loading:** Inline spinner near the search input; previous results stay visible until new ones arrive (no flash-to-empty between keystrokes).
- **Error:** Inline "Search failed — try again" beneath the input (drawer stays open) for search failures; `ResourceForm`-style error summary for save failures.
- **Populated:** Selected user locked in (name/email shown, not re-editable without clearing); Save enabled only once user + role + scope are all set.
- **Partial:** While user is picked but role/scope isn't yet chosen, Save simply stays disabled — no premature error messaging (matches `ResourceForm`'s validate-on-blur/submit philosophy, not on every keystroke).
- **Overflow:** Typeahead results cap at 10, scrolling internally if more exist.
- **Zero-one-many:** Zero matches → "No users match "{query}""; one/many results render as the same selectable list, no special-casing.
- **Long-text:** Long name/email in a dropdown row truncates with ellipsis (unlike table cells, which wrap) — the full value is visible again once selected.

### AuditTable
- **Empty:** Both cases use `ResourceTable`'s existing branching — "No audit events yet" (genuine zero, possible only right after a brand-new deployment) vs "No audit events match these filters" (filtered).
- **Loading / Error:** Same skeleton / error-panel convention as `ResourceTable`, even though `AuditTable` is a new component (D-32's "modeled on ResourceTable's conventions" framing).
- **Populated:** Collapsed rows show actor/action/target/time; clicking expands in place (D-32) to show the full diff, reason, scope. **One row expanded at a time (accordion-style)** — expanding a new row collapses the previous one.
- **Partial (diff content):** The expanded view shows **only the fields that actually changed** (field: old → new), not the full before/after objects verbatim — skips null/unchanged noise.
- **Overflow:** Expanded diff content has a max-height with internal scroll, not unbounded page growth.
- **Zero-one-many:** No special-casing beyond the shared noun-count convention.

### RoleDetailPage
- **Empty:** History tab just shows the single v1 row when no edits have happened yet — a role can never have zero versions, so v1 itself is the "nothing has changed" state.
- **Loading / Error:** Inherited `DetailLayout` page-level skeleton; both page-level (403/could-not-load) and per-section error isolation (a failing tab doesn't break the others) apply unchanged.
- **Populated:** Overview tab (`DetailFacts`: name, status, isDefault, version, assignment count); **Permissions tab IS the `RoleForm` embedded inline** (not a separate read-only view + distinct edit screen); History tab (D-06 version list).
- **Partial:** N/A — a `Role` fetch is all-or-nothing; History tab is not paginated this phase.
- **Overflow:** Content scrolls vertically within the active tab panel; the page itself never scrolls sideways.
- **Zero-one-many:** The History tab's badge shows a bare version-count number, never pluralized copy.
- **Long-text:** Long description wraps within `DetailFacts`' value cell, no truncation.
