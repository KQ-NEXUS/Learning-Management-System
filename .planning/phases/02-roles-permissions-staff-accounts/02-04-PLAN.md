<objective>
Expand the phase to the second half of the access model: binding a user to a role at a scope, and
taking that binding away again — the RBAC-04 assignment lifecycle, plus the scope-target lookups the
assignment UI needs.

Purpose: RBAC-04 is where scope stops being theoretical. An assignment created at the wrong scope
is an elevation-of-privilege path, and a revoke that touches a sibling row silently removes access
nobody asked to remove. Both are guarded here, in the service, before any UI exists.

Output: `assignment-service.ts` with create and revoke only (assignments are immutable per D-23),
`scope-lookup-service.ts` for the four-scope-type picker, and two database-free test files.
</objective>

Create `src/server/services/assignment-service.ts`, following `course-service.ts`'s wiring shape
(prisma from the db module, `withPermission` from the permissions barrel, `recordAudit` from the
audit service) but hand-written rather than routed through `createResourceService`, which has no
concept of revocation.

Export `assignmentTargetScope(scopeType: ScopeType, scopeId: string | null): ResourceScope`,
mirroring `courseScope`'s shape: GLOBAL yields an empty object, PROGRAMME yields a programmeId,
COURSE yields a single-element courseIds array, COHORT yields a cohortId. A non-GLOBAL scope type
with a null scopeId is a caller error — throw `ScopeError` rather than degrading to an empty object,
because an empty object is the shape a GLOBAL grant reaches and silently widening a scoped request
into a global one is the exact escalation `grantMatches` is written to prevent.

Export `AssignmentReasonRequiredError` copying `ScopeError`'s three-line shape, and re-export
`MIN_REASON_LENGTH` from the role service so the revoke gate and the role gates share one constant.

Define a narrow injectable `AssignmentStore` port carrying only `assignment.findUnique`,
`assignment.findMany`, `assignment.create`, `assignment.update`, `assignment.count`,
`role.findUnique`, and `$transaction(fn)`. Export
`createAssignmentService(deps: { store; withPermission; audit })` and a bound `assignmentService`
singleton.

`create({ userId, roleId, scopeType, scopeId, endsAt, reason })` is gated on `roles.manage` with the
scope resolver `assignmentTargetScope(input.scopeType, input.scopeId)` — so the caller's own grant
must reach the target scope, which is what stops a Programme-scoped administrator granting globally.
Inside the handler: load the role and reject when it is missing or inactive; for every permission
the role carries, call `assertScopeAllowed(permission, scopeType)`, which is the existing
implementation of the global-only rule and throws `ScopeError` when, for instance, a role bundling
`licence.activate` is being assigned at COURSE scope; create the Assignment row with `active` true,
`startsAt` set to the current time (D-20 — immediate start only; do not accept a caller-supplied
start), the supplied `endsAt` or null, the supplied reason or null, and `createdById` from the
actor. Accept exactly one scope target per call — no array, no batch (D-21). After the write, audit
with action `assignment.created`, targetType `Assignment`, the new id, the created row as after,
the reason, and — this is what plan 02's audit change exists for — the assignment's own `scopeType`
and `scopeId` (RESEARCH Pitfall 3).

`revoke({ assignmentId, reason })` is gated on `roles.manage` with a scope resolver that loads the
assignment and returns `assignmentTargetScope` for its stored scope, so authority is checked against
the assignment's real scope rather than anything the caller asserted. Inside the handler: reject
with `AssignmentReasonRequiredError` when the trimmed reason is shorter than `MIN_REASON_LENGTH`
(D-14); load the assignment with its role's permissions; when the assignment is already revoked,
return it unchanged rather than writing a second revocation. Open one `$transaction`: when the
assignment's `scopeType` is GLOBAL and its role's permissions include `roles.manage`, call
`assertRoleManagementContinuity` with the transaction client's assignment count and an exclusion of
kind assignment carrying this assignment id (D-24a); then update that one row by id, setting
`revokedAt` to now, `revokedById` to the actor, `active` to false, and `reason` to the supplied
reason. Update exactly that row — never a `updateMany`, never a filter that could match a sibling
(RBAC-04, edge RBAC-04/unclassified). After commit, audit with action `assignment.revoked`, the
before and after rows, the reason, and the assignment's `scopeType` and `scopeId`. Do not add an
update method: D-23 makes assignments immutable, and a scope or end-date change is revoke-old plus
create-new.

`listForUser(userId)` is gated on `users.view` with an empty scope and returns that user's
assignments newest first, including the role's id, name and active flag, and the assignment's
scopeType, scopeId, startsAt, endsAt, active, revokedAt and reason — the data D-19's per-user row
list renders.

Create `tests/assignment-service.test.ts` on the fake-store harness, with a describe block whose
name contains the word scope so `-t scope` selects the scope cases per 02-VALIDATION.md. Cover:
`assignmentTargetScope` maps each of the four scope types to the right `ResourceScope` shape;
it throws `ScopeError` for a non-GLOBAL type with a null scopeId; `create` refuses without a
`roles.manage` grant; `create` with only a Course-scoped grant refuses a GLOBAL target; `create`
with a Course-scoped grant succeeds for that same course id; `create` rejects a role carrying
`licence.activate` at COURSE scope with `ScopeError` and performs no write; `create` sets `startsAt`
to a non-null value and ignores any caller-supplied start; `create` emits one audit entry whose
`scopeType` and `scopeId` equal the assignment's own; `revoke` without a reason throws
`AssignmentReasonRequiredError` and performs no write; `revoke` with a 10-character reason updates
exactly one row, identified by id; revoking one of a user's three assignments leaves the other two
untouched in the fake store; revoking a GLOBAL `roles.manage` assignment invokes the continuity
check with an exclusion of kind assignment and, when the injected count returns zero, throws
`ContinuityError` and performs no write; revoking a COURSE-scoped assignment of the same role does
not invoke the continuity check at all; and `revoke` on an already-revoked assignment writes
nothing.
