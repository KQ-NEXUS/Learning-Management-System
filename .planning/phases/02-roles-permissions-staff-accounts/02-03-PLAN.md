<objective>
Expand the tracer's create-only role slice into the full role lifecycle: edit with versioning,
rename, deactivate and reactivate, all reason-gated and continuity-guarded, with version history
visible on a role detail page.

Purpose: RBAC-02 requires that an edit create a new version, preserve prior versions, and demand a
reason for sensitive reductions. That is the phase's most intricate write path — it combines the
versioning transaction, an optimistic lock, a conditional reason gate, and two of the four RBAC-07
trigger points in one operation.

Output: `roleService.update`, `roleService.setActive`, `roleService.versions`,
`roleService.assignmentCount`, the `/staff/roles/[id]` detail page with Overview, Permissions, and
History tabs, and the Server Actions that drive them.
</objective>

Add `update` to the service, gated on `roles.manage` with an empty scope, taking `id`,
`expectedVersion`, `name`, `description`, `permissions`, and a nullable `reason`. In order:
call `validateRolePermissionSet` on the submitted permissions; read the current row and throw if it
is missing; throw `RoleVersionConflictError` when the stored `version` differs from
`expectedVersion` — this is the optimistic lock, and it must compare before anything is written;
compute the removed set as the stored permissions minus the submitted permissions; when the removed
set is non-empty and the trimmed reason is shorter than `MIN_REASON_LENGTH`, throw
`ReasonRequiredError` (D-09), while an edit that only adds permissions passes with no reason (D-10)
— one reason covers however many permissions a single save removes (D-15). Then open one
`$transaction`: inside it, when `roles.manage` is present in the stored permissions and absent from
the submitted set, call `assertRoleManagementContinuity` with the transaction client's assignment
count and an exclusion of kind role carrying this role id (D-24b); update the `Role` row with the
submitted fields and `version` set to the stored version plus one; create the `RoleVersion` row at
that new version carrying the post-update name, description, permissions and active flag, the
reason, and `createdById` from the actor. After the transaction commits, call the audit sink with
action `role.updated`, targetType `Role`, the id, the pre-update row as before, the post-update row
as after, the reason, `scopeType` GLOBAL, `scopeId` null, outcome SUCCESS. Per RESEARCH Pattern 3,
`RoleVersion` and the audit event serve two different surfaces — write both every time, never one
instead of the other. Do not diff to suppress a no-op edit: an identical resubmission still bumps
the version (edge RBAC-02/idempotency). Apply this path to seeded default roles with no exemption
(D-39, RESEARCH Pitfall 4); `isDefault` influences nothing here.

Add `setActive`, gated on `roles.manage` with an empty scope, taking `id`, a boolean `active`, and a
nullable `reason`. Deactivation requires a reason of at least `MIN_REASON_LENGTH` and throws
`ReasonRequiredError` otherwise (D-11); reactivation requires none. Inside one `$transaction`: when
deactivating and the role's current permissions include `roles.manage`, call
`assertRoleManagementContinuity` with the transaction client's count and an exclusion of kind role
carrying this role id (D-24c); update the `Role` row's `active` flag and bump `version`; create the

assignment's grant on the next authorization check (D-07's reversibility note describes the cost of
abandoning that live-join design, not the cost of reactivating).

Add `versions(roleId)`, gated on `roles.view` with an empty scope, returning that role's

`roles.view` with an empty scope, counting Assignment rows for the role that are active, not
revoked, and whose window is currently open — this is the number D-05's extra confirmation and
