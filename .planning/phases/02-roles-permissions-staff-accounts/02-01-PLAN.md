`src/server/services/role-service.ts` (new). Follow `course-service.ts`'s import block exactly
(`prisma` from `@/server/db`, `withPermission` from `@/server/permissions`, `ResourceScope` type,
`recordAudit` from the audit service). Do NOT route Role through `createResourceService` — its
generic `archive()` writes a status value Role does not have, which is RESEARCH Pitfall 2. Export:
`roleScope()` returning an empty `ResourceScope` object (Pattern 1: an empty resource is reachable
only by a GLOBAL grant, so role administration is inherently global with no extra code);
`InvalidPermissionSetError` as a plain Error subclass copying `ScopeError`'s exact three-line shape
from `src/server/permissions/scope.ts`; `validateRolePermissionSet(input: readonly string[]):
Permission[]` which rejects any entry failing `isPermission()` (message names the offending
identifiers), rejects a set whose deduplicated size differs from its length, and accepts an empty
array unchanged — the seeded Learner role has an empty permission set, so a non-empty check would
break it (per D-03 and edge RBAC-01/empty). Define a narrow injectable port type `RoleStore`
carrying only what this service uses: `role.findMany`, `role.findUnique`, `role.create`,
`role.update`; `roleVersion.create`; `assignment.count`; and `$transaction(fn)`. Export
`createRoleService(deps: { store: RoleStore; withPermission: WithPermission; audit: (event:
BusinessAuditEvent) => Promise<void> })` returning `list`, `get`, and `create`, and export a bound
singleton `roleService` constructed from `prisma`, the live `withPermission`, and `recordAudit`.
`list` is gated on `roles.view` with an empty scope and returns id, name, description, active,
isDefault, version, permissions, createdAt. `get(id)` is gated on `roles.view` with an empty scope.
`create({ name, description, permissions })` is gated on `roles.manage` with an empty scope; it
validates the permission set first, then runs one `$transaction` that creates the `Role` row
(`isDefault` false, `active` true, `version` 1) and the matching `RoleVersion` row (version 1, same
name/description/permissions/active, `reason` null, `createdById` from `ctx.actor.userId`); after
the transaction commits it calls the audit sink with action `role.created`, targetType `Role`, the
new id, the created row as `after`, null reason, outcome `SUCCESS`. Per RESEARCH Pattern 3,
`RoleVersion` and the audit event are two different tables serving two different surfaces — write
both, never one instead of the other. No try/catch inside the service: `withPermission` throws for
the caller to handle, matching the codebase convention.
