<objective>
Build the enrolment state machine: the five staff actions COH-05 names, each validated against an explicit
transition table, reason-captured, audited, evented, and seat-correct.

Purpose: this is mechanism, not policy (D-16). No approval workflow, no rules engine, no automated refund
or credit — PRD §15.3(4) explicitly forbids automating that approval logic. What the system owes is: the
transition is legal, the reason is captured, the audit row is written, the seat count stays true, and no
duplicate active enrolment can exist. Phase 6 checkout and Phase 7 manual-payment confirmation both call
into this surface rather than re-implementing it.
Output: `enrolment-service.ts`, a unit test file, and a Testcontainers integration test file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff browser → enrolment action | Untrusted enrolment id, target cohort id, status target and reason |
| source cohort scope → target cohort | A transfer writes into a second cohort the caller's grant may not cover |
| enrolment state → seat count | Any transition that miscounts silently oversells or undersells the cohort |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-38 | Tampering | An illegal state jump, e.g. `WITHDRAWN` → `ACTIVE`, resurrecting access without a re-enrolment | mitigate | Explicit `VALID_TRANSITIONS` table with `assertTransition` called before every write; terminal statuses have empty allow-lists; unit + integration tested |
| T-05-39 | Elevation of Privilege | A scoped staff member acting on an enrolment outside their cohort grant | mitigate | `withPermission("enrolments.manage", enrolmentCohortScope \| cohortResourceScope)`; scope resolved from the row, never caller-asserted |
| T-05-40 | Elevation of Privilege | Transfer used to write into a cohort the caller's grant does not cover | mitigate | Same-offer restriction (`CrossOfferTransferError`) confines the target to a sibling cohort of the same Course/Programme, which any grant reaching the source also reaches through `courseIds`/`programmeId`; cross-offer transfer is deferred, not silently allowed |
| T-05-41 | Tampering | Seat double-count on approve, drifting `seatsTaken` above real occupancy until the cohort falsely reads full | mitigate | `holdsSeat` consulted before `takeSeat` (Pitfall 3); both branches unit-tested for increment count; integration test asserts `seatsTaken` never exceeds the true occupancy |
| T-05-42 | Tampering | Duplicate active enrolment on a replayed request | mitigate | The partial unique index is the guard; `AlreadyEnrolledError` is the translation; grep gate proves there is no application-level pre-check (which would itself be a race) |
| T-05-43 | Repudiation | A transition with no reason or no audit row | mitigate | `requireReason` on all five actions; `recordAudit` after commit with before/after; audit table is append-only (`tests/audit-append-only.test.ts`) |
| T-05-44 | Repudiation | A committed transition whose Phase-13 notification event was lost | mitigate | `writeDomainEvent` inside the same `$transaction` as the status write; integration test asserts exactly one row per action |
| T-05-45 | Tampering | Automated refund/credit logic quietly introduced with a withdrawal | mitigate | Header states PRD §15.3(4) forbids it; grep gate confirms no refund/credit write; Finance owns this in Phase 7/8 |
| T-05-46 | Information Disclosure | A partially-applied transfer leaving a learner enrolled twice or in neither cohort | mitigate | Release and take happen in ONE `$transaction`; integration test asserts atomic failure on a full target |
</threat_model>
