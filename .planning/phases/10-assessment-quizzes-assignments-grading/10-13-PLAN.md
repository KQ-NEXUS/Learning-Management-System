<objective>
Build the grade-entry screen (ASM-05, ASM-06): read-only submission context, score and feedback entry,
explicit release, and D-07's mandatory-reason override on an already-released grade.

Purpose: This screen is where ASM-05's "record grades/feedback, save drafts, release explicitly" and
ASM-06's "override requires a mandatory reason" both land. Its rendering rules are load-bearing —
UI-SPEC §5 states that showing the override flow on a DRAFT row is itself a spec violation, because
it would let staff bypass the mandatory-reason path.
Output: the route, the client component, the action module, and two test files.
</objective>

    a released grade immediately disappears from the DRAFT queue in the same response. No follow-up
    client fetch, no `router.refresh()`.

    Create `GradeEntryClient.tsx` as a client component with two mutually exclusive modes driven by the
    grade's `status`.

    DRAFT mode (or no grade yet): a `ResourceForm`-shaped editable zone with a Score field
    (`TextInput` type="number", label "Score", hint "out of {totalMarks}") and a Feedback field
    (textarea, at least `rows={3}`, label "Feedback", hint "Visible to the learner once released.").
    Buttons: "Save draft" in the secondary `BTN` style, always available; "Release" in `BTN_PRIMARY`,

    buttons are GONE — replaced by a single "Override grade" action with the `RotateCcw` icon. The two
    sets must never be visible at once: leaving a Save button beside an Override button would let a
    grader bypass the mandatory-reason path by simply re-saving, which is precisely the warning sign
    10-RESEARCH.md Pitfall 5 names. Add a comment in the render stating this.

    The override opens `ConfirmModal` with `tone="default"` (a correction is not irreversible data
    loss; danger stays reserved for that), `minReasonLength={10}`, title "Override grade", and the §6
    description "This grade has already been released to the learner. Overriding it requires a reason
    and will be recorded in the audit history." The modal also collects the new score — render it as an
    additional field inside the modal's `description` slot, which is typed `ReactNode` and accepts
    arbitrary content, rather than widening `ConfirmModal`'s props. Confirming calls
    `overrideGradeAction` with the new score and the reason.

    Override history: after any override, render a read-only, never-editable fact row per override,
    newest first, reading "Overridden from {previousScore} to {newScore} by {actorName}, {date} —
    \"{reason}\"" per §6.1.

    Named gap (§6.2): once the grade is RELEASED, render the labelled placeholder "Certificate impact —
    not yet evaluated (arriving in a future update)" in the read-only zone, in muted text with no icon

    `grade.overridden` event it will consume. Do not compute or invent an impact value.

    Colour rules: no raw hex, no `--accent` used as a `StatusPill` tone, `neutral` for "Draft" and
    `success` for "Released". `RotateCcw` is a named `lucide-react` import.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff browser → grading actions | Score, feedback, reason and the path ids cross here |
| released grade → mutation path | Only the override may change it, and only with a reason |
| submission file → staff download | Must be gated by the same Cohort scope as the queue |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-05 | Repudiation | mandatory-reason bypass | mitigate | Three independent gates: the modal's `minReasonLength={10}`, the action's zod schema, and the service's own trim-and-length check. The render contract removes the Save control entirely in RELEASED mode so there is no plain-edit affordance to bypass through |
| T-10-26 | Tampering | override on a DRAFT grade | mitigate | The override affordance renders only inside a `status === "RELEASED"` branch (UI-SPEC §5's rendering contract), and `grade-override-service.ts` throws `GradeNotReleasedError` independently |
| T-10-03 | Elevation of Privilege | grade-entry route and actions | mitigate | Every read and write goes through the `withPermission`-wrapped, `enrolmentCohortScope`-resolved services; the route imports no `@prisma/client`, enforced by an AST assertion |
| T-10-23 | Information Disclosure | IDOR on `submissionId` | mitigate | `getGradingDetail` resolves scope by first reading the submission row, so an id from another Cohort produces a denial rather than a read of the learner's name and file |
| T-10-20 | Information Disclosure | submission file download | mitigate | Staff download resolves through the grading detail under the `submissions.view` grant; the learner-path download function is not called from a staff route |
| T-10-32 | Tampering | fabricated certificate impact | mitigate | ASM-06's completion/certificate impact renders as an explicit named gap rather than a computed value, so no downstream reader can mistake a placeholder for an evaluated fact (UI-SPEC §6.2) |
| T-10-SC | Tampering | npm installs | accept | No package installs |
</threat_model>
