<objective>
Build Assessment authoring (ASM-01, ASM-03): the pure draft-validation evaluator, and the service
that creates, edits, archives, nested-writes questions for, and publishes an Assessment under the
existing permission catalogue and audit conventions.

Purpose: This is the staff-facing half of the assessment loop. Its draft validation is the gate that
makes "published settings are versioned" and "draft validation catches incomplete questions"
(ASM-01) true, and its server-side constraint storage is what plan 10-05 later enforces on upload
(ASM-03's "published constraints apply consistently to server validation").
Output: `assessment-readiness.ts`, `assessment-service.ts`, and two unit test files.
</objective>

    - QUIZ MULTI_CHOICE question with zero `isCorrect` options produces a blocking FAIL
    - QUIZ question with fewer than two options produces a blocking FAIL
    - QUIZ question with `marks` less than 1 produces a blocking FAIL
    - QUIZ where `totalMarks` is set and differs from the sum of question marks produces a blocking FAIL naming both figures

    - `passMark` null produces a non-blocking WARN (an ungraded-threshold assessment is allowed but worth surfacing)
    - `maxAttempts` less than 1 produces a blocking FAIL; `maxAttempts` null is treated as unlimited and passes
    - `attemptGradingMethod` is always present (schema default HIGHEST) so it never blocks; when `maxAttempts` is 1 it produces a non-blocking WARN stating the setting has no effect at a single attempt

    - ASSIGNMENT with `maxFileSizeBytes` null or less than 1 produces a blocking FAIL
    - ASSIGNMENT with blank `instructions` produces a blocking FAIL
    - `availableFrom` later than `availableUntil` produces a blocking FAIL (both types)
    - `dueAt` later than `availableUntil` produces a non-blocking WARN (D-03: the due date is informational, the window is the hard cutoff — a due date past the cutoff is confusing but not invalid)
    - A fully valid QUIZ and a fully valid ASSIGNMENT each produce zero blocking items
    - The evaluator never reads a database and never reads the clock

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff client → assessment authoring server action | Caller supplies `assessmentId`, question drafts, and settings values |
| application → database | `feedbackBehaviour` is a raw String column; Prisma enforces no closed set |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-07 | Elevation of Privilege | `assessment-service.ts` authoring actions | mitigate | Every write wraps in `withPermission` with `toScope: assessmentCourseScope`, which reads `courseId` from the row; a missing row yields `{}` and is denied. Unit test asserts a thrown `AuthorizationError` for a sibling course, not a silent filter |
| T-10-13 | Tampering | `feedbackBehaviour` | mitigate | Validated against the exported `FEEDBACK_BEHAVIOURS` allow-list before the write, because the Prisma column is a raw `String` with no database-level constraint (10-RESEARCH.md Anti-Patterns) |
| T-10-14 | Tampering | publish path | mitigate | `publishAssessment` calls the same pure evaluator the authoring UI renders; a blocking failure refuses the transition rather than partially publishing, so a client that skips the UI checklist cannot publish an incomplete Quiz |
| T-10-15 | Information Disclosure | Assessment read path | accept | Reads gate on `courses.view` because the closed catalogue has no `assessments.view`. A staff member who can view the Course can view its Assessments — acceptable because assessment content is course content, and the alternative (a new catalogue identifier) requires PRD §1.3 approval that is out of this phase's scope |
| T-10-SC | Tampering | npm installs | accept | No package installs in this plan |
</threat_model>
