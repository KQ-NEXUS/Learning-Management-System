<objective>
Build the learner Assignment submission pipeline (ASM-04) with the server-side enforcement of
ASM-03's authored constraints: presign a staged upload, verify the stored object, promote it, and
only then write a durable receipt.

Purpose: ASM-04's hard invariant is that "failures never display false success." The only way to make
that structurally true is the intent/complete two-step `lesson-resource-service.ts` already proved —
the row is written `READY` after `HeadObject` confirms the bytes, never on the browser's word.
Output: `submission-service.ts` and `tests/submission-service.test.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| learner client → submission server actions | Caller supplies `assessmentId`, filename, declared mime type and size |
| browser → object store | Direct presigned PUT; the file body never traverses the Next.js server |
| staged object → final object | Server-side promote only, after verification |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-02 | Information Disclosure | all submission functions | mitigate | Enrolment re-derived from `actor.userId`; no exported input carries an `enrolmentId`; `getOwnSubmissions` returns an empty list for a non-owner rather than revealing existence |
| T-10-06 | Tampering | staged upload URL | mitigate | The staged key embeds `randomUUID()` and lives under `submission-uploads/`; `finalSubmissionKeyFor` is the only path to `submissions/` and it runs server-side after verification, so a leaked write URL cannot overwrite another learner's final object |
| T-10-18 | Tampering | declared size / mime type | mitigate | `inspectLessonObject` compares the stored object's real size and content type against the declared values before promote; a mismatch marks the row ERROR and refuses, so a client cannot smuggle an oversized or wrong-typed object past the authored constraints |
| T-10-19 | Repudiation | false-success receipt | mitigate | `receiptId` is not returned from the intent step at all, and `uploadStatus: "READY"` is written only after a successful `promote`. Three unit cases assert `promote` was never called on each failure branch (10-RESEARCH.md Pitfall 3) |
| T-10-20 | Information Disclosure | staged-object download | mitigate | `getOwnSubmissionDownloadUrl` refuses unless `uploadStatus === "READY"`, so only the promoted final key is ever presigned for GET |
| T-10-SC | Tampering | npm installs | accept | No package installs in this plan |
</threat_model>
