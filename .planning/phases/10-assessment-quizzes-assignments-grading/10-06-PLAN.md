    Preconditions: load the attempt, ownership-compare its enrolment's user to `actor.userId`, refuse

    Merge the supplied `responses` into the stored payload using the same discard rules

    1. Update the `Attempt` to `status: "SUBMITTED"`, `submittedAt: now()`, `score`, `maxScore`,
       `passed`, and the merged payload written back to `answers` (the `questionSnapshot`, `passMark`
       and `totalMarks` keys stay byte-identical — only `responses` changes).
    2. Create the `Grade` row with `assessmentId`, `enrolmentId`, `attemptId`, `score`, `maxScore`,

       there is no human judgment call to make on an objectively-scored attempt. `gradedById` and
       `releasedById` are null because no staff member acted — add a comment saying so explicitly, so a
       future reader does not mistake the nulls for a bug.
    3. Write two domain events with the caller's tx: `attempt.submitted` (payload: attemptId,
       assessmentId, enrolmentId, attemptNumber, status) and `grade.released` (payload: gradeId,
       assessmentId, enrolmentId, attemptId, score, maxScore, passed, plus a marker distinguishing
       this automatic release from a staff release, e.g. `releasedBy: "SYSTEM_AUTO"`). Phase 11 and
       Phase 13 both drain `grade.released`; the marker is what lets them tell an auto-release from a
       staff one without a second event type.

    `targetType: "Attempt"`, `targetId: attemptId`, `actorId: actor.userId`, `outcome: "SUCCESS"`,

    action is the trigger — so unlike the Stripe webhook's actorless system writes, this audits with a
    real actor id. 10-RESEARCH.md Pitfall 4 is explicit that the audit trail must not be skipped just
    because no staff member clicked release.

    including each question's `correctOptionIds` and `explanation` so plan 10-11's post-submit review
    render needs no second query. Set `expired: false` here; Task 2's expiry path sets it true.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| learner client → submit action | Caller supplies raw option selections only |
| frozen snapshot → scoring | The only input to the score; live rows are never consulted |
| scoring → Grade visibility | An auto-released quiz grade is immediately learner-visible |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-01 | Tampering | `submitAttempt` input | mitigate | The input type carries only `attemptId` and `responses`; `score`/`passed` are not representable, and the score is always recomputed by `scoreAttempt` from the stored snapshot |
| T-10-08 | Tampering | retroactive question edit | mitigate | Scoring never queries `QuizQuestion`; the real-Postgres integration case mutates live option rows between start and submit and asserts the score follows the frozen snapshot |
| T-10-21 | Repudiation | auto-release with no staff actor | mitigate | The submit path writes an `AuditEvent` with the learner as `actorId` and both `attempt.submitted` and `grade.released` outbox rows inside the same transaction, so an automatically released grade is as traceable as a staff-released one (10-RESEARCH.md Pitfall 4) |
| T-10-11 | Elevation of Privilege | attempt-limit bypass | mitigate | The non-abandoned attempt count is enforced server-side with the composite unique constraint as the race backstop; the integration suite exercises both the refusal and the legitimate second attempt |
| T-10-22 | Information Disclosure | answer-key leakage before submit | mitigate | `AttemptResultView`'s `correctOptionIds` and `explanation` are populated only on the post-submit/expired result path; the in-progress read path returns the snapshot without correctness fields (verified again at the UI layer in plan 10-11) |
| T-10-SC | Tampering | npm installs | accept | No package installs in this plan |
</threat_model>
