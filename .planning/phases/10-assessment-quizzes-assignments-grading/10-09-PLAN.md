<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff client → override action | Caller supplies `gradeId`, a new score and a reason string |
| database Grade rows → learner payload | Only `RELEASED` rows may cross |
| learner client → results read | Caller identity is the only trusted input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-05 | Repudiation | `overrideGrade` | mitigate | The reason is trimmed and length-checked server-side before any write; the `GradeOverride` row plus an independent audit row both preserve original value, revised value, actor and time. `grading-service.ts`'s `saveDraftGrade` refuses RELEASED grades, so this is the only route to changing a released score |
| T-10-26 | Tampering | D-07 boundary | mitigate | `GradeNotReleasedError` is thrown before any write for a DRAFT grade — the simpler override-for-everything path is explicitly rejected, with a unit case asserting zero writes |
| T-10-04 | Information Disclosure | `getOwnResults` | mitigate | `status: "RELEASED"` is a database-level `where` clause, so a draft score never enters the RSC payload; the unit case asserts on the serialised result rather than a single field |
| T-10-02 | Information Disclosure | learner read paths | mitigate | The enrolment is re-derived from `actor.userId`; a non-matching request returns an empty array rather than a distinguishable error |
| T-10-03 | Elevation of Privilege | `overrideGrade` | mitigate | Scope resolves through `enrolmentCohortScope` on the grade's own `enrolmentId`; a grant for another Cohort throws `AuthorizationError` |
| T-10-27 | Information Disclosure | override attribution | mitigate | Only the overriding actor's display name is returned to the learner, never their email address |
| T-10-SC | Tampering | npm installs | accept | No package installs in this plan |
</threat_model>
