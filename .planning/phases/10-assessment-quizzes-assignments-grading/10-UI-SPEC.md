# Phase 10 — UI Design Contract

> Visual and interaction contract for Assessment — Quizzes, Assignments & Grading. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This phase renders entirely on top of the
> approved Phase 04.1 design system (`src/app/globals.css` token chain, the four hand-rolled
> primitives, `StaffShell`, `LearnerShell`) and directly replaces `LessonContent`'s existing
> `QUIZ`/`ASSIGNMENT` `Placeholder` branch (Phase 4's own doc comment: "assessment authoring and
> delivery arrive in Phase 10"). **No token, primitive, or shell change is proposed here.** Where
> this document states a value, it is either **inherited** (traced to `04.1-UI-SPEC.md`, not
> re-litigated), **decided** (traced to a `10-CONTEXT.md`/`10-RESEARCH.md` D-number or Open
> Question), or **resolved this phase** (this document's own answer to a gap `10-CONTEXT.md` and
> `10-RESEARCH.md` both explicitly left to `/gsd:ui-phase 10`).

## 0. Grounding — Scope

### 0.1 What's new this phase

No `/staff/*/assessments`, `/staff/cohorts/[id]/grading`, or learner attempt/submission UI exists
on disk today (confirmed this session — `LessonContent.tsx`'s `QUIZ`/`ASSIGNMENT` branches render
only the inert `Placeholder` component). This document proposes the route shape the planner should
adopt, following the codebase's two already-established nesting conventions rather than inventing a
third:

| Route (proposed) | Status | Requirement | Purpose |
|---|---|---|---|
| `/staff/courses/[id]/assessments` | **New** | ASM-01, ASM-03 | Assessment list for this Course — `ResourceTable`, mirrors `/staff/courses/[id]/lessons` |
| `/staff/courses/[id]/assessments/new` | **New** | ASM-01, ASM-03 | Create Quiz or Assignment — `ResourceForm`, mirrors `/staff/courses/[id]/lessons/new` |
| `/staff/courses/[id]/assessments/[assessmentId]` | **New** | ASM-01, ASM-03 | Edit Assessment settings + question builder (Quiz) or constraints (Assignment); publish/version bump — mirrors `/staff/courses/[id]/lessons/[lessonId]` |
| `/staff/cohorts/[id]/grading` | **New** | ASM-05 | Per-Cohort grading landing — one row per Assessment in this Cohort's Course/Programme with pending/draft/released counts — a **new `DetailLayout` tab** ("Grading") on the existing Cohort detail page, alongside its existing Learners/Sessions/Exceptions tabs |
| `/staff/cohorts/[id]/grading/[assessmentId]` | **New** | ASM-05, ASM-06 | Submission queue for one Assessment within this Cohort — `ResourceTable` with the D-06 batch-release selection wired to a real action (see §7.2) |
| `/staff/cohorts/[id]/grading/[assessmentId]/[submissionId]` | **New** | ASM-05, ASM-06 | Grade-entry screen (`ResourceForm`-shaped) — score, feedback, save draft, release; override affordance on an already-released grade |
| `/learn/[enrolmentId]/lessons/[lessonId]` | **Extended** | ASM-01, ASM-02, ASM-04 | Existing Phase 9 lesson-reading pane — this phase replaces `LessonContent`'s `QUIZ`/`ASSIGNMENT` `Placeholder` with the real attempt-taking / submission UI (§7.3–7.4). No new route. |
| `/learn/[enrolmentId]/results` | **New** | ASM-07 | Full released-results list across every Assessment in this Enrolment's Course — fills Phase 9's named-gap "Results" dashboard slot (`09-UI-SPEC.md` §6.1) |

**Discretionary note (flagged for planner confirmation):** as with `09-UI-SPEC.md` §0.1, this
document mandates the *shape*, not the literal path strings — Assessment authoring nests under
Course (matching Lessons/`arrange`), grading nests under Cohort (matching Sessions/Exceptions/
Learners), and attempt/submission UI lives *inside* the existing lesson pane rather than a
separate route, because `Lesson.assessmentId` already ties a Quiz/Assignment to exactly one Lesson
slot in the ordered content — there is no independent "assessment page" outside a Lesson today, and
inventing one would fragment the sequencing/locking model Phase 9 already built.

### 0.2 Explicitly out of this contract

- **Certificate issuance/verification UI** — Phase 11. This phase only needs to produce trustworthy
  `Grade`/`Attempt` evidence; it does not render or link to a certificate.
- **Result-release notification/email UI** — Phase 13. This phase emits `DomainEvent` rows only.
- **Any change to `globals.css`, the four primitives' contracts, `StaffShell`/`LearnerShell`'s
  chrome, or `LessonContent`'s existing content-type switch beyond swapping in the two new
  branches** — this phase is a consumer of the 04.1 system, not a contributor to it.
- **A per-attempt countdown timer.** No `Assessment.timeLimit`-shaped field was found in the schema
  during research (only `availableFrom`/`availableUntil`/`dueAt`/`maxAttempts`) — this document
  does not invent a countdown UI unsupported by data. The only time-boxing this phase's UI shows is
  the `availableUntil` window (§7.3.4, §0.3).

### 0.3 Resolved this phase — the two flagged open UI items

Both `10-CONTEXT.md`'s Claude's Discretion and `10-RESEARCH.md`'s Open Question 4 name these as
genuinely UI-phase decisions. Resolved here, prescriptively:

**Quiz-attempt navigation: single page, not one-question-per-page.**
The attempt renders every question on one scrollable page inside a single `<form>`, submitted once
("Submit quiz" — see §7.3). Rationale: no stepper/wizard primitive exists anywhere in this codebase
(`ResourceForm` is single-submit by design); a paginated attempt would need new client state, new
per-page persistence, and a new a11y pattern (focus management across steps) that nothing else in
the app has proven; a single page keeps the "server always recomputes the score from a snapshot"
invariant (`10-RESEARCH.md` Pitfall 1) simple — one POST, one snapshot read, one scoring pass. A
sticky "Question N of M answered" counter (§7.3.1) gives orientation without a stepper. If a future
phase's real quiz lengths prove this wrong (very long quizzes), that is a re-litigation, not a gap
in this contract.

**`IN_PROGRESS` → `ABANDONED`/`EXPIRED`, evaluated lazily on read (no cron), with an explicit UI
contract for what the learner sees:**

| Trigger | New status | What the learner sees |
|---|---|---|
| An `IN_PROGRESS` `Attempt` is read (page load, resume) after `Assessment.availableUntil` has passed | `EXPIRED`, auto-submitted using whatever answers were saved, scored normally (D-01 auto-release still applies) | The attempt page shows an `AlertTriangle`-icon `--warning` banner: **"This assessment's availability window has closed. Your answers as submitted were scored automatically."** — then renders the scored result exactly as a normal `SUBMITTED` attempt (§7.3.5). Never a silent redirect; the learner is told why they're suddenly looking at a scored result they didn't explicitly submit. |
| An `IN_PROGRESS` `Attempt` exists with no `availableUntil` set (untimed) and the learner navigates away and back | Stays `IN_PROGRESS` | Resumes exactly where they left off, all previously-entered answers pre-filled — no timeout ever fires for an untimed quiz. |
| The learner starts a new Attempt while a previous one is still `IN_PROGRESS` (only reachable when `maxAttempts` allows another attempt) | The previous Attempt flips to `ABANDONED` at that moment | The "Start new attempt" action, when a prior `IN_PROGRESS` attempt exists, shows a plain-text (not `ConfirmModal`) inline notice beneath the button: **"Starting a new attempt will abandon your unfinished one — it won't be scored."** This is informational, not destructive-audit-sensitive (mirrors `09-UI-SPEC.md` §6's framing of learner self-undo as reversible-record, not an audited action) — a lightweight inline notice, never a `ConfirmModal`. |
| Attempt history list (`ABANDONED` row) | — | `StatusPill` `neutral` "Abandoned" — no score shown (`—`), distinguished from `SUBMITTED`'s scored pills. |
| Attempt history list (`EXPIRED` row) | — | Renders identically to a `SUBMITTED` row (it was scored) — `EXPIRED` is a *display-only* provenance note (see §7.3.5), never its own visual pill tone, since to the learner the outcome is "scored," not "failed to submit." |

## 4. Typography

Inherited from `04.1-UI-SPEC.md` §4.3's primitive/app-UI scale — this phase introduces **no new
size or weight**, staying within the locked 4-size, 2-weight cap.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 14px | 600 | 1.5 |
| Heading | 25px | 600 | 1.2 |
| Display | 16px | 600 | 1.3 |

Notes:
- **Heading (25px/600)** is the page `<h1>` — "{Assessment title}" (attempt page, submission page),
  "Grading — {Assessment title}", "Your results".
- **Display (16px/600)** fills the section-heading role — each quiz question's prompt text,
  grade-entry screen's "Score & feedback" section header, results-page per-Assessment card title.
- The score fraction ("14 / 20") and percentage renders at Label role (14px/600) matching the
  `09-UI-SPEC.md` §4 "countdown timer"/progress-percentage precedent (color/weight carries
  emphasis, not a bespoke size) — never a fifth type size.
- A quiz option's label text renders at Body role (14px/400); the selected/correct-after-release
  indicator (§7.3.5) uses `--success`/`--danger` color, never bold, to avoid conflating emphasis
  weight with correctness (correctness is a color+icon fact, not a typographic one).

## 5. Color

Inherited token values from `04.1-UI-SPEC.md` §5.3 — **no new hex, no new token.** This phase
reuses the teal progress role, the success/warning/danger semantic roles, and the accent role
exactly as already locked; no new color decision is introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--surface-2` (page ground) + `--foreground` ink | Page background and default text — `StaffShell`/`LearnerShell`'s existing ground, unchanged |
| Secondary (30%) | `--surface` white (cards) + `--border` (card/decorative edges) + `--muted-foreground` (hints, timestamps, question numbers) | Every question block, submission card, grade-entry fact panel |
| Accent (10%) | `--accent` brand blue `#2457d6` | Reserved for exactly: "Submit quiz" / "Submit assignment" / "Save draft" primary buttons, "Start new attempt" link, the active/current tab in `DetailLayout`'s new Grading tab, focus ring. **Never** used for a `StatusPill` tone, a correctness indicator, or the progress bar fill — same reservation list `09-UI-SPEC.md` §5 already locked, unchanged. |
| Destructive / second semantic | `--danger` / `--danger-surface` | Reserved for genuine failures only: upload/submission failure (`Submission.uploadStatus = ERROR`), "not passed" is **not** rendered in this tone (see below) — a missed pass threshold is informational, not an error, mirroring `09-UI-SPEC.md` §5's "a lock is an expected, navigable state, not a failure" principle applied here to "not yet passed" |
| `--teal-fill` / `--teal-text` | `#12a594` / `#0f766e` | **Not drawn by this phase.** Teal is reserved for lesson/course *completion* progress (09's role); a quiz score is a different kind of number (a mark, not a completion fraction) and uses plain `--foreground`/Label weight instead — drawing teal here would blur the "teal = completion progress" convention 09 established |
| `--success` `#15803d` | Via `StatusPill`'s green tone | "Passed" quiz result, "Released" grade status, `Submission.uploadStatus = READY` |
| `--warning` `#b45309` / `--warning-surface` | Via `StatusPill`'s amber tone / banner backgrounds | "Not passed" quiz result (informational, not an error — see above), "Late" submission flag, "Draft" grade... **no** — "Draft" uses `neutral` (see below), amber is reserved for "not yet passed"/"late"/the `EXPIRED`-window banner (§0.3) |
| `neutral` (grey pill tone) | `--pill-grey-*` | "Draft" grade status (unreleased — deliberately the *least* visually alarming tone, since a draft grade is a normal in-progress work state, not a warning), "Abandoned" attempt status |
| `accent` (blue pill tone) | `--pill-blue-*` | "In progress" attempt status only — distinct from the brand-blue `--accent` role above (this is `StatusPill`'s own blue tint, the same one Phase 9 reserved for "Active" enrolment) |

**Grade override visual rule (D-07):** the "Override grade" action (`RotateCcw` icon) is **only
ever rendered on a `RELEASED` grade** — never on a `DRAFT` one. This is a rendering-contract
requirement, not just a server-side check: a grading UI that shows the mandatory-reason override
flow on a `DRAFT` row is itself a spec violation (`10-RESEARCH.md` Pitfall 5's own "warning sign").
A `DRAFT` grade's only action is the ordinary "Save" button inside `ResourceForm`.

## 7. Screens & States — Interaction Detail

### 7.0 Staff nav — no new top-level item

`StaffShell`'s `NAV` array (`src/app/staff/layout.tsx`) is **not** extended with a "Grading" entry.
Grading is reached via the existing Cohort detail page's new "Grading" tab (§0.1) — consistent with
how Sessions/Exceptions/Learners are already Cohort-scoped sub-views rather than top-level nav
items. Assessment authoring is reached via the Course detail page (a new "Assessments" link
alongside the existing "Lessons"/"Arrange" actions on `/staff/courses/[id]`), matching the existing
Course-detail actions surface (`CourseDetailActions.tsx`). This keeps the top-level nav's item count
unchanged (D-20's "nothing here promises a page the product cannot open" applies in reverse too —
no clutter for a capability reachable one click deeper).

### 7.1 Assessment authoring (`/staff/courses/[id]/assessments`, `/new`, `/[assessmentId]`)

- **List** (`ResourceTable`, Course-scoped) — columns: Title, Type (`ListChecks`/`ClipboardList`
  icon + "Quiz"/"Assignment" text, not a `StatusPill` — type is a fixed fact, not a state),
  Status (`StatusPill`: `neutral` "Draft" / `success` "Published"), Version (mono, right-aligned).
  No delete affordance — archive replaces it, matching CAT-08's precedent (`selection.actions`
  offers "Archive…" only, disabled/no-op until the planner wires it, mirroring `CoursesTable.tsx`'s
  own still-open Archive action rather than inventing a second unimplemented pattern).
- **Create/Edit form** (`ResourceForm`) — Quiz and Assignment share the same route shape but render
  different field groups below a shared header block (title, instructions, `availableFrom`/
  `availableUntil`):
  - **Quiz fields**: `maxAttempts`, `passMark`, `totalMarks` (derived/read-only once questions are
    added — shown as a `DetailFacts` fact, not an editable `TextInput`, since it's a sum), `attemptGradingMethod`
    (segmented control matching `ResourceTable`'s existing ≤4-option segmented-filter pattern:
    Highest / Latest / Average), `feedbackBehaviour` (select, validated against the explicit
    allow-list per `10-RESEARCH.md`'s Anti-Pattern note). A nested question builder (add/reorder/
    edit `QuizQuestion`+`QuizOption` rows) reuses `ArrangeBoard`'s drag/keyboard-reorder precedent
    from Phase 4 rather than inventing a new list-builder interaction.
  - **Assignment fields**: `dueAt`, `allowedFileTypes` (multi-select chips, not a free-text field —
    validated against a closed extension list, mirroring `UploadPanel`'s `FRIENDLY_LIMIT_MESSAGES`
    precedent), `maxFileSizeBytes` (numeric input with a human-readable hint, e.g. "50 MB"),
    grading scale (numeric `totalMarks` + `passMark`), `allowResubmission` (checkbox, 16px/
    1.5px-border restyled native control per 04.1 §7.3's "restyle a native control, don't invent a
    custom widget" precedent).
  - **Draft validation** (ASM-01) — follows `readiness-service.ts`'s pure-evaluator shape
    (`10-RESEARCH.md` Code Examples): incomplete questions, a `passMark` exceeding `totalMarks`, or
    a missing `attemptGradingMethod` at publish time surface in `ResourceForm`'s existing error
    summary (no new error-display pattern) — publish stays blocked, matching CAT-05's readiness-gate
    precedent, never a silent partial-publish.

### 7.2 Grading (`/staff/cohorts/[id]/grading`, `/[assessmentId]`, `/[submissionId]`)

#### 7.2.0 Cohort Grading tab (landing)

New `DetailLayout` tab on the existing Cohort detail page. Content: a compact list (not a full
`ResourceTable` — this is a summary, not a filterable collection) of Assessments belonging to this
Cohort's Course/Programme, each row showing "{Assessment title} — {pendingCount} pending ·
{draftCount} draft · {releasedCount} released", linking to `/staff/cohorts/[id]/grading/
[assessmentId]`. **Quiz assessments never appear here** — D-01's auto-release means a quiz never
has a `DRAFT`-status Grade a human needs to act on; this tab lists **Assignment-type Assessments
only**. (If a Quiz's *attempt* needs human review for any reason, that is out of this phase's
scope — no such need is named in any requirement.)

#### 7.2.1 Submission queue (`/staff/cohorts/[id]/grading/[assessmentId]`)

`ResourceTable`, Cohort+Assessment-scoped. **Cohort-scope banner (D-05)** renders above the table,
reusing the exact visual language `ResourceTable`'s own "N selected" bar already establishes
(`rounded-md border border-accent/30 bg-accent/5 px-4 py-2`) so it reads as part of the same visual
system, not a bespoke component: `GraduationCap` icon + "Grading: {Cohort name} · {Assessment
title}" in `--accent`-colored Label-weight text. This is the D-05 requirement made "visually
obvious" — a grader can never lose track of which Cohort's submissions they're looking at, because
the banner is present on every render of this route, not just an initial toast.

Columns: Learner name, Submitted (timestamp, mono), Late (`StatusPill warning` "Late" or blank —
conditional fact, no placeholder when on-time, per the established `06-UI-SPEC.md` §7.2
convention), Status (`StatusPill`: `neutral` "Draft" / `success` "Released"), Score (mono,
right-aligned, `—` until graded).

#### 7.2.2 Filters

`status` filter (segmented: "All" / "Draft" / "Released" — ≤4 options, uses `ResourceTable`'s
existing segmented-filter auto-activation, no new filter UI). No search filter — a Cohort's
submission volume for one Assessment is expected to be small (matches the roster-scale assumption
`09-UI-SPEC.md` §7.4 already made for sessions).

#### 7.2.3 Batch release (D-06) — the first real bulk-select action

`selection.actions` gains exactly one **enabled** entry: `{ label: "Release selected", onClick,
disabled: <true only when the selection contains zero DRAFT-status rows> }`. Clicking it opens
`ConfirmModal` (`tone="default"`, no `minReasonLength`, copy per §6): **"Release {N} grades"**.
Confirming calls one server action taking the selected Grade ids, executed as one
`prisma.$transaction` per `10-RESEARCH.md` Pattern 4 (one round trip, one audit/DomainEvent batch,
never N client-dispatched calls — Next.js 16.3.4 serializes those). On success, the modal closes,
the table re-renders with those rows now `success` "Released" (read-your-own-write via the existing
`revalidatePath`/`updateTag` convention, no follow-up client fetch), and the selection clears.
Already-released rows included in a stale selection are silently skipped server-side (never
double-released) — the UI does not need to pre-filter them client-side, since the server's skip is
the actual safety boundary (`10-RESEARCH.md` Pattern 4's code example).

#### 7.2.4 Grade-entry screen (`/staff/cohorts/[id]/grading/[assessmentId]/[submissionId]`)

`DetailLayout`, stacked mode (this is a focused read-then-act task, not a tabbed record — mirrors
`06-UI-SPEC.md`'s checkout-summary precedent for single-purpose screens). Two zones:

- **Read-only context** (`DetailFacts`): Learner name, submitted timestamp, `isLate` flag,
  attempt number (D-04's resubmission history — a `DetailFacts` row per prior `Submission` row for
  this Enrolment+Assessment, most recent first, each linking its file), file download link
  (reusing the existing presigned-URL download convention, `FileText` icon per 09's inventory).
- **Editable** (`ResourceForm`): Score (`TextInput` type="number", hint "out of {totalMarks}"),
  Feedback (`textarea`, matches `ConfirmModal`'s reason-field sizing convention — `rows={3}`
  minimum). Buttons: "Save draft" (`BTN` secondary style) always available while `status = DRAFT`;
  "Release" (`BTN_PRIMARY`) available once a score is entered. Once `status = RELEASED`, both
  buttons are replaced by a read-only fact display of score/feedback plus the single "Override
  grade" (`RotateCcw` icon) action, which opens `ConfirmModal` with `minReasonLength={10}` per §2/
  §5's D-07 rendering rule — **never both a Save button and an Override button visible at once**,
  since that would let staff bypass the mandatory-reason path by just re-saving (`10-RESEARCH.md`
  Pitfall 5's exact warning sign).
- **Named-gap fact** (§6.2): "Certificate impact — not yet evaluated (arriving in a future
  update)" renders in the read-only zone once a grade is `RELEASED`.

### 7.3 Quiz attempt (inside `/learn/[enrolmentId]/lessons/[lessonId]`, replaces `Placeholder`)

Single scrollable page inside the existing `LessonContent` slot, `max-w-2xl` matching
`LessonContent`'s own existing prose width (§0.1 — no narrower override).

#### 7.3.1 Pre-attempt state

Assessment title (Heading role), instructions/description (Body role), a `DetailFacts`-style
summary row (max attempts, remaining attempts, pass mark, time window if `availableUntil` is set —
`Clock` icon), and the "Start quiz" / "Start new attempt" button (§6). If a prior `IN_PROGRESS`
attempt exists, the button reads "Resume attempt" instead and the abandon notice (§0.3) does not
render (resuming ≠ starting a competing attempt).

#### 7.3.2 In-progress state

Every question renders in order inside one `<form>`: question number + prompt (Display role),
marks value (muted, "{N} marks"), then its options — `SINGLE_CHOICE`/`TRUE_FALSE` as native radio
groups, `MULTI_CHOICE` as native checkboxes — each option a Body-role label with a 16px/1.5px-border
restyled native control (04.1 §7.3 precedent, same as the assignment `allowResubmission` checkbox).
A sticky counter ("{answeredCount} of {totalQuestions} answered", §6.1) pins to the top of the
viewport on scroll (`sticky top-0`, matching no existing precedent exactly but structurally
identical to `StaffShell`'s own `lg:sticky` sidebar — the same CSS mechanism, not a new pattern).
"Submit quiz" (`BTN_PRIMARY`, disabled until every question has at least one answer — mirrors
`ConfirmModal`'s "disabled until valid, not error-after-the-fact" philosophy) sits at the page
bottom.

#### 7.3.3 Submit — client behavior

The submit payload contains **only the learner's raw selections** (`10-RESEARCH.md` Pitfall 1) —
never a client-computed score. `ResourceForm`'s existing pending-button convention
("Submitting…" + disabled) covers the in-flight state; no new loading pattern.

#### 7.3.4 `availableUntil` passed before starting

If the window has already closed before an attempt is even started, the pre-attempt state (§7.3.1)
replaces its "Start quiz" button with the same `AlertTriangle`/`--warning` treatment as the
assignment's hard-cutoff state (§6.1) — **"The window for this assessment has closed."** No attempt
is created at all in this case (distinct from §0.3's mid-attempt expiry, which scores whatever was
saved).

#### 7.3.5 Result state (post-submit, D-01 auto-release)

Renders in place of the attempt form immediately (D-01 — no waiting screen, no "pending grading"
state for a quiz). Score line + pass/not-pass pill (§6.1), then each question re-rendered read-only
with the learner's answer marked and, if `feedbackBehaviour` permits, the correct answer indicated
(`--success` check / `--danger` cross **only here**, post-release — never during the in-progress
state, which would leak answers). "Start new attempt" renders beneath if `maxAttempts` allows
another; otherwise "You've used all {maxAttempts} of your attempts for this quiz." (§6.1). An
`EXPIRED`-provenance attempt shows the §0.3 banner above this same result layout — no separate
result template for expired vs. normally-submitted.

### 7.4 Assignment submission (inside `/learn/[enrolmentId]/lessons/[lessonId]`, replaces `Placeholder`)

Single page inside the existing `LessonContent` slot, same `max-w-2xl` width.

#### 7.4.1 Pre-submit state

Assessment title, instructions (rendered exactly as authored, sanitized), due date (§6.1, `Clock`
icon, never `--danger`), allowed file types/size hint, then a file picker control reusing
`UploadPanel`'s visual states (`Upload` icon, drag-or-browse target, `statusPresentation`'s
`success`/`danger`/`neutral` `StatusPill` mapping for `UPLOADING`/`READY`/`ERROR` — §2). Once a file
is selected past `dueAt`, the "This submission will be marked late" notice (§6.1, `--warning`)
appears inline, never blocking the submit action (D-03 — accept and flag, never hard-block on due
date alone).

#### 7.4.2 Hard cutoff (`availableUntil`) passed

Replaces the entire submit control with the `AlertTriangle`/`--warning` "submission window has
closed" state (§6.1) — matches §7.3.4's quiz treatment exactly, since both read the same
`Assessment.availableUntil` field per `10-RESEARCH.md`'s Open Question 3 resolution.

#### 7.4.3 Receipt state (post-verified-upload, ASM-04)

Only rendered once the server has verified the object-store PUT (`HeadObjectCommand`, per
`10-RESEARCH.md` Pitfall 3 — never optimistic). `FileCheck` icon, "Submitted — receipt {receiptId}"
(§6.1), `StatusPill success` "Submitted" + `StatusPill warning` "Late" if applicable, file name/
size as `DetailFacts`. If `allowResubmission = true`, "Submit new version" reopens the file picker
(§7.4.1) and, on a fresh verified upload, creates a new `Submission` row per D-04 — the receipt
state then shows the **full submission history**, most recent first, each with its own receipt id
and (if released) its own grade — never overwriting the prior receipt's visible record.

#### 7.4.4 Upload failure

Reuses `UploadPanel`'s existing `danger`-tone failure copy shape but with this phase's own wording
(§6, "Your file couldn't be uploaded" / "Nothing was submitted") — the picker resets to its
pre-submit state, no partial/ambiguous receipt is ever shown (ASM-04's "failures never display
false success" is a rendering contract here, not just a backend one).

### 7.5 Learner results (`/learn/[enrolmentId]/results`)

Renders inside `LearnerShell`, single column, `max-width` matching the shell's content width (a
browsing/scanning view, same reasoning `09-UI-SPEC.md` §7.2 gave for the lesson-list page). One
card per Assessment the learner has attempted/submitted, ordered by course order (matching the
lesson-list's own ordering convention, not by date), each card showing:
- Assessment title (Display role), type icon (`ListChecks`/`ClipboardList`).
- Current result: score/pass-pill for a quiz (§6.1), status/score for a released assignment grade,
  feedback text if present.
- **Attempt/submission history** — expandable list of every prior `Attempt`/`Submission`, each with
  its own timestamp, status pill, and score (matching the grade-entry screen's §7.2.4 history
  pattern, reused here read-only).
- **Unmet pass requirement** (ASM-07's explicit acceptance wording) — the §6.1 "You haven't yet
  passed… N attempt(s) remaining" / "used all your attempts" copy, rendered only when relevant
  (never for an already-passed Assessment).
- **Draft grades never appear here at all** — not as a "pending" placeholder, not as a muted row,
  nothing. A `DRAFT`-status Grade simply has no representation on this page until it becomes
  `RELEASED` (ASM-05's "learners cannot see draft grades" is a hard content-filter, not a visual
  dimming choice — the server-side read this page uses must already exclude `DRAFT` rows entirely,
  per `10-RESEARCH.md` Pattern 3's ownership-scoped `getOwnX` shape).
