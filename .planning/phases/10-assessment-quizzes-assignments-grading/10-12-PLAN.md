    Create `grading-actions.ts` in `src/app/staff/cohorts/[id]/` with `"use server"` and one exported
    action `releaseGradesBatchAction({ cohortId, gradeIds })`. It parses input with `zod` — `gradeIds`
    a non-empty array of strings capped at the service's `MAX_BATCH_RELEASE` — then delegates to
    `releaseGradesBatch`. It calls the service ONCE with the whole array; it must never loop calling a
    single-release action, because Next.js 16.3.4 dispatches Server Actions sequentially per client
    and N calls would be N round trips AND N fragmented audit/outbox entries for one user action. It
    catches `AuthorizationError` and returns it as a form-level error rather than a 500, and after
    success calls the current-model revalidation API from inside the action so the same response
    carries the re-rendered table. No `@prisma/client` import.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff browser → grading actions | The selected grade-id array and the `cohortId` path parameter cross here |
| grader identity → cohort visibility | A grader must never see or act on another Cohort's submissions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-03 | Elevation of Privilege | queue routes and batch action | mitigate | All reads and the batch write go through plan 10-07's `withPermission`-wrapped, `enrolmentCohortScope`-resolved service; route files import no `@prisma/client`, enforced by an AST assertion |
| T-10-09 | Elevation of Privilege | batch selection | mitigate | The server resolves every supplied grade id's scope and rejects a cross-cohort batch whole; the client never pre-filters, so there is exactly one place the rule lives |
| T-10-30 | Information Disclosure | grader losing Cohort context | mitigate | The Cohort-scope banner renders on every render of the queue route, not as a transient toast, so a grader cannot mistake one Cohort's queue for another's |
| T-10-24 | Denial of Service | oversized batch | mitigate | `zod` caps `gradeIds` at `MAX_BATCH_RELEASE` before the service is called, and the service enforces the same cap independently |
| T-10-31 | Tampering | double release | mitigate | Already-released rows in a stale selection are skipped server-side and reported in `skipped`; the UI deliberately does not duplicate that check client-side |
| T-10-SC | Tampering | npm installs | accept | No package installs |
</threat_model>
