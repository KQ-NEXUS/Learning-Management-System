<objective>
Build the grader-facing half of ASM-05: a Cohort-scoped submission queue, draft grade saving that is
invisible to learners, explicit attributed release, and D-06's batch release as one server-side

learners cannot see draft grades, and release is explicit and attributed. Each needs a distinct
server-side mechanism, and D-06's batch variant needs to be one transaction because Next.js 16.3.4

    `releaseGrade(input: { gradeId })`, wrapped in
    `withPermission("grades.manage", async (input) => enrolmentCohortScope(<the grade's own enrolmentId>))`.
    Refuse unless the grade's current `status` is `DRAFT` (a second release is a no-op returning the
    existing row, never a duplicate event). Inside one transaction set `status: "RELEASED"`,
    `releasedById: ctx.actor.userId`, `releasedAt: now()`, and write a `grade.released` domain event
    carrying `gradeId`, `assessmentId`, `enrolmentId`, `submissionId`, `score`, `maxScore`, `passed`
    and a `releasedBy: "STAFF"` marker distinguishing it from plan 10-06's `SYSTEM_AUTO` automatic
    quiz release. Audit with action `grade.released`, `actorId: ctx.actor.userId`, before/after
    carrying status and the release attribution. ASM-05's "release is explicit and attributed" is
    exactly these two fields plus this audit row.

    `releaseGradesBatch(input: { gradeIds: string[] })` — D-06. This MUST be a single server action
    over an array of ids executed in one `prisma.$transaction`, not N client-dispatched calls: Next.js
    16.3.4 serialises Server Actions per client, so N calls would be slow AND would fragment the audit
    and outbox trail into N entries for what the user experienced as one action.

    Authorization shape: resolve the scope of EVERY supplied grade id before any write. Read all the
    grades' `enrolmentId` values, resolve each through `enrolmentCohortScope`, and require that a
    single scope covers all of them — if the selection spans cohorts the actor's grant does not cover,
    reject the WHOLE batch with an `AuthorizationError` rather than partially releasing the covered
    subset. A partial success here would be a silent scope leak dressed up as a convenience. Implement
    this by resolving to the common scope in the `withPermission` scope-resolver argument, exactly as
    10-RESEARCH.md's Pattern 4 example sketches.

    Inside the transaction, for each id: read the grade, SKIP it (do not throw) when its status is not
    `DRAFT` — a stale client selection containing an already-released row must never double-release,
    and the server-side skip is the real safety boundary, not a client-side pre-filter. For each row
    actually released, write the same fields and the same `grade.released` event as `releaseGrade`,
    with the caller's tx. Return `{ released, skipped }` id arrays so the UI can report accurately.

    After the transaction, write one audit entry per released grade (all of them written together,
    inside or immediately after the one transaction) so the audit export (RPT-05) sees the same
    per-grade granularity a single release produces, plus one batch-level entry with action
    `grade.released_batch` carrying the released and skipped counts. Factor the per-grade release body
    so `releaseGrade` and `releaseGradesBatch` share it and cannot drift.

    Cap the batch size at a documented constant (e.g. 200 ids) and refuse a larger request, so one
    request cannot hold a long transaction open indefinitely.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff client → grading server actions | Caller supplies submission ids, grade ids, scores and feedback |
| grade status → learner visibility | A DRAFT grade must be invisible to the learner and to the outbox; RELEASED is visible |
| batch selection → authorization | A client-supplied array of ids could span cohorts |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-03 | Elevation of Privilege | every grading action | mitigate | Scope resolves through `enrolmentCohortScope` on the row's own `enrolmentId`, never a caller-asserted cohort id; cross-cohort access throws `AuthorizationError` rather than filtering. Reused unmodified from the existing resolver so the T-05-07/T-05-08 mitigations are inherited, not reimplemented |
| T-10-09 | Elevation of Privilege | `releaseGradesBatch` | mitigate | Every supplied grade id's scope is resolved before any write; a selection spanning cohorts outside the grant rejects the WHOLE batch. A unit case asserts no grade changed status on that path. Batch size is capped at a documented constant |
| T-10-04 | Information Disclosure | draft grades | mitigate | `saveDraftGrade` writes no domain event and leaves `releasedAt`/`releasedById` null; plan 10-09's learner read path filters on `status: "RELEASED"`. A unit case asserts zero outbox rows for a draft save |
| T-10-05 | Repudiation | mandatory-reason bypass | mitigate | `saveDraftGrade` throws `GradeAlreadyReleasedError` on a RELEASED grade, so the only route to changing a released score is plan 10-09's audited, reason-mandatory override. Plan 10-17 adds an executable invariant gate for this |
| T-10-23 | Information Disclosure | IDOR on `submissionId` / `gradeId` | mitigate | `getGradingDetail`, `saveDraftGrade` and `releaseGrade` resolve scope by first reading the target row, so an id from another cohort produces a denial rather than a read |
| T-10-24 | Denial of Service | unbounded batch | mitigate | `MAX_BATCH_RELEASE` caps the id array, so a single request cannot hold a long write transaction open |
| T-10-SC | Tampering | npm installs | accept | No package installs in this plan |
