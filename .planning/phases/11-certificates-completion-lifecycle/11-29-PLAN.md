<objective>
Fix the renderer half of CR-01 and both halves of CR-02.

CR-01 (reproduced): the renderer embeds only `StandardFonts.Helvetica` (WinAnsi); `widthOfTextAtSize` and `drawText` throw for Yoruba ọ/ṣ/ẹ, Ł, Cyrillic, CJK, Arabic and any `\n`. This plan swaps in the human-approved bundled font (plan 11-26) via the already-installed `@pdf-lib/fontkit`, subset per document, and adds a sanitiser so no text can ever abort a render. Decoupling a render failure from the caller's write is plan 11-30/11-31; this plan makes the failure much rarer and makes it correct for real-world names.

CR-02: the template asset allow-list accepts WebP and GIF but the renderer embeds only PNG and JPEG, so one such logo breaks every issuance from that template. Reconcile both sides: restrict template assets to PNG and JPEG (the "restricting asset types" part, explicitly in scope) and guard the renderer so an undecodable image is skipped rather than fatal. An asset the resolver cannot FETCH (missing object, storage outage) still throws: that is an operational, retryable failure, and after plan 11-30 it can no longer roll back a caller's write. Unsupported or corrupt image BYTES are permanent, so retrying can never succeed; skipping the image is the only outcome that lets the certificate exist.

Known limits recorded here, not fixed: complex-script shaping and combining-mark positioning (pdf-lib draws glyph advances only, no GPOS mark placement), so text is normalised to NFC first to use precomposed letters; CJK/Arabic/Hebrew need a fallback font (human accepted the limitation in plan 11-26). Existing templates that already reference WebP/GIF assets keep working (the image is skipped); the upload UI stops creating new ones. WR-03 (asset-key domain validation) stays out of scope.

Output: the Unicode renderer, the font loader with Next tracing, the image guard, the template-asset allow-list, and tests that fail against the current code.
</objective>
