<objective>
Fix the renderer half of CR-01. (CR-02, the image guard and template asset allow-list, moved to plan 11-34 in revision iteration 1 so it does not wait behind the blocking human font gate in plan 11-26; plan 11-34 runs first, in an earlier wave, because both plans edit certificate-pdf-renderer.ts.)

CR-01 (reproduced): the renderer embeds only `StandardFonts.Helvetica` (WinAnsi); `widthOfTextAtSize` and `drawText` throw for Yoruba ọ/ṣ/ẹ, Ł, Cyrillic, CJK, Arabic and any `\n`. This plan swaps in the human-approved bundled font (plan 11-26) via the already-installed `@pdf-lib/fontkit`, subset per document, and adds a sanitiser so no text can ever abort a render. Decoupling a render failure from the caller's write is plan 11-30/11-31; this plan makes the failure much rarer and makes it correct for real-world names.

Known limits recorded here, not fixed: complex-script shaping and combining-mark positioning (pdf-lib draws glyph advances only, no GPOS mark placement), so text is normalised to NFC first to use precomposed letters; CJK/Arabic/Hebrew need a fallback font (human accepted the limitation in plan 11-26).

Font filename single source of truth: plan 11-26 requires assets/fonts/certificate/README.md to record the exact .ttf filename on a `Filename:` line (with licence, source and SHA-256). The loader here exports a `CERTIFICATE_FONT_FILENAME` constant transcribed from that line, and a test in tests/certificate-pdf-unicode.test.ts parses the README `Filename:` line and asserts equality with the constant, so a wrong or drifted name fails in CI rather than at first render. The loader does NOT parse README.md at runtime (a documentation edit must never be able to break production rendering); README is the recorded value, the constant is its pinned copy.

Output: the Unicode renderer, the font loader with Next tracing, and tests that fail against the current code.
</objective>
