## 4. Accepted risks assessed

Only T-11-45 in this batch has disposition `accept`.

- **T-11-45 (a certificate failure breaking lesson completion for every learner).** Recorded rationale: "issuance runs in the same transaction by design (D-03); a rendering failure correctly rolls back the completion rather than leaving a half-completed state." That premise no longer holds: rendering and storing were moved out of the transaction (plans 11-30, 11-31), so a rendering or object-store failure, or a P2028 timeout caused by a large logo, can no longer roll back a learner's lesson-progress or a staff attendance write. The accepted risk has been converted into a mitigated one, and a stronger one than the plan accepted. Recommended record update: replace the rationale with "issuance is database-only inside the caller's transaction; the PDF is produced after commit or on demand".
  Residual worth knowing (not an OPEN threat, unchanged from plan time in kind): `issueCertificateForEnrolment` still throws on data-integrity faults inside the caller's transaction (missing Enrolment/Cohort/award/User, unreadable inserted row, `certificate-issuance-service.ts:294-296,309,341,387,448,436`), and the DB writes (row, enrolment update, audit, event) share the caller's transaction. A dangling `courseId`/template reference could therefore still fail a lesson completion. Typed non-error outcomes exist for the expected cases (`not-eligible`, `revoked-blocked`, `no-template`, `not-enabled`, `already-issued`).
  Outcome: CLOSED, recorded as superseded/reduced.

## 5. Advisories (not blockers, no open threat)

- **A-1 (T-11-63): queue scope is authorization-only.** `computePendingIssuance` ignores `input.scope`. Today the only caller passes none, so only GLOBAL `certificates.view` holders reach it and cohort-scoped staff get a 404. If someone later passes a cohort/course scope to `listPendingIssuance`, the permission check would pass for a scoped grant and return every cohort's learner names. Add a scope filter or a test asserting a cohort-scoped grant is denied.
- **A-2 (T-11-47): Reissue on an ACTIVE row needs only `certificates.issue`.** `reissueCertificate` (`certificate-service.ts:642-665`) accepts an ACTIVE row (`status in ACTIVE, REVOKED`) and supersedes it, which makes the old reference verify as "revoked" publicly and withdraws the learner's download of it, without `certificates.revoke`. The plan specified the `certificates.issue` gate and the UI only offers Reissue on revoked rows, and a valid replacement is issued with a mandatory reason and an audit row, so I did not count this as open. The server action does not enforce the UI's restriction.
- **A-3: Invariant 1 timing.** `tests/certificate-phase-invariants.test.ts` invariant 1 walks and parses every file under `src/` with the TypeScript compiler and takes about 7.5 s under a parallel run against the 5 s default timeout, so it can fail intermittently. A gate that flakes tends to get skipped or removed; give it an explicit timeout.
- **A-4: evidence claims without tests.** Plan 11-15 promises a test that the server action's schema rejects a 9-character reason (T-11-49) and a test header asserts it; no such test exists. Plan 11-12's promised denial pin for `certificates.manage` on the asset actions (T-11-56) is also not tested because `withPermission` is mocked as always-allow. Both controls are present in code.
