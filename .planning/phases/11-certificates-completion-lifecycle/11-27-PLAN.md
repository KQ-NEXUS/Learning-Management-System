<objective>
Close CR-06 with an additive migration, and record CR-05 as a deliberately deferred limitation.

CR-06: `enrolment_one_active_per_learner_cohort` is `UNIQUE (userId, cohortId) WHERE status = 'ACTIVE'`. Phase 11 makes issuance move an enrolment to COMPLETED, which frees that index. Staff or checkout can then create a second ACTIVE enrolment for the same learner and cohort. A later revoke or CRD-06 flag tries COMPLETED to ACTIVE on the first enrolment and violates the index (P2002): `revokeCertificate` fails permanently, and `flagCertificateForReview` running inside a learner's lesson-progress or a staff attendance transaction fails that write. The phase 9 header in completion-service.ts and learning-phase-invariants.test.ts explicitly warned about this.

User decision (fixed): widen the index to also cover COMPLETED, by migration, checking first for rows that would violate it and handling that explicitly. Handling chosen: the migration itself contains a preflight that ABORTS with a message naming the violating count and the diagnostic query, changing no data. Auto-resolving duplicates is refused because nothing in the data says which of two enrolments is the real one (that is a human/business call). The abort is safe because Postgres DDL is transactional.

Migration mechanics: create the new index FIRST, then drop the old one (no window without protection; if the create fails the old index is intact). The new index name `enrolment_one_live_per_learner_cohort` is used because the old name would lie; every P2002 translation in src/ is duck-typed on the code only (verified: no code matches on the index name).

CR-05 (user decision: DEFER): flags stay uncleared and no Clear-flag control is added (locked UAT decision). This plan only documents the limitation.

HARD SAFETY RULE for this plan: `.env` DATABASE_URL points at the remote Neon database. The executor must not run `prisma migrate dev`, `prisma migrate deploy`, `prisma db push` or `prisma db execute` from the shell, and must not export DATABASE_URL from `.env`. The migration is created by hand as a file; it is exercised only through `startTestDatabase()` (tests/support/pg.ts), which overrides DATABASE_URL with a Testcontainers URL. No schema.prisma change is needed (partial indexes are raw SQL) so `prisma generate` is not required.

Output: the migration file, a real-Postgres test, comment updates, and the CR-05 record.
</objective>
