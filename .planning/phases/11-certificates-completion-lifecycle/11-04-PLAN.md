  <behavior>
    - Given a layout with one `text` element whose `field` is `learnerName`, and fields `{ learnerName: "Amara Okafor", ... }`, the produced PDF's extracted text contains `Amara Okafor` and does not contain the literal string `learnerName`.
    - The same holds independently for `awardTitle`, `issuedAt`, and `verificationRef`.
    - A `text` element with `field: "literal"` renders its `literal` string verbatim.
    - `EMPTY_LAYOUT_V1` renders a valid single-page PDF with no elements (no throw).
    - `orientation: "portrait"` and `orientation: "landscape"` produce pages whose width/height are swapped relative to each other for the same `pageSize`.
    - `pageSize: "LETTER"` produces different page dimensions from `pageSize: "A4"`.
    - A `border` element produces a PDF whose byte length exceeds that of the same layout with the border removed (proof it was drawn, not skipped).
    - An `image` element with an `assetKey` whose bytes are supplied by the caller's resolver embeds that image; an `assetKey` the resolver cannot resolve causes the render to throw rather than silently emit a certificate with a missing logo.
    - The produced value's first four bytes are the `%PDF` magic header.
  </behavior>
  <action>
    Create `src/server/services/certificate-pdf-renderer.ts` exporting:

    `renderCertificatePdf(input: { layout: CertificateTemplateLayoutV1; fields: CertificateRenderFields; resolveAsset: (assetKey: string) => Promise<Uint8Array>; }): Promise<Uint8Array>`

    where `CertificateRenderFields = { learnerName: string; awardTitle: string; issuedAt: Date; verificationRef: string }`
    — exactly the four fields the `Certificate` model already stores, and nothing more. Do not add a QR
    field: the QR dynamic-field element is a deferred discretion item and `certificate-template-layout.ts`
    has no `"qr"` element kind to render.

    Implementation requirements:
    - Import the PDF library only in this file. No other file in `src/` may import it; plan 11-16's
      invariants test will assert that mechanically.
    - Map `pageSize`/`orientation` onto concrete point dimensions (A4 = 595.28 × 841.89pt, LETTER =
      612 × 792pt; landscape swaps them). Define these as named constants, not inline magic numbers.
    - Iterate `layout.elements` in array order so later elements draw over earlier ones — the editor's
      z-order is array order, and 11-12's canvas must render the same way.
    - For `kind: "text"`, resolve the value: `literal` for `field: "literal"`, otherwise the matching
      `fields` entry. Format `issuedAt` with a single named formatter function exported from this module
      so the editor's sample-value preview (11-12) can call the identical formatter and staff see the
      same date shape they will get.
    - For `kind: "image"`, `await resolveAsset(element.assetKey)` and embed. Injecting the resolver rather
      than importing `storage-service.ts` keeps this module free of the object-store dependency and makes
      it unit-testable with an in-memory PNG.
    - For `kind: "border"`, draw a rectangle inset from the page edge; `"double"` draws two concentric
      rectangles.
    - Parse `color` (`#RRGGBB`) into the library's colour primitive with one small local helper.
    - `align` positions the text relative to the element's `x`/`width` box.
    - If a text element's resolved value is longer than its box at the given `fontSize`, the text must
      still be emitted (truncation or overflow is acceptable and visually checked in 11-16's manual
      verification) — never throw and never silently drop the element, which would produce a certificate
      missing the learner's name.

    Add a header comment stating this module is the sole PDF-library boundary and that D-08 rejects
    HTML-to-PDF/headless-browser rendering, so nobody "improves" it later by reaching for Puppeteer.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff-authored layout JSON → PDF construction loop | Arbitrary staff-chosen coordinates, colours, sizes and asset keys drive server-side rendering |
| object store → renderer | Image bytes fetched by `assetKey` are embedded into a document handed to learners |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-14 | Tampering | `assetKey` supplied by a layout element | mitigate | The renderer never touches the object store itself — it calls an injected `resolveAsset`; the caller (plan 11-07) resolves keys only from the template's own persisted asset records, so a hand-edited `assetKey` cannot reach an arbitrary object path from here |
| T-11-15 | Denial of Service | Pathological layout (huge dimensions, thousands of elements) | accept | Template authoring is a permission-gated staff act behind the identifier decided in 11-DECISIONS.md; a staff member able to author templates can already disrupt certificate output by other means. Rendering is synchronous and bounded by the element count the editor can produce |
| T-11-16 | Repudiation | Certificate rendered without the learner's name because an element silently failed | mitigate | Task 1 mandates: a text element whose value resolves is always emitted, never dropped; an unresolvable `assetKey` throws rather than producing a silently incomplete credential |
| T-11-17 | Tampering | Reintroduction of a headless-browser rendering path | mitigate | Acceptance criteria grep for `puppeteer|playwright|chromium` in this module and assert the PDF library appears in exactly one file repository-wide |
| T-11-SC | Tampering | npm installs | mitigate | This plan installs nothing; the library was gated and pinned in plan 11-02. `git diff package.json` must be empty |
</threat_model>
