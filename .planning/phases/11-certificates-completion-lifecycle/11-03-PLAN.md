<objective>
Build the three foundation primitives every later certificate plan consumes: a pure versioned parser for
the template layout blob, a high-entropy verification-reference generator, and the storage-service
functions for writing and reading generated certificate PDFs and template assets.

Purpose: These are small, independently testable, and block almost everything else. Getting the
reference entropy right here is the single most load-bearing security decision in the phase — the public
verification route has no rate limiting to fall back on.
Output: Two new pure-ish modules with tests, plus a fourth sibling function group in `storage-service.ts`.
</objective>

<planner_decision>
**`verificationRef` entropy diverges from `generateOrderReference()` — this is a resolved discretion
item, not an open question.** `11-CONTEXT.md` states: reuse the `generateOrderReference()` convention
"unless research finds a reason to diverge." `11-RESEARCH.md` Pitfall 1 found one and documented the
entropy math: `generateOrderReference()` emits only 32 bits of randomness (`randomUUID().slice(0,8)`),
which is acceptable because order lookup is permission-gated, and unacceptable for `verificationRef`,
which is looked up by anyone, unauthenticated, with no rate-limiting infrastructure anywhere in `src/`
(verified by exhaustive grep). This plan therefore keeps the *convention* (crypto-random,
non-sequential, prefixed) and rejects the *length*. No human gate is needed: CONTEXT.md pre-authorized
this exact divergence path.
</planner_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous internet → public verification lookup | Anyone holding or guessing a `verificationRef` reaches learner name + award title |
| staff-authored JSON → PDF renderer | A template layout blob crosses from a client editor into a server-side rendering loop |
| object store → presigned URL holder | Whoever holds a resolved presigned URL can fetch the certificate bytes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-08 | Information Disclosure | `verificationRef` enumeration on the unauthenticated verify route | mitigate | ≥128-bit crypto-random reference, no date stamp, no truncation (Task 2); entropy is the primary defense because no rate-limiting infrastructure exists anywhere in `src/` (Pitfall 2) |
| T-11-09 | Information Disclosure | Certificate object keys | mitigate | `certificates/${certificateId}/${randomUUID()}` — holding the certificate id is insufficient to construct the key (Task 3), matching the existing submission-key convention |
| T-11-10 | Information Disclosure | Leaked presigned download URL replayed | mitigate | 60-second FILE-class TTL sourced from `upload-limits.ts`, never the 4-hour VIDEO TTL (Task 3) |
| T-11-11 | Tampering | Template-asset upload as an XSS/traversal vector | mitigate | Template-asset presign reuses `upload-limits.ts`'s IMAGE allow-list verbatim with `image/svg+xml` still excluded; no parallel looser validation path (Task 3) |
| T-11-12 | Tampering | Unrecognised layout keys silently accepted then rendered | mitigate | Allow-list-per-element-kind parser that throws `UnsupportedCertificateLayoutError`, mirroring `parseCompletionRule` (Task 1) — ASVS V5 |
| T-11-13 | Spoofing | Predictable reference forged to fake a credential | mitigate | Reference is crypto-random and carries no derivable structure; the verify route resolves it against a stored row, never parses meaning out of it |
| T-11-SC | Tampering | npm installs | mitigate | This plan installs nothing — `git diff package.json` must be empty on completion |
</threat_model>
