# Phase 11 — UI Design Contract

> Visual and interaction contract for Certificates & Completion Lifecycle. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This phase renders entirely on top of the
> approved Phase 04.1 design system (`src/app/globals.css` token chain, the four hand-rolled
> primitives, `StaffShell`, `LearnerShell`) with **one genuinely novel surface** — the D-09
> certificate-template editor — which has no comparable precedent anywhere in this codebase
> (confirmed by `11-RESEARCH.md`: "no comparable drag/position UI exists... this is genuinely new
> UI work"). **No token, primitive, or shell change is proposed here.** Where this document states
> a value, it is either **inherited** (traced to `04.1-UI-SPEC.md`, not re-litigated), **decided**
> (traced to an `11-CONTEXT.md` D-number), or **resolved this phase** (this document's own answer
> to a gap `11-CONTEXT.md`/`11-RESEARCH.md` explicitly left to `/gsd:ui-phase 11`).

## 0. Grounding — Scope

### 0.1 What's new this phase

No `/staff/certificates`, `/verify/*`, or template-editor route exists on disk today. Following
`11-RESEARCH.md`'s Recommended Project Structure and the codebase's two established nesting
conventions (Course-scoped authoring, Cohort-scoped operational queues), this document proposes:

| Route (proposed) | Status | Requirement | Purpose |
|---|---|---|---|
| `/staff/certificates` | **New** | CRD-01, CRD-02, D-04 | **Landing view = the MANUAL-mode pending-review queue** (D-04's own illustrative path, taken literally as the default/actionable view — mirrors Phase 10's grading-queue landing being the actionable table, not a passive list) |
| `/staff/certificates/issued` | **New** | CRD-03, CRD-05, CRD-06 | Full `Certificate` record list — Active / Flagged / Revoked / Superseded, filterable, links to detail |
| `/staff/certificates/issued/[id]` | **New** | CRD-05, CRD-06 | Certificate detail — award facts, verification reference, revoke/reissue actions, supersede chain (old↔new links) |
| `/staff/certificates/templates` | **New** | D-09, D-10 | `CertificateTemplate` library list — Course-scoped template picking reads from here |
| `/staff/certificates/templates/new` | **New** | D-09 | The template editor, empty canvas |
| `/staff/certificates/templates/[id]` | **New** | D-09 | The template editor, editing an existing (or archived, read-only — Pitfall 5) template |
| `/verify/[verificationRef]` | **New — top-level, unauthenticated** | CRD-04 | Public verification page — deliberately **outside** the `(public)` route group (Anti-Pattern, `11-RESEARCH.md`): no `LearnerShell` catalogue nav, no "Sign in" CTA, minimal single-purpose chrome |

| `/staff/courses/[id]`, `/staff/programmes/[id]` (existing) | **Extended** | D-02, D-10 | Course/Programme edit form gains two new fields: `certificateIssuanceMode` (AUTOMATIC/MANUAL) and `certificateTemplateId` (picker from the template library) |

**Discretionary note (flagged for planner confirmation, same framing `09-UI-SPEC.md` §0.1 and
`10-UI-SPEC.md` §0.1 already used):** this document mandates the *shape* — a landing pending-queue,
a separate full-record list, a detail page for revoke/reissue, a separate template-authoring area,
and a top-level-nav-worthy unauthenticated verification route — not the literal path strings.

### 0.2 Nav placement — a new top-level `StaffShell` item, unlike Phase 10's nested tab

`StaffShell`'s `NAV` array (`src/app/staff/layout.tsx`) gains **"Certificates"** as a new top-level
entry (after "Payments"), pointing at `/staff/certificates`. This is a deliberate departure from
Phase 10's choice to nest "Grading" inside the Cohort detail page: D-04's pending-review queue is
**cross-cutting** — it lists eligible enrolments across every MANUAL-mode Course/Programme/Cohort at
once, exactly like the existing "Enrolments" and "Payments" top-level items, not scoped to one
Cohort's detail page the way Grading is. Template authoring lives one click deeper, under
`/staff/certificates/templates`, reached via a link from the Certificates landing page — not a
second top-level nav item (mirrors 04.1 D-20's "nothing here promises a page the product cannot
open" restraint already applied in `10-UI-SPEC.md` §7.0).

### 0.3 Explicitly out of this contract

- **The certificate PDF's own visual design is NOT this document's concern beyond the editor's
  chrome.** This is the single most important scope boundary in this phase's UI contract: the app's
  design system (tokens, spacing, typography roles) governs the **editor's toolbar, element
  palette, and property inspector** — but the **canvas content itself** (a school-authored
  certificate layout) is deliberately a free-design surface where staff choose arbitrary fonts,
  colors, and positions per `CertificateTemplateLayoutV1` (D-08/D-09). §5's "zero raw hex" rule does
  **not** apply to the per-element color-picker's output value — that value is user-authored
  certificate content data, not app UI styling (see §7.3.4).
- **Certificate-issuance/revocation transactional emails** — Phase 13.
- **Support ticket UI** — Phase 12; the dashboard's tickets slot stays a named gap.
- **Any change to `globals.css`, the four primitives' contracts, or `StaffShell`/`LearnerShell`'s
  chrome beyond the one new `NAV` entry and the one new `LearnerNavItem`-free public route** — this
  phase is a consumer of the 04.1 system, not a contributor to it.
- **A rate-limiting UI/banner on `/verify/[ref]`** — `11-RESEARCH.md` Pitfall 2 confirms no
  rate-limiting infrastructure exists anywhere in this codebase and this phase does not build any;
  the page's only defense-in-depth is entropy (Pitfall 1) and denial-parity response shape
  (Pitfall 3), neither of which has a UI dimension beyond §7.5's three-outcome render contract.

### 0.4 Resolved this phase — items `11-CONTEXT.md`/`11-RESEARCH.md` flagged for the UI pass

**Revoke uses `tone="danger"`; Reissue uses `tone="default"`.** Both are `ConfirmModal` consumers
(its own docstring already names "certificate revocation" as an intended consumer — confirmed
unused until now). These are NOT symmetric in tone despite both being "corrections, not deletions"
in data terms (nothing is hard-deleted either way — `supersedesId` preserves history per D-05/CRD-05).
The distinction is **real-world consequence, not database semantics**: revoking flips a credential's
*public-facing* status to invalid immediately (CRD-05: "revocation changes public status promptly")
— an externally visible, reputationally significant act, matching the weight `ConfirmModal`'s
`tone="danger"` default already carries for Phase 7's refund/payment actions. Reissuing, by
contrast, produces a *new* active credential alongside a preserved old one — corrective and
additive, matching Phase 10's `tone="default"` grade-override precedent exactly. Both require
`minReasonLength={10}` (project-wide mandatory-reason convention, `10-UI-SPEC.md` §2).

**MANUAL-mode queue: per-row action, no bulk-select.** Unlike Phase 10's D-06 batch-release,
`11-CONTEXT.md` D-04 describes a per-enrolment "staff click Issue" action, not a batch capability —
no requirement calls for issuing multiple certificates in one transaction. `ResourceTable`'s
`selection` prop is **not wired** on this view, to avoid inventing an unrequested capability (the
same discipline `10-UI-SPEC.md` §2 applied when it *did* wire selection — wire only what's asked
for). If a future phase needs batch issuance, that is a re-litigation, not a gap in this contract.

**Template-editor canvas does NOT reuse `ArrangeBoard`'s `@hello-pangea/dnd` list-drag pattern.**
`ArrangeBoard` (already in this codebase, Phase 4) solves *ordered-list* reordering via
`Droppable`/`Draggable` — a fundamentally different interaction than **free x/y canvas
positioning**, which `@hello-pangea/dnd` is not built for. This document specifies the canvas's
*visual and interaction contract* (§7.3) without mandating the underlying drag mechanism (pointer
events, a canvas library, or another dependency) — that choice is implementation detail for the
planner, flagged explicitly so no one assumes `ArrangeBoard` is reusable here. The one interaction
convention this document DOES lock: **every element also has keyboard-accessible nudge controls**
(arrow keys move the selected element by 1px, Shift+arrow by 10px) — mirroring `ArrangeBoard`'s own
"two entry points, one commit" philosophy (pointer AND keyboard, never pointer-only), which is a
WCAG 2.2 AA (NFR-09) necessity for a canvas with no native drag-and-drop accessibility story.

## 3. Spacing Scale

Inherited verbatim from `04.1-UI-SPEC.md` §3.1 — not re-litigated:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, element-palette icon padding |
| sm | 8px | Compact control internal padding, property-inspector field gaps |
| md | 16px | Card body padding, list row padding |
| lg | 24px | Card padding, section gaps, editor toolbar/palette/inspector panel padding |
| xl | 32px | Page container top/bottom padding |
| 2xl | 48px | Empty/error panel padding |

**Exception — the editor canvas itself is NOT governed by this scale.** Element positions
(`x`, `y`, `width`, `height` in `CertificateElementV1`) are staff-chosen pixel/point coordinates on
a certificate-page-sized canvas, not app-layout spacing — this is the same "content vs. chrome"
split as §0.3/§5's color exception. The canvas's own **surrounding chrome** (toolbar, palette,
inspector, page margins around the canvas preview) uses the scale above normally.

Control height stays at the inherited **38px** standard / **32px** compact (04.1 §3.2) — "Issue
certificate", "Revoke", "Reissue", "Save template", "Add element" all use the 38px standard height.

## 4. Typography

Inherited from `04.1-UI-SPEC.md` §4.3's primitive/app-UI scale — this phase introduces **no new
size or weight** for the app's own chrome, staying within the locked 4-size, 2-weight cap.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 14px | 600 | 1.5 |
| Heading | 25px | 600 | 1.2 |
| Display | 16px | 600 | 1.3 |

Notes:
- **Heading (25px/600)** is the page `<h1>` — "Certificates", "Certificate templates", "Verify a
  certificate", "{Learner name}'s certificate".
- **Display (16px/600)** fills the section-heading role — the editor's palette/inspector panel
  titles ("Elements", "Properties"), the pending-queue's per-row learner name.
- The `verificationRef` renders in **mono, Label weight (14px/600)** everywhere it appears
  (pending-queue rows have none yet; issued rows, the detail page, the public verify page, and the
  downloadable-PDF-adjacent UI all show it identically) — matching the existing
  receipt-ID/attempt-timestamp mono convention (`10-UI-SPEC.md` §1). Because `11-RESEARCH.md`
  Pitfall 1 requires materially more entropy than `generateOrderReference`'s 8-hex-char shape, the
  reference string is **longer** than prior mono-rendered identifiers in this app — its container
  must wrap (`break-all`, never `truncate`/ellipsis, since a verification reference must never be
  partially hidden from the person trying to read it off a printed certificate) rather than assume
  it fits one line, exactly the same discipline `09-UI-SPEC.md` §8 applied to unknown-length
  strings pending real content.
- **Editor chrome typography is the app's, not the certificate's.** A `CertificateElementV1`'s own
  `fontSize`/font choice (staff-authored, arbitrary) is data rendered *inside* the canvas preview —
  it does not participate in, and must never be confused with, this section's 4-size/2-weight
  cap. The property inspector's "Font size" numeric *input label* is Label role; the *value it
  controls* can be any number the school's design needs.

## 5. Color

Inherited token values from `04.1-UI-SPEC.md` §5.3 — **no new hex, no new token** for the app's own
UI. This phase is a consumer of the existing accent/success/warning/danger/neutral roles, plus one
explicit, scoped exception for the template editor's canvas content.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--surface-2` (page ground) + `--foreground` ink | Page background and default text — `StaffShell`'s existing ground for staff routes; `/verify/[ref]`'s own minimal layout uses the same `--surface-2`/`--foreground` pairing for visual continuity with the rest of the app even though it renders outside `LearnerShell` |
| Secondary (30%) | `--surface` white (cards) + `--border` (card/decorative edges) + `--muted-foreground` (hints, timestamps, metadata) | Every list row, detail fact panel, the editor's toolbar/palette/inspector chrome |
| Accent (10%) | `--accent` brand blue `#2457d6` | Reserved for exactly: "Issue certificate" primary button, "Add element" / "Save template" primary buttons in the editor, the selected canvas element's selection outline (a 2px accent-colored bounding-box ring, distinguishing "this is the app telling you what's selected" from any staff-chosen certificate color), focus ring. **Never** used for a `StatusPill` tone or a certificate-canvas element's own fill/text color. |
| Destructive / second semantic | `--danger` / `--danger-surface` | "Revoke" button and its `ConfirmModal` (§0.4), "Revoked" `StatusPill`, delete-element control in the editor (a small `X`/trash affordance on the selected element, `--danger` only on hover/focus, never a resting-state red on every element) |
| `--warning` `#b45309` / `--warning-surface` | Via `StatusPill`'s amber tone / banner backgrounds | "Flagged for review" `StatusPill` (CRD-06) — takes visual **precedence** over "Active" when both are true (a flagged certificate is still technically `status: ACTIVE` in the schema, but the UI must never show a plain "Active" green pill for a certificate a human needs to look at — see the precedence rule below) |
| `--success` `#15803d` | Via `StatusPill`'s green tone | "Active" (not flagged) `StatusPill`, "Issued" confirmation toast/state |
| `neutral` (grey pill tone) | `--pill-grey-*` | "Superseded" `StatusPill` (an old version after reissue — deliberately the least alarming tone, since superseding is expected lifecycle, not a problem) |
| `accent` (blue pill tone) | `--pill-blue-*` | Not used by this phase's own new states — reserved per Phase 6/9's existing "Active enrolment" convention, left undisturbed |

**Precedence rule (CRD-06, load-bearing):** `StatusPill` tone selection for a `Certificate` row
follows this exact order, first match wins: (1) `status === "REVOKED"` → `danger` "Revoked"; (2)
`reviewFlaggedAt !== null` → `warning` "Flagged for review" (**even if** `status === "ACTIVE"` —
flagged-but-technically-active must never render as a plain green "Active" pill, since that would
contradict CRD-06's "flagged for review" requirement being visually inert); (3) `status ===
"SUPERSEDED"` → `neutral` "Superseded"; (4) `status === "ACTIVE"` (unflagged) → `success` "Active".
This four-branch order is a rendering contract, not just a data fact — a plan that computes tone
from `status` alone, ignoring `reviewFlaggedAt`, fails this spec.

**§0.3's color exception, stated precisely:** the template editor's per-element color picker (for
text color, border color, background fill within `CertificateElementV1`) legitimately outputs and
displays **arbitrary hex values chosen by staff** — this is certificate-content data, analogous to
how a `RichTextEditor`'s authored body text can contain arbitrary inline styles Phase 4 already
permits. The **editor's own chrome** (buttons, panels, the selection-outline ring) must still draw
exclusively from the semantic token set above. `gsd-ui-checker`'s zero-raw-hex dimension should
scope its check to files outside the canvas-rendering/color-picker-value path, mirroring how prior
phases scoped that same rule around user-authored content.

## 7. Screens & States — Interaction Detail

### 7.0 Staff nav

"Certificates" added to `StaffShell`'s `NAV` array (§0.2), positioned after "Payments" — both are
cross-cutting, permission-scoped operational lists rather than record-detail sub-views.

### 7.1 Pending-review queue (`/staff/certificates`)

`ResourceTable`, no selection (§0.4). Columns: Learner, Award (Course/Programme title, with a small
type indicator — "Course" / "Programme" text, not an icon, matching the existing plain-text type
convention `10-UI-SPEC.md` §7.1 used for Quiz/Assignment before deciding on icons — here reused as
plain text since there is no existing icon precedent for Course-vs-Programme and inventing one is
unnecessary scope), Eligible since (mono date), row action "Issue certificate" (`--accent`
`BTN_PRIMARY`, 38px). Denied/scope rules follow the existing `certificates.issue`
`withPermission` pattern — same denied visual every other `ResourceTable` already uses, no new
denial copy.

Clicking "Issue certificate" opens a lightweight `ConfirmModal` (§6.1, no reason field — this is
D-03's "AUTOMATIC" issuance shape's manual-trigger twin, a forward action, not a correction). On
confirm: the row disappears from this queue (it's no longer eligible-not-issued) and a toast/inline
success state confirms, matching the existing `revalidatePath` read-your-own-write convention
(`10-UI-SPEC.md` §7.2.3).

### 7.2 Issued list (`/staff/certificates/issued`)

`ResourceTable`, segmented filter (§6.1: All/Active/Flagged/Revoked, ≤4 options — auto-activates the
existing segmented-filter control, no new filter UI). Columns: Learner, Award, Verification
reference (mono, `break-all`), Issued (mono date), Status (`StatusPill`, precedence rule §5). Row
click → detail page. No inline actions in the list itself — revoke/reissue live only on the detail
page (§7.4), matching `10-UI-SPEC.md` §7.2.4's "one focused action screen, not row-level destructive
buttons in a dense table" precedent for consequential actions.

### 7.3 Template editor (`/staff/certificates/templates`, `/new`, `/[id]`)

#### 7.3.1 Templates list

`ResourceTable`. Columns: Name, Default (§6.1 pill), Last edited (mono date), row action "Edit" (or
"View" for an archived template, read-only per Pitfall 5 — no Edit affordance on an archived row,
only a plain link to view its locked layout, since editing an archived template that
already-issued certificates conceptually reference would violate the "issuance is a frozen
artifact" invariant `11-RESEARCH.md` Pitfall 5 names). "New template" CTA top-right (`--accent`
`BTN_PRIMARY`).

#### 7.3.2 Editor layout

Three-panel layout, matching no existing precedent structurally but built from the same chrome
primitives (`--surface` panels, `--border` dividers, the standard spacing scale, §3's
canvas-content exception):

```
┌─────────────┬──────────────────────────────┬─────────────┐
│  Elements   │           Canvas              │ Properties  │
│  (palette)  │  (certificate-page preview,   │ (inspector) │
│  §7.3.3     │   scaled to fit, §7.3.4)       │  §7.3.5     │
└─────────────┴──────────────────────────────┴─────────────┘
```
Palette and inspector panels: `w-64`-equivalent fixed-width sidebars, `--surface` background,
`--border` dividing lines, `lg` (24px) internal padding — same visual language as `StaffShell`'s own
228px sidebar (04.1 §7.1), reused for panel treatment rather than reinvented. Below `lg` breakpoint,
panels collapse to expandable drawers (mirrors `StaffShell`'s off-canvas collapse mechanism, same
CSS-toggle approach, no new responsive pattern).

Template name (`TextInput`, required) and page-size/orientation controls (`CertificateTemplateLayoutV1`'s
`pageSize`/`orientation`, §Pattern 4 of `11-RESEARCH.md`) sit in a header bar above the three-panel
layout, alongside "Save template" (`--accent` `BTN_PRIMARY`) and a Cancel/back link.

#### 7.3.3 Element palette

One entry per element kind (§1's icon table: `Type` Text, `ImageIcon` Image, `Square` Border,
`QrCode` QR code if included) — clicking adds a new element at a default position (canvas center)
in a default size, immediately selecting it (moves focus to the canvas selection, opening the
property inspector for that element). This click-to-add pattern, not drag-from-palette, is the
locked interaction — drag-from-palette-onto-canvas is a strictly harder a11y problem (two-stage
drag) with no accessibility fallback; click-to-add plus keyboard-nudge (§0.4) gives every staff
member, including keyboard-only users, a complete path to build a template.

#### 7.3.4 Canvas

Renders at a fixed aspect ratio matching the template's `pageSize`/`orientation` (A4/Letter ×
landscape/portrait), scaled to fit the available panel width, with a visible `--border` page
boundary (a plain rectangle, not a drop-shadow-heavy "paper" skeuomorph — matching this app's flat,
bordered-card visual language everywhere else). Each placed element renders as its own
absolutely-positioned box within the canvas:

- **Selected element**: 2px `--accent` outline ring (§5) + small delete (`X`, `--danger` on
  hover/focus only, §5) and resize-handle affordances at the four corners.
- **Unselected elements**: no visible chrome beyond their own content (a text element shows its
  actual text at its actual staff-chosen size/color; an image element shows the actual uploaded
  asset; a border element shows its actual line).
- **Dynamic-field text elements** (`learnerName`/`awardTitle`/`issuedAt`/`verificationRef`) render
  **placeholder sample values** in the canvas preview — e.g. "Jordan Example", "Sample Award
  Title", today's date, a sample reference string — never the literal token name
  (`{{learnerName}}`), so staff see something close to a real rendered certificate while designing.
  A small muted caption beneath the selected dynamic-field element's inspector panel clarifies:
  "This will be replaced with the learner's actual {field} when issued."
- **Keyboard interaction** (§0.4): selected element responds to arrow keys (1px nudge) and
  Shift+arrow (10px nudge); Delete/Backspace removes it (no `ConfirmModal` — element deletion
  inside an unsaved draft is trivially undoable by not saving, matching `ArrangeBoard`'s own
  "nothing autosaves" philosophy, §0.4).
- **Nothing autosaves.** "Save template" commits the whole `CertificateTemplateLayoutV1` blob in one
  write, disabled until something changes — reusing `ArrangeBoard`'s exact dirty-state/disabled-
  until-changed convention (`ArrangeBoard.tsx`'s own `dirty`/`onSave` props), not inventing a new
  autosave or debounced-write pattern.

#### 7.3.5 Property inspector

Renders the selected element's editable fields, form-primitive styled (`ResourceForm`'s
`FormField`/`TextInput` conventions, §2):

- **All elements**: X, Y, Width, Height (numeric inputs, synced live with drag/nudge — editing a
  number moves the element on canvas and vice versa).
- **Text element**: Field type (select: the four dynamic fields + "Custom text"), literal text
  (only if "Custom text"), font size (numeric), color (a color-picker input — §5's exception,
  arbitrary hex allowed here), alignment (segmented: Left/Center/Right).
- **Image element**: uploaded asset (reuses the presigned-upload pattern, `UploadPanel`'s visual
  states per `10-UI-SPEC.md` §2 — `success`/`danger`/`neutral` `StatusPill` mapping for the
  upload's own state, MIME-restricted per `upload-limits.ts`, no `image/svg+xml` per
  `11-RESEARCH.md`'s Security Domain table).
- **Border element**: style (select: Solid/Double), color (picker), width (numeric, "pt" suffix
  hint).
- Nothing selected: inspector shows a muted placeholder — "Select an element to edit its
  properties." — never a blank panel with no explanation.

#### 7.3.6 Discretionary note — no separate "publish" step for templates

`11-CONTEXT.md`/`11-RESEARCH.md` do not describe a template draft/publish lifecycle distinct from
"archived or not" (Pitfall 5). This document does not invent one: "Save template" produces an
immediately-usable template (selectable from any Course/Programme's `certificateTemplateId`
picker the moment it's saved) — archiving, not a publish gate, is the only lifecycle transition
this phase's data model supports. If a future phase needs draft-vs-published templates, that is new
scope, not a gap here.

### 7.4 Certificate detail (`/staff/certificates/issued/[id]`)

`DetailLayout`, stacked mode. Read-only `DetailFacts` per §6.1's fact list, flagged/revoked banners
(§6.1) rendered above the facts when applicable (precedence: revoked banner wins over flagged, since
a revoked certificate's flagged history is historical context, not an active concern — mirrors §5's
`StatusPill` precedence exactly). Actions zone:

- **Active, unflagged**: "Revoke certificate" (`Ban` icon, `--danger`-bordered `BTN`, opens
  `ConfirmModal` `tone="danger"`, §6).
- **Active, flagged**: same "Revoke certificate" action, plus the flagged banner's own framing
  (§6.1) — no separate "Clear flag"/"Dismiss" action exists in this phase's scope (CRD-06 requires
  flagging for human review, not a one-click dismissal that could silently un-flag without an
  audited decision; if the correction turns out to be fine, staff simply take no action and the
  flag itself is a permanent historical fact on the record, not a togglable UI state).
- **Revoked**: "Reissue certificate" (`RefreshCw` icon, `--accent`-bordered `BTN`, opens
  `ConfirmModal` `tone="default"`, §6) — the only action available on a revoked certificate.
- **Superseded**: no actions — read-only historical record, link to the superseding certificate
  (§6.1's supersede-chain fact).

### 7.5 Public verification page (`/verify/[verificationRef]`)

**Deliberately minimal, unauthenticated, outside every existing shell** (§0.1 Anti-Pattern). A
standalone `layout.tsx` renders just enough chrome for brand continuity — a simple header with the
product/school name (reusing whatever brand mark `(auth)/layout.tsx`'s split panel already uses,
not a new logo asset) and nothing else: no nav, no "Sign in" link, no footer catalogue links. Single
centered card, `max-w-md`, `--surface` background, `--border`, matching the visual weight of
`(auth)`'s existing card treatment (04.1 §7.2) since both are single-purpose, unauthenticated,
minimal-chrome surfaces.

Exactly three render outcomes (Pitfall 3's denial-parity discipline, adapted from a route handler
to a page — same "one lookup function, one of exactly three outcomes" principle):

| Outcome | Icon | Copy |
|---|---|---|
| **Active** | `ShieldCheck`, `--success` | "This certificate is valid." Then the approved minimal facts as a plain `<dl>`: Learner name, Award title, Issued date. Nothing else — no course description, no school-internal ids. |
| **Revoked** | `ShieldX`, `--danger` | "This certificate has been revoked and is no longer valid." — the same minimal facts still shown (Learner name, Award title, Issued date) per CRD-04's "active/revoked status **and** approved award facts" wording — revocation reason is **never** shown (staff-internal detail, not an approved public fact). |
| **Not found** | `ShieldQuestion`, `--muted-foreground` (deliberately neutral, not `--danger` — an unknown reference is not itself alarming, it might just be a typo) | "We couldn't find a certificate with this reference. Double-check the reference and try again." — **zero other fields rendered**, not even empty placeholders for Learner/Award/Issued (Pitfall 3: the response shape for "unknown" must never structurally echo the shape used for a real result). |

No loading spinner needed beyond the existing SSR-page convention (`09-UI-SPEC.md` §8's "SSR pages,
no client-side loading state for initial render" — this route performs one server-side lookup per
`11-RESEARCH.md` Pitfall 6's Cache-Components guidance, rendering directly, no client fetch).

A plain-text entry form (single text input + "Verify" button) sits above the result card, letting a
visitor who lands on the bare `/verify` path (no reference in the URL) type one in manually —
`11-CONTEXT.md`/`11-RESEARCH.md` don't specify this explicitly, but CRD-04's "public certificate
verification" framing implies more than a deep-link-only surface; this is a **discretionary
addition**, flagged for planner confirmation, following the same low-risk-addition pattern
`06-UI-SPEC.md` used for comparable small gaps.

### 7.6 Dashboard certificate slot (`/dashboard`, extends Phase 9)

Fills Phase 9's `CERTIFICATE_DEFERRED` named-gap card (`09-UI-SPEC.md` §6.1's "Certificate —
arriving in a future update" placeholder). Five branches, first match wins, per enrolment:

1. **Not yet complete** — existing Phase 9 copy stays exactly as-is until a `CompletionRecord`
   passes (out of this phase's concern to alter).
2. **Eligible, MANUAL mode, not yet issued** — §6.1's reassuring "being finalized" copy, no action.
3. **Issued, active, unflagged** — `Download` icon link "Download certificate" →
   `/api/certificates/[id]/download` (opens/downloads directly, no intermediate confirmation —
   downloading one's own certificate is not a destructive or consequential action).
4. **Issued, flagged** — §6.1's non-alarming flagged copy; the download link is **still shown**
   (CRD-06 says "flagged for review," not "hidden" — a flag does not retroactively deny the
   learner's already-earned access to their own file; only an actual revocation removes the
   download).
5. **Revoked** — §6.1's revoked copy, no download link (a revoked certificate's file is no longer
   the credential of record — the detail-level PDF may still exist in storage per D-07/CAT-08's
   no-hard-delete convention, but this phase's UI does not surface a "download your revoked
   certificate" affordance to a learner, since that would visually contradict "no longer valid").
