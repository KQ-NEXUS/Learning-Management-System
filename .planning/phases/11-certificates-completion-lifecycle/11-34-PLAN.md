<objective>
Fix CR-02: the template asset allow-list accepts WebP and GIF but the renderer embeds only PNG and JPEG, so one such logo breaks every issuance from that template.

Split out of plan 11-29 (revision, iteration 1) so this font-independent fix does not wait behind the blocking human font gate in plan 11-26. Reconcile both sides: restrict template assets to PNG and JPEG (the "restricting asset types" part, explicitly in scope) and guard the renderer so an undecodable image is skipped rather than fatal. An asset the resolver cannot FETCH (missing object, storage outage) still throws: that is an operational, retryable failure, and after plan 11-30 it can no longer roll back a caller's write. Unsupported or corrupt image BYTES are permanent, so retrying can never succeed; skipping the image is the only outcome that lets the certificate exist.

Ordering note: this plan and plan 11-29 both edit certificate-pdf-renderer.ts and tests/certificate-pdf-renderer.test.ts, so they can never share a wave. This plan runs first (wave 1, no font dependency); plan 11-29 (wave 2) then swaps the font and MUST leave the image guard and its tests intact.

Known limits recorded here, not fixed: existing templates that already reference WebP/GIF assets keep working (the image is skipped); the upload UI stops creating new ones. WR-03 (asset-key domain validation) stays out of scope.

Output: the image guard, the template-asset allow-list, and tests that fail against the current code.
</objective>
