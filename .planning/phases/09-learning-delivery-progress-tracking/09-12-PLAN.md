<planner_rulings>
- **DD-2 (resolves D-09's client event model, left to Claude's discretion):** `VideoWatchTracker` is a
  `"use client"` component that accepts the server-rendered subtree as `children` and locates the
  `<video>` element through a ref on its own wrapping `<div>` (`ref.current.querySelector("video")`).
  This is what lets `LessonMediaPlayer.tsx` stay a Server Component with no client directive, as its
  own doc comment requires, while still getting a listener attached. It attaches on mount, detaches on
  unmount, and no-ops when no `<video>` is found.
- **DD-28 (resolves the throttle interval):** at most ONE dispatch per 15 seconds of wall clock while
  playing, plus an immediate flush on `pause`, `ended`, and `visibilitychange` to hidden. RESEARCH
  Pitfall 3 makes this a hard constraint, not a preference: `timeupdate` fires roughly 4x/second and
  Next.js dispatches Server Actions sequentially per client, so a per-event dispatch would queue
  indefinitely on a slow connection.
- **DD-29:** a failed write is swallowed (logged to `console.debug` only), never surfaced as an error
  state, and never blocks playback. Because 09-06 stores forward-only high-water marks, the next
  throttled tick carries the same or a higher position and repairs the gap — this is the UI-SPEC
  section 8 backstop's required behaviour.
- **DD-30:** no progress percentage, scrubber, or overlay of any kind is drawn on top of the
  `<video>` element (UI-SPEC 7.3, explicit). The native controls remain the sole visible progress UI.
</planner_rulings>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser playback state → server progress record | Playback position is entirely client-observed and client-reported |
| background Server Action dispatch → session lifetime | A write can fire after the session expires or the tab is backgrounded |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-05 | Tampering | Forged watch position | accept (documented) | The action's input carries seconds only — no percent, no completion flag. The server clamps, computes the percent, and owns the 90% decision (09-06). Client-reported POSITION remains trusted at the same level as mainstream LMS video tracking; recorded as a known accepted v1 limitation per RESEARCH's Security Domain table. A stronger anti-gaming control is a v2 concern |
| T-09-08 | Denial of Service | Dispatch frequency | mitigate | DD-28 — one dispatch per 15s plus an in-flight guard; Next.js's sequential per-client dispatch means a backlog cannot fan out, and the composite-unique upsert means row count is bounded regardless |
| T-09-41 | Denial of Service | Playback blocked by a failed write | mitigate | DD-29 — every dispatch is try/caught, failures are `console.debug` only, and no failure path touches the video element; asserted by a test on `paused` |
| T-09-42 | Tampering | Stale write reversing a D-15 undo | mitigate | 09-06's forward-only high-water mark requires the percent to advance past the stored value before re-completing |
| T-09-43 | Information Disclosure | Background write after session expiry | mitigate | The action returns `{ completed: false }` for a missing actor instead of redirecting, so an expired session neither writes nor navigates the learner away mid-video |
| T-09-SC | Tampering | npm/pip/cargo installs | accept | Zero new packages this phase — no video-analytics library is added, per RESEARCH's rejected alternative |
</threat_model>
