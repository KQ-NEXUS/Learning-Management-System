# Phase 9 — UI Design Contract

> Visual and interaction contract for Learning Delivery & Progress Tracking. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This phase is the **first genuinely new
> learner-facing surface** since Phase 6/7's checkout screens — there is no prior dashboard,
> lesson-reading, or session-visibility UI to extend — but it renders entirely on top of the
> approved Phase 04.1 design system (`src/app/globals.css` token chain, the four hand-rolled
> primitives, `LearnerShell`) and reuses `src/components/catalogue/LessonContent.tsx` verbatim,
> which Phase 4 built specifically anticipating this phase ("Phase 9 builds the learner journey
> around this component" — its own doc comment). **No token, primitive, or shell change is
> proposed here.** Where this document states a value, it is either **inherited** (traced to
> `04.1-UI-SPEC.md`, not re-litigated), **decided** (traced to a `09-CONTEXT.md` D-number), or
> **discretionary** (this document's own resolution of a gap `09-CONTEXT.md` explicitly left to
> Claude's discretion, flagged as such).

## 0. Grounding — Scope

### 0.1 What's new this phase

No `/dashboard`, `/learn/*`, or session-visibility route exists on disk today (confirmed this
session — `src/app` has `(auth)`, `(checkout)`, `(public)`, `account`, `orders`, `staff`, and no
learner-delivery surface). `09-CONTEXT.md` leaves exact routing to research/planning; this
document proposes the route shape the planner should adopt, following the codebase's established
convention of addressing a learner's own record by its owned-resource id (`/checkout/[orderId]`,
`/orders/[reference]`) rather than by course slug, since one learner may in principle hold more
than one Enrolment and the Enrolment — not the Course — is the authorization boundary (D-checks
throughout `09-CONTEXT.md` are enrolment-scoped, never course-scoped):

| Route (proposed) | Status | Requirement | Purpose |
|---|---|---|---|
| `/dashboard` | **New** | LRN-01 | Personal enrolment dashboard — next action, progress, sessions, obligations, results, tickets, certificate state, own records only |
| `/learn/[enrolmentId]` | **New** | LRN-02 | Course-level lesson list — ordered Modules/Lessons with lock state, links into individual lessons |
| `/learn/[enrolmentId]/lessons/[lessonId]` | **New** | LRN-03, LRN-04, LRN-05 | Lesson reading pane — renders `LessonContent`, manual complete/undo control, video watch-progress tracking |
| `/learn/[enrolmentId]/sessions` | **New** | LRN-06 | Scheduled-session list for this Cohort, meeting-link visibility window |

**Discretionary note (flagged for planner confirmation):** this document does not mandate these
exact path segments — it mandates the *shape* (enrolment-scoped, not course-slug-scoped; a
dashboard entry point; a course-level lesson list distinct from the per-lesson reading pane;
sessions as their own view rather than buried inside the lesson list). If research finds a
stronger precedent inside the codebase during planning, the route strings may change without
invalidating anything else in this document.

### 0.2 Explicitly out of this contract

- **Quiz/Assignment lesson content** — `LessonContent`'s existing `QUIZ`/`ASSIGNMENT` branches
  already render a `Placeholder` ("assessment authoring and delivery arrive in Phase 10 — this
  lesson still holds its place in the order"). This phase does not touch that branch; Phase 10
  replaces it.
- **Certificate download/verification UI** — Phase 11. The dashboard's certificate-state slot
  renders as a named gap (§6.1) exactly like Phase 5's roster columns did for this phase.
- **Support ticket list/detail UI** — Phase 12. The dashboard's tickets slot renders as a named
  gap (§6.1).
- **Any change to `globals.css`, the four primitives' contracts, `LearnerShell`'s chrome, or
  `LessonContent`'s existing eight-branch content-type switch** — this phase is a pure consumer
  of the 04.1 system and Phase 4's content renderer, not a contributor to either.
- **Staff-side attendance/enrolment UI** — already built in Phase 5 (`RosterTab`, session
  management). This phase's `"attendance changed"` consumption is a completion-recalculation
  trigger (D-11), not a UI change to the staff roster.

### 0.3 Discretionary layout choice — fact-card pattern and `LearnerShell`, not `DetailLayout`

Same reasoning `06-UI-SPEC.md` §0.3 already established and this document reuses rather than
re-deriving: `DetailLayout` is shaped for **staff** records (breadcrumbs, RBAC-flavored
`denied`/`error` states keyed to `permission`). Every screen this phase adds is a
**learner-owned, ownership-authorized** record — no `withPermission` call, no permission string to
show in a denied state; ownership is "this Enrolment belongs to the calling actor," which is a
different, and simpler, boolean than RBAC's scope match. This phase reuses `LearnerShell` (not
`StaffShell`) and the fact-card `<dl>` pattern Phase 6 already established for order-summary/
confirmation, extended with the pieces this phase specifically needs: a lesson-list tree with lock
affordances, a progress bar, and a lesson reading pane.

## 4. Typography

Inherited from `04.1-UI-SPEC.md` §4.3's primitive/app-UI scale — this phase introduces **no new
size or weight**, staying entirely within the 4-size, 2-weight cap already locked for that scale.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 14px | 600 | 1.5 |
| Heading | 25px | 600 | 1.2 |
| Display | 16px | 600 | 1.3 |

Notes:
- **Heading (25px/600)** is the page `<h1>` — "Your dashboard", "{Course title}", "{Lesson
  title}", "Scheduled sessions".
- **Display (16px/600)** fills the card/section-heading role — dashboard card titles ("Next up",
  "Your progress", "Upcoming sessions"), the lesson-list Module group headers, sessions-list
  card titles.
- The progress-percentage figure ("62% complete") is **not** a fifth type size — it renders at
  the Label role (14px/600), matching the existing "countdown timer" precedent from
  `06-UI-SPEC.md` §4 (color/weight carry emphasis, not a bespoke display size).
- The blocking-lesson-title inline in a locked row's explanation text ("Complete '{Lesson
  title}' to unlock this", D-06) renders at Body role (14px/400) with the quoted title at Label
  weight (600) via an inline `<strong>`/`font-semibold` span — not a separate size.

## 7. Screens & States — Interaction Detail

### 7.1 Dashboard (`/dashboard`)

Renders inside `LearnerShell` (new "Dashboard" nav item leading, §2), single page, no tabs — a
grid of cards on ≥768px (`Next up` full-width top row; `Your progress` / `Upcoming sessions` as a
two-column row beneath; the four named-gap slots as a final row of smaller cards), stacking to one
column below 768px (existing responsive convention, no new breakpoint).

- **"Next up" card** — the phase's single most important derivation (`09-CONTEXT.md` flags this
  as Claude's Discretion). Priority order, evaluated per Enrolment, first match wins: (1) an
  upcoming session starting within the next 24 hours → session variant; (2) the next
  incomplete required Lesson in course order (per D-04/D-05's sequencing) → lesson variant, only
  if it is not itself locked (it never should be, since it's the *next* required lesson by
  definition — but the render must not assume this, it must check); (3) course/programme fully
  complete → a congratulatory variant pointing at the (forward-gap) certificate slot; (4) nothing
  matches (e.g. self-paced access window ended before completion, D-03) → the empty state (§6).
  Each Enrolment gets its own card if the learner holds more than one active Enrolment — the
  dashboard does not collapse multiple enrolments into a single derived action.
- **"Your progress" card** — the teal progress bar (§5, "new this phase" row) plus the "{N} of {M}
  required lessons complete" caption. If `Cohort.attendanceThresholdPct` is set (D-10's rule (b)),
  a second, identical bar for attendance renders beneath it, labelled "Attendance: {earned}% of
  {required}% required" — two independent bars, never merged into one composite percentage
  (the two rule components are evaluated and displayed separately, matching how `readiness-service`
  already keeps distinct check items separate rather than collapsing them into one score).
- **"Upcoming sessions" card** — up to 3 nearest sessions as compact rows (title, date/time,
  mode icon `MapPin`/`Video`); "View all" link to `/learn/[enrolmentId]/sessions` if more than 3
  exist; empty-state copy (§6) if none.
- **Named-gap row** — four small cards, muted, per §6.2.

### 7.2 Lesson-list page (`/learn/[enrolmentId]`)

Renders inside `LearnerShell`, single column, max-width matching the shell's content width (no
narrower override, unlike checkout's focused 640px — this is a browsing/scanning view, not a
focused read-then-act task).

- **Access gate (D-07)** — before any lesson-list content renders, the server verifies
  `Enrolment.status === "ACTIVE"`. Anything else (including `PENDING_PAYMENT`) renders the
  **same denied treatment ResourceTable/DetailLayout already use for RBAC denial** (visual
  consistency, not the same authorization mechanism) — "You don't have access to this course yet"
  with, where applicable, a link back to the relevant order/checkout page. No lesson titles,
  module structure, or any other catalogue detail leaks through this gate (D-07's "nothing is
  accessible at all" is absolute — this is a stricter gate than RBAC-06's denial-parity rule,
  since there is no "record exists" question at all here, only an access-window boolean).
- **Module groups** — Display-role (16px/600) group headers, each followed by its ordered Lesson
  rows. A Lesson row: leading state icon (`CheckCircle2` green / `PlayCircle` accent for the
  current "next action" lesson / `Circle` muted for not-started-but-unlocked / `Lock` muted+warning
  tint for locked), title (Body role, Label weight if it's the current lesson), optional duration/
  type hint (Body role, muted, e.g. "Video · 8 min" — only if that metadata exists; no
  placeholder when absent, per the established "conditional fact row, never an empty placeholder"
  convention from `06-UI-SPEC.md` §7.2).
- **Locked row** — entire row is non-interactive (no `href`, `aria-disabled="true"` on a
  `<div>` rather than a disabled-styled `<a>`, since a locked row genuinely has nothing to
  navigate to yet), with the D-06 explanation text (§6.1) rendered beneath the title at Body role,
  muted-foreground, referencing the specific blocking lesson by title — never a generic
  "complete the previous lesson."
- **Course-level progress bar** — same teal composition as the dashboard's progress card (§7.1),
  rendered once at the top of this page beneath the `<h1>`, so a learner scanning module structure
  also sees where they stand without returning to the dashboard.

### 7.3 Lesson reading pane (`/learn/[enrolmentId]/lessons/[lessonId]`)

Renders inside `LearnerShell`, single column, `max-width: 720px` centered (matching prose-reading
width conventions, wider than checkout's 640px since lesson bodies may include wider embeds/
images at `max-w-2xl` per `LessonContent`'s own existing classes — the wrapping page must not
constrain narrower than what `LessonContent` itself already assumes).

- **Header** — breadcrumb-style back link ("← {Course title}", `ChevronLeft` icon, reusing the
  existing "back to courses" glyph precedent) to the lesson-list page, then the lesson title
  (Heading role).
- **`LessonContent`** — rendered exactly as authored, unchanged (§2). This is the entire content
  body; this phase adds nothing inside it.
- **Manual-complete control** (renders only when `Lesson.allowManualComplete` is true, D-08/D-09
  — TEXT/FILE/IMAGE/EMBED/LINK types by default; VIDEO only if manual override is separately
  allowed, since VIDEO's primary path is auto-completion): a single button beneath the content,
  38px height, `--accent` background when actionable ("Mark complete"), switching to a
  `CheckCircle2` + "Completed" static label with an adjacent muted "Undo" text link once complete
  (§6.1) — never two competing buttons at once.
- **Auto-video completion** (VIDEO type, D-08) — no button at all in the default case; the
  player's watch-progress crossing 90% silently writes the `LessonProgress` row and the page
  reflects it via the same "Completed" + caption + "Undo" treatment as manual completion (§6.1),
  distinguished only by the caption text ("Marked complete automatically" vs. no caption for a
  manual mark). The watch-progress mechanism itself (throttled `timeupdate` writes, exact
  interval/debounce) is implementation detail per `09-CONTEXT.md`'s Claude's Discretion — this
  document's only visual requirement is that **no progress percentage or scrubber overlay is
  drawn on top of the native `<video>` element** (the browser's own controls remain the sole
  visible progress UI during playback; the 90%-crossing event is silent until it fires, then the
  post-completion caption appears below the player, not on it).
- **Prev/Next lesson navigation** — footer row, "← Previous lesson" / "Next lesson →" as
  `--accent` text links (not buttons — this is wayfinding, not a primary action), each disabled
  (rendered as muted, non-interactive text, not hidden) at the first/last lesson respectively. The
  "Next lesson" link is **not** gated by this lesson's completion — navigating forward is always
  allowed once a lesson is unlocked; D-04's lock only gates *which lessons are reachable at all*,
  not re-visiting an already-unlocked one out of completion order.

### 7.4 Sessions page (`/learn/[enrolmentId]/sessions`)

Renders inside `LearnerShell`, fact-card list matching the dashboard's "Upcoming sessions" card
pattern but showing the full Cohort session list (past and future), each session as its own
`rounded-lg border border-border bg-surface px-4 py-3 shadow-xs` card (§6.1 fields). Sessions are
grouped by "Upcoming" / "Past" (a simple date-relative split, not a filter control — this list is
expected to be short per Cohort, matching Phase 5's own scheduling volume assumptions, so no
pagination or search is introduced). A past session shows its attendance outcome if the learner's
own `AttendanceRecord` exists for it (`StatusPill`: `success` "Attended" / `neutral`
"Not recorded" / `warning` "Late" / `danger` "Absent" — reusing the exact tone mapping Phase 5
already established for attendance states, not inventing a new one).

### 7.5 Open item — staff override UI (D-14)

`09-CONTEXT.md` D-14 requires staff be able to override a learner's `LessonProgress` with a
mandatory reason, mirroring Phase 5's attendance-correction pattern. **This document does not
specify a staff screen for it** — no staff route for lesson-progress override exists on disk, and
`09-CONTEXT.md` does not name one explicitly (it describes the *behavior*, not a *screen*). Flagged
for the planner: either (a) fold it into the existing `staff/cohorts/[id]` roster/detail area as a
new action on the (currently deferred) progress column Phase 5 already reserved, using
`ConfirmModal` exactly as Phase 5's attendance correction does, or (b) confirm with the user this
is out of Phase 9's actually-shipped scope and belongs to a later pass. This document takes no
position beyond: **if built this phase, it must use `ConfirmModal` verbatim** (mandatory reason,
`StaffShell`, not `LearnerShell`) — never a bespoke dialog.
