<planner_rulings>
- **DD-6 — PLANNER RULING on RESEARCH Assumption A1 / Pitfall 5 (`Enrolment.status` → `COMPLETED`).**
  This phase does **NOT** transition `Enrolment.status`. `VALID_TRANSITIONS.COMPLETED` is `[]` —
  terminal — while D-12 requires a satisfied completion to be reversible via `supersededAt` (an
  attendance correction can drop a learner back below threshold, and D-13/D-15 let a learner
  self-undo at any time). Transitioning to a terminal `COMPLETED` would make the very next supersede
  unrepresentable, and would also silently free the `(userId, cohortId) WHERE status = 'ACTIVE'`
  partial unique index, permitting a duplicate enrolment. `CompletionRecord` is the evidence LRN-07
  asks for and the evidence Phase 11 consumes; Phase 11 ("Certificates & **Completion Lifecycle**")
  owns any status transition, alongside the revocation semantics that make a terminal state safe.
  Record this ruling in `completion-service.ts`'s header so the `enrolment-transitions.ts` comment is
  answered in code rather than left dangling. Do NOT call `assertTransition` from this service.
- **DD-12:** recalculation is a plain synchronous function call taking the caller's `tx`. It never
  polls `DomainEvent` (the outbox header is explicit that it is not a work-queue API) and never
  schedules anything (D-11 forbids a batch/sweep job).
- **DD-13:** the events this phase emits are write-once, read-never-by-this-phase output for Phase
  13. No Phase 9 code path may consume them as a trigger — that is what would create the duplicate/
  circular write RESEARCH Pitfall 4 describes.
</planner_rulings>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff attendance mutation → learner completion state | A staff-authorized attendance write now has a side effect on a learner's completion evidence; both must commit or roll back together |
| stored rule JSON → completion decision | An unevaluable rule must fail, never default to a verdict |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-19 | Repudiation | `CompletionRecord` supersede | mitigate | `supersededAt` is stamped, never a delete; `completedAt`, `ruleVersion` and `evidence` remain, so the historical verdict stays reconstructable (D-12) |
| T-09-20 | Tampering | Completion write atomicity | mitigate | `recalculateCompletion` takes the caller's `tx` and opens no transaction of its own — a failed attendance write cannot leave a completion recorded, and vice versa |
| T-09-21 | Spoofing | Forged completion via unevaluable rule | mitigate | `parseCompletionRule` throws on unknown version/keys and the throw propagates out of the transaction; an unpinned cohort returns `not-evaluable` with zero writes |
| T-09-22 | Denial of Service | Recalculation cost on bulk attendance entry | accept | One recalculation per enrolment per write, bounded by cohort size; no fan-out, no recursion (DD-13 forbids event-triggered re-entry) |
| T-09-23 | Elevation of Privilege | `Enrolment.status` mutation | mitigate | DD-6 — this service never calls `assertTransition` and never updates `Enrolment`; enforced by an explicit test assertion |
| T-09-SC | Tampering | npm/pip/cargo installs | accept | Zero new packages this phase |
</threat_model>
